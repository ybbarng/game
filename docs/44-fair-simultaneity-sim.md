## 0. 한 줄 결론

**반응 시간 비교(방법 3)는 망 종류와 상관없이 같은 성적(Δ 20ms에서 85%, 30ms에서 94%)을 내고 방장 이점을 50%로 지운다. 남는 오차는 거의 모두 기기 화면·터치 지연 차이다. 반면 거짓 rt 거르기(방법 4)는 여유를 넓히는 만큼 거짓말쟁이 이득도 커지고, RTT_min을 청구하는 쪽이 부풀릴 수 있으면 아예 무너진다. 원카드 B안은 여유 0.3초면 억울한 판정이 끝 직전에서도 2~4%이고 그 원인은 전부 앞 막힘(패킷 재전송)이다.**

가장 크게 짚을 것 세 가지:

1. **창 X는 정확도를 올리지 못한다.** 방법 3의 오차는 양쪽에 고르게 퍼져 있어서, X를 넓히면 맞힌 판과 틀린 판이 같이 동전으로 간다. X=40이면 단순 반응에서 판의 절반이 동전이 되고, 평균 20ms 빠른 사람의 11판 다수 승률이 86% → 77%로 떨어진다. 31이 제안한 40~50ms는 너무 넓다. 0~20ms를 권한다.
2. **방법 4의 RTT_min은 청구하는 쪽이 부풀릴 수 있다.** 핑 답만 D만큼 늦추고 rt를 D만큼 깎으면 통과율은 그대로(70%)인데 승률이 D=100ms에서 94%, D=300ms에서 99%가 된다. 31은 "RTT_min을 부풀리면 자기에게 불리"라고 봤는데, 바른 방향(아래 경계)에서는 **유리**하다. 방장도 같은 구멍이 있다. 참가자에게 자극을 D만큼 늦게 보내고 rt를 D만큼 깎으면 참가자 쪽 확인을 90% 통과하고 94~99% 이긴다.
3. **앞 막힘이 억울함의 거의 전부다.** 원카드 B안과 방법 4에서 정직한 사람이 억울해지는 경우는 순서 보장 채널의 재전송(200~400ms 튐) 때문이다. 앞 막힘을 없애면 원카드 이동통신 억울 비율이 4.0% → 0.0%가 된다. 청구를 순서 없는 채널로 보내자는 docs/43 제안이 가장 값싼 개선이다.

## 1. 무엇을 흉내 냈나

한 판 = 방장 엔진이 판을 바꾸는 순간(참 시각 0)부터 두 사람이 누르기까지.

1. 자극 전달: 방장은 지연 0, 참가자는 편도(방장→참가자) 뒤 메시지를 받는다.
2. 그리기: 받은 뒤 첫 프레임(`requestAnimationFrame` 시각 = `shownAt`)에 그리고, 그리기 줄(1~2 프레임) + 패널 반응 뒤 빛이 나온다. 가끔 한 프레임 더 밀린다.
3. 사람: 빛이 보인 뒤 반응 시간 rt_사람 뒤 손가락이 닿는다.
4. 입력: 기기 고정 터치 지연 + 터치 표본 주기 안 흔들림 뒤 `event.timeStamp`. 처리기가 0~4ms 뒤 보낸다.
5. 잰 값: `rt = floor(timeStamp) − floor(shownAt)`(타이머 1ms, 기기마다 시계 시작점이 다르다).

"진짜 빠른 사람" = **사람 반응 시간**(빛이 보인 순간 → 손가락)이 짧은 사람. 모두가 같은 자극을 같은 순간에 보는 오프라인 판에서 먼저 누르는 사람과 같다. 기기 화면·터치 지연은 사람 실력이 아니므로 오차로 센다.

방법별 판정:

| 방법 | 판정 |
|---|---|
| 1 도착 순서 | 방장 엔진에 청구가 닿은 시각 |
| 2 시계 + 시각 | 핑 10개 중 왕복이 가장 짧은 표본으로 시계 차이를 추정(Cristian)하고, 방장 시계로 바꾼 누른 시각 |
| 3′ 받은 시각 기준 | rt를 `shownAt` 대신 "메시지 받은 시각"부터 잼(프레임을 기다린 시간이 들어감) |
| 3 반응 시간 | `rt = timeStamp − shownAt` |
| 3+5 창 X | rt 차이가 X 미만이면 동전(0.5승) |
| 8 중립 서버 | 서버 도착 시각(각자 서버까지 편도. 자극은 여전히 방장에게서 온다) |
| 4 아래 경계 | 참가자 청구: 여분 = (a − s) − RTT_min − rt. 방장 청구(참가자가 확인): 여분 = (a_G − r_G) − rt_H. 여분 > 여유면 **버리기**(무효) 또는 **깎기**(rt를 여분 − 여유만큼 올림 = docs/43의 `max(rt_보고, 아래 경계)`) |

판마다 기기 둘과 연결을 새로 뽑아 "여러 기기 조합의 평균"을 본다(한 쌍의 기기에 고정된 치우침은 8절 한계 참고).

  - 참가자는 자극 도착이 평소 편도보다 늦은지 통계로 볼 수 있지만, 늦추는 값이 흔들림 정도면 가려지지 않는다.

## 7. 점검한 작은 경우

결과가 직관과 다를 때 스크립트 버그를 먼저 의심하려고, 실행할 때마다 아래를 확인한다(`--check`). 모두 통과.

- 지연 0·흔들림 0·같은 기기·프레임 없음·타이머 연속: 방법 1·2·3·3′·8이 1ms 차이도 100% 맞히고, 실력이 같으면 정확히 반반.
- 같은 조건에서 방법 4의 정직한 여분이 정확히 0, 여유 0에서 1ms 깎은 청구가 늘 걸림.
- 고정 지연(편도 21~39ms, 흔들림 0): 방법 3은 100%, 방법 1은 RTT(42~78ms)보다 작은 차이(30ms)를 늘 뒤집고 큰 차이(100ms)는 늘 맞힘, 방법 2는 편도만큼 손해(20ms 늘 짐, 40ms 늘 이김).
- 비대칭 a, 흔들림 0: Cristian 시계 오차가 정확히 a/2(31 방법 2의 식).
- 창 X=40, 기본 모형, 실력이 같은 참가자 둘: 50% ± 3% 안.

만들다가 잡은 버그: 타이머 단위 0에서 기기 시계 시작점(최대 10⁶ms)을 더했다 빼며 생긴 반올림 차이로 "같은 반응 시간"이 같지 않게 나왔다. 단위 0이면 시작점을 더하지 않게 고쳤다.

## 8. 한계

- **모든 망·기기·사람 값이 가정이다.** 숫자 자체보다 방법 사이의 크기 차이와 민감도의 방향을 본다.
- 판마다 기기 쌍을 새로 뽑아 평균을 냈다. 실제로는 **한 쌍의 폰이 판 내내 같다.** 이 모형에서 두 기기의 고정 지연 차이는 표준편차 약 18ms라, 특정 쌍에서는 한 사람이 매 판 그만큼 앞선다. "평균 85%"가 "어떤 쌍에서는 늘 한쪽으로 기운다"를 가린다. 그래서 기기별 지연 보정(실측한 기기 지연을 rt에서 빼기)을 할지가 실측 뒤 갈림길이 된다.
- 흔들림은 메시지마다 독립인 지수 분포로 두었다. 실제 이동통신은 몰려서 나빠지고(연달아 늦음), 앞 막힘은 뒤 메시지 여럿을 함께 늦춘다.
- 시계 흐름(분당 수 ms), 숨긴 탭, 기기가 바쁠 때의 프레임 빠짐은 넣지 않았다.
- 참가자끼리의 확인(그물 연결로 서로의 청구를 재는 것)은 넣지 않았다. 방장↔참가자 확인만 흉내 냈다. 방장이 참가자 청구의 도착 시각을 거짓으로 말하는 경우도 넣지 않았다(다른 참가자가 직접 잰 값으로만 맞춰 볼 수 있다).
- 4-2의 막는 길(`getStats` RTT 기준)은 흉내 내지 않았다.
- 할리갈리에서 자극이 연달아 덮이는 경우(`stimulusId`), SET에서 겹치지 않는 세트를 둘 다 인정하는 규칙은 넣지 않았다. 한 자극에 두 사람이 겨루는 경우만 봤다.
- 세 사람 이상은 보지 않았다. 둘씩 겨루는 곡선에서 대략 짐작할 수 있다(가장 빠른 사람을 고르는 판에서 기기 오차의 몫은 사람 수가 늘수록 조금 커진다).
- 자동 누르기 프로그램은 범위 밖이다(31·42와 같다).
