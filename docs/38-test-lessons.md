# 38. 시험을 빠르고 결정적으로 만들며 얻은 것 (2026-10-29~30)

사용자 요구: "테스트는 빨라야 해", "전체 테스트가 최대한 빠르고, 효율적이고, flaky하지 않기를". 이틀 동안 단위 시험과 화면 시험을 손본 결과와 교훈이다. 지킬 규칙은 CLAUDE.md "작업 규칙"과 docs/21 10절에도 있다.

|---|---|---|---|
| 단위 시험 전체(이 기계) | 194초(부하로 멈춘 시험 포함) | 약 16초, 2400개 | 약 11~12초, 2404개 |
| 단위 시험, 전체 두 벌 동시(부하) | — | — | 회차당 20~22초 |

## 1. flaky 시험은 대개 진짜 버그였다

가끔 실패하는 시험을 쫓아가 보니 대부분 공통 온라인 방의 실제 경합이었다. 모두 친구와 대전할 때 생길 수 있다.

| 증상 | 원인 | 고친 곳 |
|---|---|---|
| 새로고침한 참가자가 "방장이 시드를 공개하지 않았다" | 내 패를 다 알기 전 판이 끝나 검증 재료가 없음 | `guest-room.ts` |
| "방장이 더미 카드를 엔진과 다르게 열었다" | 다시 받은 카드 열기 요청을 처리하기 전에 기록 검증 | `hwatu-table.ts` |
| "기록 속 내 행동이 내가 보낸 것과 다르다" | 거절된 행동이 저장 목록에 남음, 남의 차례 화면을 내 행동 결과로 착각 | `guest-room.ts`, `host-room.ts`(`mine`) |
| 참가자가 끝없이 기다림 | 다시 세우는 중인 방장이 받은 행동을 소리 없이 버림 | `host-room.ts` |
| 끊긴 사람 투표가 열리지 않음 | 입장 확인(비동기) 중 나간 연결을 자리에 앉힘 | `host-room.ts` |
| 방장 새로고침 뒤 판 끝 검증이 오지 않음 | 방장 서명 확인 전에 온 메시지를 "방장 아님"으로 버림 | `guest-room.ts` |

→ 시간 상한을 늘렸다면 이 버그들은 남았다. flaky는 단서다.

## 2. "느린 것"과 "멈춘 것"을 먼저 가린다

겉보기는 둘 다 시간 초과다. 단계마다 시각을 남기면 갈린다. 느리면 시험의 일을 줄이고, 멈추면 경합을 찾는다(처방이 정반대).

## 3. 부하 아래에서만 드러난다

- 따로 240번 통과한 시험이 전체 시험과 함께 돌자 멈췄다. 고친 뒤에는 **전체 시험 두 벌을 동시에** 돌리며 반복한다.
- 원인을 찾으면 **부하 없이도 반드시 재현하는 시험**(`MemoryNetwork`·`ManualClock`으로 순서를 강제)을 먼저 만들고 고친다.

## 4. 시험은 역할만큼만 일한다

| 하던 것 | 바꾼 것 | 그래도 보장하는 것 |
|---|---|---|
| 섞기 증명 53장 | 4장(두 군) | 증명 정합·변조 잡기는 덱 크기와 무관 |
| 마이티 변형 한 판 끝까지(세 크기) | 첫 트릭까지 | 인원별 장면은 모두 첫 트릭 전 |
| 무작위 시드 15개 | 4개 | 180판을 수마다 확인 |
| 단위 시험 안 세기 비교 | bench로 | 세기는 따로 잰다 |
| 판 끝 화면을 보려고 한 판 끝까지 | 기권 등 가장 짧은 길 | 같은 판 끝 화면 |
| 여러 탭 멘탈 포커 두 판 | 한 판 | 판 잇기는 방 단위 시험이 본다 |

"무엇을 보장하려는가"를 먼저 적으면 어디서 멈춰도 되는지 보인다. 확인 범위(판 끝·게임 끝 검증, 부정 감지)는 줄이지 않는다.

## 5. 운을 없애면 시간도 일정해진다

마이티 방장 새로고침 시험이 0.9~185초로 들쭉날쭉했다(모두 공약 포기 → 다시 나누기). 방장이 늘 높게 공약하게 하자(`hostBidsTop`) 1.3초로 일정해졌다. 운에 따라 다시 시도하기보다 운이 들어갈 자리를 없앤다. 멘탈 포커는 각 기기의 난수로 패가 정해져 방장 시드로 고정할 수 없다는 점도 알아 둔다.

## 6. 기다림은 시간이 아니라 신호로

- 화면이 준비를 알린다: `data-hydrated`(저장값 읽기 끝), `data-moving`, `data-dealing`. 준비 전에 누르면 누름이 사라지거나 늦게 읽힌 저장값이 설정을 덮었다.
- `expect.poll` 기본 간격은 1초까지 늘어난다. 컴퓨터 차례마다 늦게 알아채 나이롱뽕 온라인 57초 → 간격 50ms 고정 후 10초.
- 연출·컴퓨터 대기·제한 시간은 시험에서 줄이거나 옮길 수 있게 둔다: 움직임 줄이기(화면 시험 기본), 시험 속도(`useTestSpeed`, 제품의 `paced`), `Clock`.

## 7. 줄이기 전에 잰다

효과는 몇 군데에 몰렸다(마이티 변형 748초가 전체의 30%). 시험별 시간 표부터 만든다. 작은 것도 쌓인다: 화면이 필요 없는 시험은 jsdom 대신 node 환경.

## 8. 공통 코드는 고치는 효과도, 깨지는 범위도 넓다

공통 온라인 방을 고치면 다섯 게임이 함께 고쳐진다. 대신 공통 코드를 바꾸면 전체 화면 시험을 돌린 뒤 올린다.

## 9. 올리는 것을 그대로 확인한다

여러 작업이 한 작업 공간에서 돌면 push 전 검사가 남의 고치던 파일까지 돈다. 그럴 때는 올릴 커밋만 깨끗한 worktree에 꺼내 확인한다.

## 10. 상한은 설정 하나에, 평소 최대의 20~30배로

- 시험마다 붙인 큰 상한(60~600초)이 설정을 덮고 있었다. 지우고 패키지 설정 하나로 둔다: 컴퓨터·엔진·별 따기 30초, 멘탈 포커 60초, 웹 60초(가장 긴 시험 혼자 3.5초), 화면 시험 90초(가장 긴 보통 시험 14초), 여러 탭 멘탈 포커 3분(실제 12~28초).
- 배수는 잰 값으로 정한다. 다른 작업과 함께 돌 때 오목 고수 시험이 1.1초 → 11초, 화투 섞기가 2.6초 → 20초 넘게, 곧 **부하 아래 10배**까지 느려졌다. 처음 10초·20초로 낮췄다가 그 부하에서 걸려 다시 올렸다.
- 기본값 5초를 쓰던 패키지도 설정에 둔다(0.5초 시험이 10배면 5초).
- 시험 안의 기다리기 함수(`until`) 상한은 시험 상한보다 짧게 둔다(웹 50초 < 60초). 그래야 시간 초과 대신 "무엇을 기다리다 멈췄는지"가 남는다.

## 11. 기계가 잠들면 모든 시험이 함께 늘어난다

부하 확인 중 한 회차가 965초 걸리며 8개가 실패했다. 서로 다른 패키지의 파일 7개가 **똑같이 944~952초**씩 늘어났는데, `pmset -g log`를 보니 맥이 03:13:48에 대기 모드로 946초 잠들었다. 시험 코드 문제가 아니다.
- 실패한 시험들이 같은 길이만큼 늘어났으면 기계 멈춤(잠들기·디스크 등)을 먼저 의심한다.
- 오래 도는 반복 확인은 `caffeinate -i`로 감싼다.

## 12. 2차 정리에서 한 것

- **jsdom 대신 node**: 웹 단위 시험 74파일 가운데 화면·브라우저 저장소를 확인하지 않는 70파일에 `// @vitest-environment node`. 남긴 것은 저장소를 직접 확인하는 `stats/recorder`·`stats/analytics`·`stardraw/wallet`·`stardraw/confirm`. node에서 "통과"해도 제품 코드가 저장소에 써야 결과가 맞는 시험(`analytics`)은 실패로 드러났다. 모두 통과했다고 다 옮기지 말고, 저장소를 쓰는 시험은 하나씩 본다.
- **고정 대기**: 결과 상자가 "머무는지" 보려고 1.5초 기다리던 화면 시험은 `page.clock.install()` + `fastForward`로 실제로 기다리지 않는다. 방장 끊김 뒤 20ms 대기 세 곳은 0ms로(메모리 네트워크가 끊김을 마이크로태스크로 알려 다음 차례 한 번이면 닿는다). 조사용으로 남은 2초 대기·스크린샷은 뺐다.
- **확인 간격**: 기록 저장을 기다리는 `expect.poll`·`toPass`에 `intervals: [50]`.
- **크기별 역할**: 게임마다의 배우기·수 배우기 화면 시험은 데스크톱만. 공통 배우기 화면 배치는 마이티 배우기, 공통 문제 화면은 장기 외통 문제가 세 크기로 본다. 기록·복기 화면은 세로 휴대폰에서 상황판을 다르게 펼쳐 크기마다 배치가 달라, 하트·마이티 한 판 시험 안에서 세 크기로 남겼다.
- **파일 나누기**: 혼자 3.3~3.9초이던 하트·나이롱뽕 방 시험을 공통 준비 파일을 떼고 두 파일씩으로.

일부러 두지 않은 것: 바둑 컴퓨터 시험(혼자 약 2초)은 출시하는 고수(6,000번 둬 보기)의 단수 판단을 보는 장면 시험이 대부분이라 그대로 둔다. 민화투·나이롱뽕 한 판 화면 시험의 새로고침 부분(1초 남짓)은 세 크기에 남겼다(시간은 판 끝까지 두며 배치를 보는 데 든다). `net/transport.ts`의 인증서 지문 기다리기(100ms × 30)는 제품 코드의 실제 시간 대기지만 실제 WebRTC 연결을 기다리는 것이라 Clock 대상이 아니다.

## 13. 가끔 멈추는 시험은 부하보다 드문 판을 먼저 의심한다

고스톱 3명 한 판 방 시험이 push 전 검사에서 50초(`until` 상한) 만에 "판 끝 검증"을 기다리다 실패했다. 부하 탓 같았지만, 멈춘 때마다 시작하자마자 게임이 끝나 있었다(첫 판 총통, 약 1%). 방장이 화투 판을 시작할 때 첫 화면은 직접 보내고 판 끝 기록은 그 뒤 화면 구독에서만 보내, 뒤따르는 화면이 없는 이 판은 기록을 영영 보내지 않았다(제품 버그). 부하 없이도 200번에 2번 났다.
- 멈춘 순간의 상태(진행 시간, 누가 무엇을 보냈는지)를 찍어 보면 공통점이 바로 보인다. 이번에는 `playMs: 0`과 방장 `audited: false`.
- 운에 달린 드문 판은 난수를 고정해 결정적으로 시험한다. 멘탈 포커는 모든 난수가 `crypto.getRandomValues`를 거치므로 바이트를 모두 같은 값으로 채우면 기기들이 부르는 차례와 상관없이 패가 하나로 정해진다(`gostop/fair-room.test.ts` 총통 시험, 값 143).

## 14. 3차 정리(2026-11-01): 별 따기가 늘린 시간

사용자: "그 테스트들이 너무 오래 걸리지는 않지? 테스트들은 모두 빠른 시간에 검증되어야 해." 하루 사이 별 따기 시험이 늘어 단위 시험 24초(조용할 때, 부하 아래 47초), CI 7~8분이 됐다.

| | 전 | 뒤 |
|---|---|---|
| 단위 시험 전체(2,964~2,966개) | 24초(부하 4.5), 파일 시간 합 155초 | 16~17초(부하 6~13), 합 103~111초 |
| CI | 약 7분 15초(화면 시험 조각 5.7·6.3분) | 약 5분 30초~6분(조각 프로젝트 차례 바꾸기 전) |
| 화면 시험 시간 합(CI) | 1,067초 | 879초 |

- **jsdom 기본값을 node로**: 2차 정리 뒤 들어온 별 따기 시험 19개가 지시 없이 jsdom으로 돌아 환경 준비가 15%를 썼다. 기본을 node로 바꾸고 저장소·화면이 필요한 7파일만 `jsdom` 지시. 새 시험이 저절로 가벼운 환경을 쓴다.
- **서버 닫기 3초**: HTTP 서버 시험이 부하 아래에서 가끔 정확히 3초씩 걸렸다. `server.close()`가 받는 쪽이 붙잡은 연결이 끊길 때까지 기다린 것. `stopServer`(closeAllConnections)로.
- **운에 달린 확인(흔들린 시험)**: 두 벌 동시 부하 시험에서 `engine.test.ts` "다른 열쇠나 지난 문제 값으로 푼 답은 받지 않는다"가 한 번 실패했다. 목표값이 1/64라 열쇠 A의 답이 B에도 우연히 맞을 수 있었다(약 3%). 한쪽에만 맞는 답을 골라 쓴다. 엉터리 답 1,000개(0.1%)는 목표값 0(어떤 답도 안 맞음)으로. 고친 뒤 두 벌 동시 18회 실패 없음.
- **같은 준비를 시험마다 되풀이**: 자격 시험 13개가 각자 12회차를 진행했다. 한 번 만든 데이터 폴더를 복사해 서버를 다시 띄운다(2.2초 → 1.3초).
- **연출을 실제 시간으로 기다리던 화면 시험**: 영수증 넘김(33초 → 5초), 소속 반송(30초 → 10초), 추첨 보기·건너뛰기(각 66초 → 10초) 등. CSS·Web Animations는 CDP `Animation.setPlaybackRate`로 20배, 타이머는 `page.clock.fastForward`로 조건까지 조금씩(`e2e/test.ts`의 `speedUpAnimations`·`fastForwardUntil`). `runFor`는 사이의 rAF 프레임을 모두 그려(하늘·추첨 캔버스) 오히려 느렸다. 연출이 끝난 뒤의 자리를 보는 시험(영수증 넘김)은 출력 중에 시계를 멈추고 출력 연출이 끝났는지를 조건으로 기다린다. 마감 시각에 걸린 시험은 마감을 넘긴 뒤부터만 감는다(「마감 직전 응모」는 실제 연출이 마감 안에 드는지 보는 시험이라 그대로).
- **스크린샷**: 사람이 보는 전체 페이지 스크린샷이 화면 시험 시간의 큰 몫이었다(화면 둘러보기 11.4초 → 1.4초). CI에서는 `path`를 준 스크린샷을 찍지 않는다(`E2E_SCREENSHOTS=1`이면 찍음).
- **조각 기울기**: Playwright는 프로젝트 차례로 늘어놓은 시험을 앞에서부터 같은 개수로 자른다. 휴대폰 화면은 시험 안에서 건너뛰는 것이 많아 데스크톱을 맨 앞에 두면 조각 1이 데스크톱 전부(585초 대 294초)를 맡았다. 데스크톱을 가운데로(어림 480 대 400).
- **CI 로그에 시험별 시간**: 리포터를 `list`+`github`로. 느린 화면 시험은 `gh run view --log --job=<id>`에서 `(12.3s)` 꼴로 뽑는다.

일부러 두지 않은 것: 혼자 2초 남짓인 멘탈 포커 방 시험들(10-30부터, 실제 섞기·열쇠 증명 계산)과 바둑 컴퓨터 시험(위 12절). 「등록증 끌기」 화면 시험(12~15초)은 끄는 동안의 회전을 보는 시험이라 손대지 않았다.

## 15. 멘탈 포커 시험을 구조대로 나누기(2026-11-04)

사용자 방향: 멘탈 포커(섞기·열쇠 증명)를 진짜 암호로 계산하는 시험이 많고 느리다. 구조가 「공통 핵심 + 게임별 약속(`kit.cardTable`)」이니 시험도 그렇게 나눈다.

- 새로고침한 참가자는 되살린 판의 판마다 검증을 일부러 건너뛴다(guest-room `verifyRound`). 새로고침 시험에서 `roundVerified`를 기다리면 멈춘다.

## 16. 바뀐 것만 시험한다(2026-11-04)

사용자 방향: 무엇이 바뀌든 모든 게임의 단위·화면 시험을 다 돌려서, 큐브 시험 실패가 하트 고침 배포를 막았고 CI가 7분에서 16분으로 늘었다. 모노레포답게 바뀐 것과 그것에 기대는 것만 시험한다(저장소는 나누지 않는다).

> 2026-11-10 17절에서 바뀐 것: main push는 화면 시험을 돌리지 않는다, 조각 수(최대 6, 시간 기준), src 파일은 화면에서 닿는지로 고른다, 단위 시험 계기(패키지 package.json·appcast 등 뺌). 아래는 처음 정한 모습이다.

- **기준 커밋**: PR은 base와의 merge-base. main push는 직전 커밋이 아니라 **마지막으로 CI가 성공한 main 커밋**(`ci.yml` plan 작업이 `gh api`로 찾고, 지금 커밋의 조상인지 본다). 앞 실행이 취소·실패했으면 그 변경도 다음 실행이 함께 시험한다. 못 찾으면 전부.
- **단위 시험**: `vitest run --changed <기준>`. vite 모듈 그래프로 바뀐 파일을 (패키지를 건너서도) 불러오는 시험만 돈다. `${기준}...HEAD`와 커밋 안 한 파일을 본다. projects 설정과 함께 동작한다(큐브 풀이기 한 파일 → cube-ai·cube-reduction·cube-scramble·cube-solver·web 30파일). 그래프에 안 잡히는 입력은 루트 `vitest.config.ts`의 `forceRerunTriggers`로 전부: package.json·vitest 설정(기본값), tsconfig·lockfile·작업 공간·biome·`.node-version`·`ci.yml`, 그리고 시험이 파일로 읽는 `apps/web/public/stats/`·`apps/web/scripts/build-hashes.mjs`. **시험이 import 대신 `readFileSync`나 다른 프로그램 실행으로 읽는 파일을 새로 두면 여기에 더한다.** 영향받는 시험이 없으면 0으로 끝난다.
- **화면 시험**: `scripts/affected-e2e.mjs`가 고른다. 게임은 `games/registry.ts`의 id, 그 게임의 `src/<id>/`·`src/app/<id>/`·`public/<id>/`·`e2e/<id>*.spec.ts`. 게임 사이 기댐(은하가 별 따기를 불러 쓴다 등)과 패키지를 쓰는 게임은 실행 때마다 웹 import·package.json에서 계산한다. 여러 게임이 쓰는 웹 코드(net·components·game·review·stats 등)·시험 도구·playwright 설정·lockfile·CI·짝 모르는 파일은 **전부**. 문서·단위 시험 파일·별 따기 서버·CLI만이면 **없음**(작업을 건너뛰고 CI 성공). 일부일 때는 홈·없는 주소·뒤로 가기와 어느 게임에도 안 든 spec을 늘 함께, spec이 12개 이상이면 2조각.
- 마이티 엔진(`packages/engine`)은 거의 모든 패키지가 기대고, fair-play는 net이 쓰므로 그 둘(과 그것을 거치는 hwatu·hearts-engine)은 늘 전부다. 큐브·바둑·윷 같은 게임 패키지는 그 게임만(`game/bot-registry.ts`는 게임마다 갈래로 컴퓨터를 부르는 곳이라 공통으로 세지 않는다).
- **안전망**: 매일 한 번(schedule, 한국 시각 03:17)과 손으로 돌리기는 전부. 배포로 이어지지 않는다(Image는 push CI만 본다). 느린 시험 기록은 시험마다 "그 시험을 잰" 실행만 센다(`slow-tests.mjs`의 `ran`).
- playwright `--only-changed`는 spec이 불러오는 파일만 따라가고 빌드된 앱 코드는 못 따라가서 쓰지 않았다. Turborepo도 견줘 봤다: 화면 시험은 apps/web 한 패키지 안에서 갈라야 해서 스크립트가 어차피 필요하고, 패키지가 소스를 그대로 내보내 build가 없고 typecheck 전체가 4초라 캐시로 줄일 것이 거의 없으며, 원격 캐시는 바깥 서비스나 서버가 든다.

## 17. CI를 10분 안쪽으로(2026-11-10)

사용자: 「우리 CI가 상당히 오래 걸리는 것 같지 않아?」, 「30분은 너무 길어」. 목표는 PR 하나가 사이트에 올라가기까지 10분 안쪽이다. 조사해 보니 화면 시험 실행이 85~90%였고, 조각은 둘뿐인 데다 Playwright `--shard`가 시험 개수로 잘라 기울어 있었다(조각 1이 1,293초, 조각 2가 993초). 시험 안에서 `test.skip`으로 건너뛰는 시험 484개도 개수에 들어갔다.

- **main 보호와 화면 시험 자리**(사용자 결정): main 보호 규칙으로 PR 필수·CI 통과 필수(검사 이름 `ci-ok`)·최신 main 반영 필수(strict)를 켠다. 그래서 화면 시험은 PR에서만 돈다(「화면 시험은 main에서 할 필요가 있을까? 작업된 PR에서만 체크하면 되지 않아?」). main push는 빠른 검사(lint·typecheck·바뀐 단위 시험·nginx 설정)만 하고, 성공하면 Image가 예전처럼 배포한다. 매일 한 번(schedule)과 손으로 돌리기는 그대로 전부다.
- **`ci-ok`**: plan·check·화면 조각들을 `needs`로 받아 늘 도는 요약 작업. 하나라도 실패·취소면 실패, 모두 성공이거나 건너뜀이면 성공. 조각 수가 바뀌거나 화면 시험을 건너뛰어도 보호 규칙은 이 이름 하나만 본다.
- **조각 2 → 6, 시간 기준**: `scripts/affected-e2e.mjs`가 고른 spec을 지난 시험 시간(`scripts/e2e-times.json`, spec마다 모든 화면 크기의 합)으로 긴 것부터 가장 가벼운 조각에 담고, 조각마다 spec 목록을 matrix로 넘긴다. 전부면 6조각(조각마다 약 375초, 작업자 둘이라 약 3분), 일부면 시간 합을 240초마다 한 조각으로 올림해 1~6조각. 시간 자료가 없으면 spec 12개마다 한 조각. 한 실행의 동시 작업은 많아야 8개(plan·check·화면 6·ci-ok)라 무료 공개 저장소 한도 20개 안이다. 시간 기준 파일은 매일 전부 실행의 `test-times-e2e-*` artifact로 `node scripts/affected-e2e.mjs --write-times scripts/e2e-times.json <e2e.json…>`를 돌려 새로 쓴다(없는 spec은 평균으로 친다).
- **한 크기만 보는 시험은 태그로**: `test.skip(info.project.name …)`을 태그 `@only-desktop`·`@only-phone-portrait`·`@no-phone-landscape`와 프로젝트 `grepInvert`로 옮겼다(`e2e/projects.ts`). 파일 전체가 한 크기만 보면 `FILE_ONLY`(testIgnore)에 적는다. 건너뛸 시험이 목록에서 빠져 브라우저 문맥을 띄웠다 닫는 일과 조각 개수에서 사라진다(1,068개 → 608개). 옮긴 뒤 `--list`를 그날 main CI 결과와 견줘 CI에서 돈 시험이 모두 남고 새로 생긴 것이 없음을 확인했다. 환경 변수(`E2E_SCREENSHOTS`·`FAIR_MULTI` 등)로 켜는 시험만 `test.skip`으로 남는다. **새 시험이 한 크기만 볼 때는 `test.skip` 대신 태그를 단다.**
- **Chrome**: 러너 이미지의 Chrome(156.0.8078.79)이 보안 공지의 최소 판(`e2e/browser.ts` `MIN_CHROME`) 이상이면 `playwright install --with-deps chrome`을 건너뛴다. 낮거나 없을 때만 설치하고, 실제로 뜨는 판은 global-setup이 그대로 확인한다. 글꼴은 `--with-deps`가 넣던 묶음(fonts-wqy-zenhei 등)과 똑같이 둔다. 러너에서 글꼴 없이 판정·글자 폭이 같은지 미리 견줄 수 없어서, 받은 .deb을 캐시해 dpkg로 바로 푼다(그 설치에서 가장 오래 걸리던 apt 목록 받기·내려받기를 아낀다).
- **Next 빌드 캐시**: `.next/cache`를 main 실행(매일·손으로)의 첫 조각이 저장하고 PR이 받아 쓴다. 이 맥에서 빌드 14초 → 7초. 주마다 새로 시작해 한없이 커지지 않게 한다.
- **화면 시험 고르기 정밀화**(11-11에 아래 「주소 → spec」으로 더 좁힘): src 파일은 화면(`src/app`의 page·layout·icon 등)에서 import로 닿는지 본다. 어디서도, 어느 spec에서도 닿지 않으면 없음(시험 전용 도우미 `tutorial/term-order*.ts` 등). 공통 폴더 파일은 닿는 주소의 게임만 돌리고(net은 온라인 방이 있는 게임만), 첫 화면·복기·프로필 같은 공용 주소가 닿으면 예전처럼 전부(globals.css, components 대부분, 용어집). `apps/web/scripts`는 빌드가 돌리는 것(build-hashes 등)만 전부, 개발 때 손으로 돌리는 생성 도구(render-cube-posters 등)는 없음. 그날 「전부」가 된 실행 여덟 가운데 셋이 큐브만으로 줄었다.
- **단위 시험 계기**: `forceRerunTriggers`에서 패키지마다의 package.json을 뺐다(루트만). 의존을 바꾸면 lockfile이 함께 바뀌어 전부 돌고, 나머지는 typecheck 전체와 매일 실행이 본다. 시험이 파일로 읽던 appcast·sw.js·큐브 page 목록은 `import.meta.glob(?raw, eager)`으로 읽어 모듈 그래프로 따라간다. `Object.keys(import.meta.glob(…))`처럼 키만 바로 쓰거나 eager 없이 쓰면 vite가 import를 빼서 그래프에 안 잡힌다. **시험이 파일로 읽는 입력을 새로 두면 되도록 이렇게 읽고, 안 되면 계기에 더한다.**
- 어림(그날 원자료 기준): 화면 시험 조각 하나가 준비 약 1분 + 시험 약 3분, plan 약 10초가 앞에 붙어 PR CI가 5분 안팎. main push는 1~4분(단위 시험이 전부로 넓어지지 않으면 1분 남짓) 뒤 Image가 배포한다.
- **주소 → 그 주소를 여는 spec(2026-11-11)**: 웹 src 파일은 게임 묶음이 아니라 주소 단위로 고른다.
  - 파일 → 닿는 주소: `src/app`의 주소(page, 아이콘·공유 그림 같은 따로 선 주소, 없는 주소 화면)마다 그 page와 위 폴더들의 layout·template에서 import를 따라간다. 모든 화면 주소가 닿는 파일(루트 layout, globals.css, 루트 layout이 불러 쓰는 StoreHydration·기록 저장 등)만 전부다. 이 판단은 그래프로 계산하고 손으로 적은 목록이 없다.
  - spec → 여는 주소: spec과 그것이 불러 쓰는 시험 도구에 적힌 주소 문자열(`goto("/review")`, `` `/stardraw/mine#…` ``, `toHaveAttribute("href", "/cube")`)과 `\/`로 시작하는 정규식(`toHaveURL(/\/cube\/daily$/)`)으로 모은다. 공용 주소 화면이 링크로 넘겨 주는 공용 주소(내 기록 → 복기)와, 게임 주소의 page 파일 자체에 적힌 같은 게임 주소(옛 주소 넘기기 `<CubeRedirect to=…>`)도 따라간다. 첫 화면은 모든 주소로 이어지는 목록이라 따라가지 않는다.
  - 게임 폴더 파일도 주소로 좁힌다(큐브 타이머만 쓰는 파일은 cube-timer만). 다만 공용 주소(복기·내 기록)에 닿으면 그 주소를 여는 spec 가운데 그 게임 것만 고른다(복기는 게임마다 갈래가 있다). 루트 layout으로만 닿는 게임 파일(저장소 불러오기)은 예전처럼 그 게임 묶음이다. 그 게임의 어느 주소도 적지 않은 spec(초대 링크로만 여는 등)은 그 게임 화면이 바뀌면 늘 함께 돈다. 패키지·`public/<게임>/`은 예전처럼 게임 묶음.
  - 화면에 닿지만 그 주소를 여는 spec이 없으면(없는 주소 화면, 사이트 아이콘) 기본 묶음만 돈다(빌드는 된다).
  - **놓칠 위험과 막은 것**: ① import 그래프가 못 읽는 꼴(변수·템플릿 문자열 동적 import, `require`, `import.meta.glob`, CSS `@import url()`, 문자열이 아닌 `new Worker`·`new URL(…, import.meta.url)`)이나 찾지 못한 import가 화면에서 닿는 파일에 있으면 웹 src 변경을 전부로 돌린다(`graphGap`, 지금은 없음). 줄을 바꾼 `import(\n"…")`, JSON·CSS import, `new Worker(new URL("…", import.meta.url))`는 따라간다. ② 눌러서 다른 주소로 넘어가는 spec은 그 주소를 적어 둔다(`toHaveURL`, `href` 확인 등). 적지 않고 넘어간 화면은 놓치고, 그것은 매일 전부 실행이 잡는다. **새 화면 시험이 링크·단추로 다른 주소에 가서 그 화면을 보면 `toHaveURL`로 그 주소를 확인한다.** ③ Tailwind는 모든 소스의 클래스 이름으로 CSS 하나를 만든다. 클래스를 더하는 것은 다른 화면을 바꾸지 않아 따로 보지 않는다.
