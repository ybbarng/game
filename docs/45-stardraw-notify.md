# 42. 하늘의 별 따기: 관측 시작을 진동·알림으로 알리기 (2026-11-03, 설계만)

사용자(2026-11-03): 「브라우저가 진동이나 푸시 알림을 줄 수 있는지? 관측 시작되면 이런 걸로 알려 주면 좋겠다.」

이 문서는 설계 제안이다. 아직 만들지 않았고 사용자가 정할 갈림길이 남아 있다(7절). 정하면 결정을 docs/36에 절로 남기고 같은 커밋에서 docs/41(연출·말투)을 고친다(루트 `CLAUDE.md` 규칙).

## 0. 한 줄 요약

- **진동**은 안드로이드 Chrome·삼성 인터넷에서, 별 따기 화면을 보고 있고 한 번이라도 누른 뒤에만 울린다. 아이폰은 어떤 브라우저든 울리지 않는다. 서버·개인정보와 상관없어 작게 바로 넣을 수 있다.
- **화면을 안 볼 때 알리는 길은 웹 푸시뿐이다.** 서비스 워커 + VAPID 열쇠 + 서버가 구독(브라우저 회사 전달 서버의 주소)을 보관하고 회차마다 보낸다. 아이폰은 iOS 16.4부터, 홈 화면에 추가한 웹 앱에서만 된다. 카카오톡 같은 앱 안 브라우저에서는 안드로이드·아이폰 모두 안 된다.
- **추천**: 진동을 먼저 작게 넣는다. 푸시는 클로즈 베타 반응을 보고 정하되, 한다면 **우주인과 묶지 않은 익명 구독, 「이번 관측만」 한 번 쓰고 지우는 구독**으로 한다. 우주국이 보관하는 것이 회차 하나 동안의 주소 하나로 줄고, 열쇠를 잃어도 피해가 그 회차뿐이다.

## 1. 지금 알리는 방법과 빈 곳

| 방법 | 언제 | 누구에게 | 코드 |
|---|---|---|---|
| 방송 토스트 | 예측 마감부터 그 회차 실시간 관측 연출이 끝날 때까지. 화면이 뜨고 1.5초 뒤 위에서 내려온다. 관측 안내(관측 15초 전) 전에는 「n회 예측을 마감했습니다. 관측은 HH:MM입니다.」, 그 뒤 「곧(지금) n회 관측이 시작됩니다. 우주인 여러분은 관측지로 이동해 주시기 바랍니다.」. 누르면 관측지, 밀면 그 회차 동안 사라짐 | 관측지 밖의 별 따기 화면을 **보고 있는** 사람 | `components/BroadcastToast.tsx`(`broadcastText`, `broadcastRound`, `BROADCAST_DELAY_MS`), docs/36 11-35·11-52 |
| 홈 → 관측지 이동 | 관측 안내 15초 전부터 연출이 끝날 때까지와 관측 1분 동안(`onAirRound`) | 그때 홈으로 **처음 들어온** 사람(이미 홈에 있던 사람은 끌고 가지 않음) | `StardrawApp.tsx`, docs/36 11-37 |
| 관측 안내 | 관측지 머리 아래 `OnAirGuide`, 상태 줄 「n회 예측을 마감했습니다. 관측까지 m:ss」 등 | 관측지에 있는 사람 | `OnAirGuide.tsx`, `RoomView.tsx` |
| 홈 회차 카드·시간표 | 늘 | 홈을 연 사람 | 홈, `/stardraw/timetable` |
| 짧은 진동(이미 있음) | 등록증 발급(20ms), 신분증 확인(20ms), 예측서 제출(20ms), 풍등 길게 누르기(15ms), 입상 직인이 찍힐 때(1등 `[40,60,80]`, 그 밖 40ms, 움직임 줄이기면 없음) | 안드로이드에서 그 동작을 한 사람 | `AstronautSetup.tsx`·`IdPresent.tsx`·`EnterSubmit.tsx`·`RoomView.tsx`·`DrawView.tsx`의 `navigator.vibrate?.(…)` |

**빈 곳**: 모두 **별 따기 화면을 보고 있는 사람**에게만 닿는다. 예측서를 내고 다른 앱으로 간 사람, 화면을 끈 사람, 다른 탭을 보는 사람은 관측 시각을 스스로 기억해야 한다. 관측은 1분(관측 시각 + 6초에 시작, 약 50초)이라 몇 분 늦으면 실시간 장면을 놓친다(늦게 와도 다시 보기는 된다, 관측지는 관측 + 7분까지).

한 회차의 시각(정식 1시간 기준, docs/41 2절): 마감 :55 → 관측 시각(drand) :00 → 연출 시작 :00:06(`LIVE_LEAD_MS`) → 관측지 닫힘 :07. 시험(20분)은 :15·:35·:55 마감, :20·:40·:00 관측.

## 2. 진동

### 2-1. 지원 범위

| 브라우저 | `navigator.vibrate` | 근거 |
|---|---|---|
| 안드로이드 Chrome·삼성 인터넷·Edge·Opera | 된다. Chrome 60부터 사용자 몸짓이 있어야 하고, 없으면 `false`. 교차 출처 iframe에서는 안 됨(55부터) | MDN browser-compat-data `api/Navigator.json` vibrate |
| 안드로이드 시스템 웹뷰(카카오톡·네이버 등 안드로이드 앱 안 브라우저) | 함수는 있다(4.4.3부터, 60부터 몸짓 필요). 실제로 울리는지는 앱이 진동 권한을 받았는지에 달려 확인 못 함 | 같은 자료 |
| 안드로이드 Firefox | 79부터 **`true`를 돌려주지만 울리지 않는다**(남용 걱정으로 꺼 둠) | 같은 자료(bug 1653318) |
| 데스크톱 Firefox | 129에서 뺐다 | 같은 자료, W3C Vibration 편집자 초안 |
| Safari(맥·아이폰), 아이폰의 모든 브라우저와 웹뷰 | 없다(`navigator.vibrate`가 undefined). WebKit은 이 표준에 반대 입장을 냈다 | 같은 자료, W3C Vibration 편집자 초안 상태 절 |
| 데스크톱 Chrome | 함수는 있지만 진동 장치가 없어 아무 일 없음 | MDN `Navigator.vibrate()` |

**울리는 조건**(W3C Vibration API 처리 순서):
- 문서가 **보이는 상태(`visible`)**여야 한다. 숨은 탭·꺼진 화면이면 `false`. 보이다가 숨으면 울리던 진동도 멈춘다.
- 페이지에 **sticky activation**이 있어야 한다(그 페이지에서 한 번이라도 누르거나 키를 친 적). 공지 링크로 들어와 아무것도 안 누르고 기다리는 사람에게는 울리지 않는다. 별 따기는 페이지 사이를 같은 문서 안에서 옮기므로(앱 안 이동) 한 번 누르면 그 탭이 닫힐 때까지 유지된다.
- 무늬는 10칸, 한 칸 10초까지로 잘린다.
- 무음·방해 금지 모드면 울리지 않는 기기가 있다(MDN).

그래서 **진동은 「화면을 보는 사람에게 소리 없이 한 번 더」**일 뿐, 1절의 빈 곳(화면을 안 볼 때)은 채우지 못한다. 토스트를 못 보고 지나칠 사람(휴대폰을 책상에 두고 화면만 켜 둔 사람, 다른 곳을 보는 사람)에게 손으로 알리는 정도다.

### 2-2. 어디서 언제 울리나

새로 울릴 곳은 둘만 둔다(동시에 여러 번 울리면 알림이 아니라 소음이다, docs/41 6절 「동시에 움직이지 않기」).

| 때 | 어디서 | 무늬(제안) | 까닭 |
|---|---|---|---|
| 방송 토스트가 내려올 때(마감 직후, 화면이 뜬 뒤 1.5초) | 관측지 밖의 별 따기 화면 | `[30, 80, 30]`(톡톡) | 토스트가 이미 「하던 일을 끊지 않고 알린다」 자리다. 회차마다 한 번(토스트를 밀어 닫은 회차는 다시 울리지 않음) |
| 관측 10초 카운트다운이 시작될 때 | 관측지(`data-room-countdown`이 뜨는 순간) | `[60]` | 「이제 시작한다」는 순간. 관측 안내(15초 전)에 울리면 토스트 문구가 「곧」으로 바뀌는 때와 겹친다 |

- 관측 안내 15초 전에 토스트 문구가 「곧 …」으로 바뀔 때는 울리지 않는다(마감 때 한 번 울렸다).
- 결과(입상 직인)의 진동은 지금처럼 둔다.
- 「관측 시작 몇 초 전」을 더 앞당기지 않는 까닭: 화면을 보고 있는 사람만 받으므로 앞당겨도 얻는 것이 없다. 화면 밖에 있는 사람을 앞서 부르는 일은 푸시(3절)의 몫이다.

### 2-3. 끄기와 움직임 줄이기

- 지금 입상 직인 진동만 「움직임 줄이기」면 울리지 않고, 나머지 네 곳은 늘 울린다. 어긋나 있다.
- 진동은 움직임이 아니라 촉감이라 움직임 줄이기(`prefers-reduced-motion`)와 뜻이 다르다. 움직임 줄이기를 켠 사람 중에는 화면 연출이 어지러운 사람이 많고, 촉감 알림은 오히려 반길 수 있다.
- **제안**: 별 따기 진동을 한 곳(`haptics.ts`의 `buzz(kind)`)으로 모으고, 「더 보기」 목록에 「진동」 켜고 끄기 한 줄을 둔다(기본 켬, 이 기기 `localStorage` `stardraw-vibrate`). 움직임 줄이기와는 묶지 않는다. 입상 직인 진동도 이 설정을 따른다. `navigator.vibrate`가 없는 기기(아이폰 등)에서는 줄 자체를 보이지 않는다(쓸 수 없는 설정을 늘어놓지 않는다). 갈림길 N2.
- 다른 안: 움직임 줄이기에 묶기(설정 칸이 생기지 않는다. 대신 움직임 줄이기를 켠 사람은 알림 진동도 못 받는다).

### 2-4. 시험

- 단위(node 환경): `haptics.test.ts` — 설정이 꺼져 있으면 부르지 않음, `navigator.vibrate`가 없거나 던지면 조용히 넘어감, 무늬 값. 토스트 진동은 「회차마다 한 번」을 상태로 확인한다(토스트 표시 판단 `broadcastRound`와 같은 입력, 시계 주입).
- 화면 시험: `page.addInitScript`로 `navigator.vibrate`를 부른 기록을 남기는 함수로 바꾸고, 마감·카운트다운까지 `fastForwardUntil`로 감아 기록을 조건으로 확인한다(실제 시간으로 기다리지 않는다, `CLAUDE.md`). 기존 `BroadcastToast`·관측지 spec 하나씩에 덧붙인다.
- 실기기: 안드로이드 Chrome에서 (1) 링크로 들어와 아무것도 안 누르면 안 울림, (2) 한 번 누른 뒤 마감 때 울림, (3) 화면을 끄면 안 울림, (4) 「진동」을 끄면 안 울림. 아이폰은 「진동」 줄이 안 보이는지만.

## 3. 웹 푸시

### 3-1. 브라우저·OS별 지원

| 환경 | 푸시 | 조건 | 근거 |
|---|---|---|---|
| 안드로이드 Chrome·삼성 인터넷·Edge | 된다 | 설치 없이 브라우저에서. 허락을 받아야 함(안드로이드 13부터 OS 알림 권한도 브라우저가 묻는다) | MDN BCD `api/PushManager.json`(chrome 42) |
| 안드로이드 Firefox | 된다 | 79부터 사용자 몸짓 안에서만 구독 | 같은 자료 |
| 데스크톱 Chrome·Edge·Firefox | 된다 | 브라우저가 떠 있어야 받는다(꺼져 있으면 다음에 켤 때, TTL 안이면) | 같은 자료 |
| 맥 Safari | 16부터(macOS Ventura 이상) | 몸짓 안에서 구독 | 같은 자료, WebKit 「Meet Web Push」 |
| 아이폰·아이패드 | **iOS·iPadOS 16.4부터, 홈 화면에 추가한 웹 앱에서만** | 매니페스트 `display`가 `standalone`이나 `fullscreen`이어야 웹 앱으로 저장된다(아니면 책갈피). 허락 요청은 누름에 바로 답해서. Safari 탭 안에서는 `Notification`이 아예 없다. 16.4부터 Chrome·Edge 등 다른 브라우저도 공유 메뉴에서 「홈 화면에 추가」를 낼 수 있다 | WebKit 「Web Push for Web Apps on iOS and iPadOS」, 「WebKit Features in Safari 16.4」, MDN BCD(safari_ios 16.4 「home screen」 주석) |
| 안드로이드 시스템 웹뷰(카카오톡·네이버·인스타그램·라인 등 안드로이드 앱 안 브라우저) | **안 된다** | | MDN BCD(webview_android false, crbug 40443309) |
| 아이폰 앱 안 브라우저(WKWebView: 카카오톡·인스타그램 등) | **안 된다** | | MDN BCD(webview_ios false) |
| Chrome 맞춤 탭(슬랙·텔레그램 안드로이드) | 확인 못 함 | 맞춤 탭은 Chrome 본체의 저장소·권한을 쓰므로 될 것으로 보이지만 확인한 자료가 없다 | |

- 이 사이트에 처음 오는 길은 회사 메신저·카카오톡 링크다(docs/36 11-52·11-54). 웹뷰는 처음 열 때 바깥 브라우저로 넘기므로(카카오톡·라인 자동, 나머지는 띠) 푸시는 **넘어간 뒤의 Safari·Chrome에서** 다룬다.
- **아이폰은 사용자가 공유 → 홈 화면에 추가를 손으로 해야 한다.** 페이지가 대신 띄워 줄 수 없다(설치 안내 API가 없다, 확인: WebKit 글은 공유 메뉴만 말한다). 아이폰 사용자 대부분에게 푸시는 「한 단계 더 거쳐야 하는 기능」이다.
- **홈 화면 웹 앱은 Safari와 저장소를 나눠 쓴다.** 홈 화면에서 연 별 따기에는 Safari에서 만든 이 기기 지갑(`localStorage`)이 없어 신분증 제시로 다시 찾아와야 한다. 패스키는 iCloud 키체인에 있어 그대로 쓸 수 있다. 공식 문서는 찾지 못했고 WebKit 버그 181849(2018)·190269의 보고와 널리 알려진 동작이 근거다. 지금 iOS에서 실기기로 확인할 것(확인 못 함).
- 지금 사이트 매니페스트(`app/manifest.ts`)는 게임 센터용(`start_url: "/"`, 이름 「게임」)이다. 별 따기에서 홈 화면에 추가하면 게임 목록이 열리는 앱이 생긴다. 푸시를 하려면 별 따기 전용 매니페스트(`id`·`start_url`·`scope`를 `/stardraw`로, 이름 「하늘의 별 따기」)를 별 따기 layout에 두는 것이 낫다. Safari 16.4가 매니페스트 `id`를 지원해 게임 센터 앱과 따로 설치된다(WebKit 16.4 글). 갈림길 N6.

### 3-2. 구성

```
[브라우저]                      [별 따기 서버]                     [브라우저 회사 전달 서버]
 sw.js(push·notificationclick)   push.ts(VAPID 서명·보내기)          FCM(fcm.googleapis.com)
 접수증의 「관측 알림」 단추 ──구독 주소──▶ push.db(회차, 주소)   ──POST(본문 없음)──▶  APNs(*.push.apple.com)
                                 회차 시계(마감 → 관측 1분 전)       Mozilla(updates.push.services.mozilla.com)
 ◀────────────── 알림 ───────────────────────────────────────────── WNS(Edge, *.notify.windows.com, 확인 못 함)
```

**서비스 워커**
- 사이트에는 이미 `public/sw.js`(범위 `/`, 오프라인용)가 하나 있다. 범위 하나에 등록은 하나라 푸시 처리도 이 파일에 더한다(별 따기만 쓰는 별도 워커를 `/stardraw/` 범위로 두는 길도 있지만, 범위가 더 좁은 워커가 그 아래 페이지를 맡아 오프라인 처리와 둘이 된다).
- `push` 이벤트: 받으면 **반드시 알림을 띄운다.** Chrome·Edge는 `userVisibleOnly: true`가 아니면 구독을 거절하고, Safari는 알림을 띄우지 않으면 구독을 거둬 간다(WebKit 「Meet Web Push」: "violations will result in a push subscription being revoked"). 회차 번호는 같은 출처의 `/stardraw-api/api/state`를 읽어 채우고, 못 읽으면 회차 없는 문구로 띄운다(3-8).
- `notificationclick`: 열려 있는 별 따기 창이 있으면 그 창을 앞으로 가져와 `/stardraw/now`로, 없으면 새 창. `tag: "stardraw-observe"`로 같은 알림이 쌓이지 않게.
- `sw.js`는 `out/`에 들어가 화면 코드 해시(`build-hashes.json`)에 포함된다(docs/36 11-8). 따로 할 일은 없다.
- 웹 푸시를 끄거나 바꿀 때 지난 판 워커가 남는 문제는 지금 오프라인 워커와 같다(새 판이 `skipWaiting`).

**본문 없는 푸시(제안)**
- 웹 푸시는 본문을 넣으려면 RFC 8291(aes128gcm, 구독마다 받은 `p256dh`·`auth`로 암호화)을 구현하거나 `web-push` 같은 바깥 패키지를 들여야 한다. 별 따기 서버는 지금 바깥 의존이 없다(`package.json`이 워크스페이스 패키지 둘뿐).
- 보낼 말이 「관측이 곧 시작된다」 하나라 본문이 필요 없다. **본문 없이 보내면** 서버는 VAPID 서명(ES256 JWT, `node:crypto`로 충분)만 하면 되고, 구독의 `p256dh`·`auth`를 보관할 까닭도 사라진다. RFC 8030은 본문 없는 메시지를 허용한다.
- 확인 못 함: Apple 전달 서버가 본문 없는 푸시를 받아 서비스 워커를 깨우는지. 만들 때 실기기로 먼저 확인하고, 안 되면 RFC 8291을 `node:crypto`로 구현한다(RFC 8291 부록의 시험 값으로 단위 시험).
- iOS 18.4의 Declarative Web Push(서비스 워커 없이 JSON 본문만으로 알림)는 본문이 필요하고 우리에게는 서비스 워커가 이미 있어 쓰지 않는다(WebKit 「Meet Declarative Web Push」).

**VAPID 열쇠 보관**
- P-256 열쇠 한 쌍. 비밀 열쇠는 서버 데이터 볼륨의 파일(예: `/data/vapid.key`, 권한 600). **장부 서명 열쇠(관인)와 다른 열쇠**로 둔다. 둘을 같이 쓰면 푸시 서명이 관인 서명처럼 쓰일 여지가 생긴다.
- 공개 열쇠는 화면이 구독할 때 `applicationServerKey`로 넘긴다. `/api/push/key`로 받거나 빌드 변수로 넣는다. 서버가 열쇠를 처음 뜰 때 만들게 하면 빌드와 맞추기 번거로우니 `/api/state`에 공개 열쇠 한 줄을 더하는 쪽을 추천.
- 잃으면: 그 열쇠로 만든 구독 전부가 쓸모없어진다(전달 서버가 다른 열쇠의 서명을 거절한다). 구독을 「이번 관측만」으로 두면 피해는 그 회차 하나라 **백업하지 않아도 된다.** 새로 만들면 된다. 운영 시작 검사(11-49)처럼 「장부와 맞는지」 확인할 것도 없다.
- JWT의 `sub`(연락처)는 이메일 대신 `https://game.byb.kr/stardraw/privacy`로 둔다(RFC 8292는 mailto나 https URL을 허용).

**서버: 구독 받기·보관·보내기**
- `POST /api/push/subscribe {round, endpoint, gate}`: 그 회차 관측 알림 하나를 맡긴다. `gate`는 예측·등록 앞단에 쓰는 작업 증명 답(docs/36 11-31)을 그대로 쓴다(3-5). 같은 주소·회차면 덮어쓴다.
- `POST /api/push/unsubscribe {endpoint}`: 주소를 아는 쪽이 곧 주인이다(주소는 브라우저만 안다).
- 보관: **장부 DB와 다른 SQLite 파일** `push.db`의 표 하나 `push_subs(endpoint TEXT, round INTEGER, PRIMARY KEY(endpoint, round))`. 매시 DB 백업·집 서버 끌어오기·앵커 사본 어디에도 들어가지 않게 파일을 나눈다(잃어도 되는 값이고, 백업에 남으면 보관 기간이 백업 기간만큼 길어진다).
- **보내는 시각**: 그 회차 관측 시각(drand) − 60초(갈림길 N5). 서버 회차 시계(`engine.ts`의 마감·봉인 흐름)에 묶는다. 마감 직후는 봉인·관측 전 사본 올리기(11-51, drand 1분 전까지)로 바쁘므로 그 일이 끝난 뒤에 보낸다. 무효로 정해진 회차도 관측 연출은 있으므로 보낸다(확인: 무효 회차의 관측지 화면이 어떤지 만들 때 본다).
- **보내기**: 동시에 10~20개씩, 요청마다 `TTL`(관측 연출이 끝날 때까지 남은 초, 약 110초. 늦게 도착한 알림은 쓸모없으니 전달 서버가 버리게), `Urgency: high`(안드로이드 절전 중에도 바로 깨우게), `Topic: observe`(밀린 알림이 쌓이지 않게 바꿔치기). 본문 없음.
- **응답 처리**: 201이면 끝. 404·410이면 지운다(만료·구독 취소, web.dev 「The Web Push Protocol」). 429면 `Retry-After`를 따라 TTL 안에서 한 번만 다시. 5xx·연결 실패는 한 번 다시, 그래도 안 되면 버린다(다음 회차에 다시 맡길 일이다).
- **정리**: 보낸 뒤 그 회차 줄은 성공·실패와 상관없이 모두 지운다. 서버가 멈춰 보내지 못한 회차도 다음 시작 때 지난 회차 줄을 지운다. 그래서 `push.db`에는 **늘 앞으로 올 회차의 줄만** 있다.
- **화면의 구독 정리**: 알림을 받은 뒤(또는 회차가 지나면) 화면·서비스 워커가 `subscription.unsubscribe()`를 불러 다음에 새 주소를 받게 한다. 같은 주소를 회차마다 다시 쓰면 서버가 「같은 브라우저의 여러 회차」를 이을 수 있다(3-4). 다시 구독하면 주소가 실제로 바뀌는지는 전달 서버마다 확인 못 함(FCM은 바뀌는 것으로 알려졌지만 1차 자료 없음).
- **배포와 겹칠 때**: guard.sh는 마감 앞뒤에 배포를 막는다(11-45). 관측 1분 전은 그 창 안이라 배포 때문에 보내지 못하는 일은 없을 것으로 보인다. guard.sh의 `AFTER_CLOSE` 값과 맞춰 만들 때 확인.
- **회차 일정과 묶기**: 보내는 시각은 장부 일정표(`roundTimes`, `DRAND_DELAY`)에서 계산한다. 회차 길이를 바꾸는 예고(11-32)가 있어도 일정표가 정한 회차 번호의 시각을 따르므로 따로 고칠 것이 없다. 구독은 회차 번호에 묶여 있고, 그 회차 시각이 바뀌면 바뀐 시각에 보낸다.
- **숫자**: 회차마다 로그 한 줄 `[stardraw] 관측 알림 {"round":…,"subs":…,"sent":…,"gone":…,"failed":…,"ms":…}`(docs/33 11-3 꼴, 개인 값 없음). `/api/state` `pressure`처럼 최근 값을 두면 gatus가 「알림 실패 많음」을 볼 수 있다.

### 3-3. 무엇을 보관하나

| 값 | 무엇인가 | 보관 | 개인정보 성격 |
|---|---|---|---|
| 구독 주소(`endpoint`) | 브라우저 회사 전달 서버의 주소. 끝에 그 브라우저(정확히는 그 서비스 워커 등록)를 가리키는 긴 토큰이 붙는다 | 그 회차 관측 1분 전까지(길어야 한 회차 길이 + 몇 분) | **기기 식별자에 가깝다.** 이름은 없지만 한 브라우저를 가리키고, 같은 주소가 여러 번 오면 같은 기기로 이어진다. 보수적으로 개인정보로 다룬다(법적 판단은 확인 못 함) |
| 회차 번호 | 알림을 받을 회차 | 같음 | 혼자로는 아무것도 아님 |
| `p256dh`·`auth` | 본문 암호화 열쇠 | **보관하지 않는다**(본문 없는 푸시) | — |
| 우주인 공개 열쇠, 예측서 id | — | **받지 않는다** | — |
| IP | 지나친 요청 막기 | 저장하지 않는다(지금 정책 그대로) | — |

**우주인 열쇠와 묶을까?**
- 묶으면 할 수 있는 것: 「내 예측서가 입상했습니다」 같은 개인 알림, 여러 기기에 같은 우주인 알림.
- 묶으면 잃는 것: 우주국이 「이 공개 열쇠(가명) = 이 기기」를 알게 된다. 지금 원칙 「우주국은 우주인이 누구인지 모른다」(docs/41 1절)와 「새 우주인으로 다시 등록하면 앞의 예측과 이어지지 않는다」(설명 페이지 「우주국이 보관하는 것」)가 무너진다. 같은 기기의 옛 열쇠와 새 열쇠가 구독 주소로 이어지기 때문이다. 운영자도 믿을 필요 없게 만든 설계(docs/36 1절)에서 운영자가 새로 쥐는 연결 고리다.
- **묶지 않으면** 서버는 「어느 브라우저가 몇 회 관측 알림을 원한다」만 안다. 개인 알림은 못 하지만 사용자가 부탁한 「관측 시작」 알림에는 충분하다.
- 입상 알림을 원하게 되면 묶지 않고도 할 수 있다: 서비스 워커가 알림을 받을 때 공개 결과를 읽고, 이 기기에 둔 내 예측서 목록(서비스 워커가 읽을 수 있게 IndexedDB에 사본)과 기기 안에서 견주어 「입상」 문구를 고른다. 서버는 여전히 아무것도 모른다(4절 ④).

**함께 드러나는 것**: 알림은 브라우저 회사(Google·Apple·Mozilla·Microsoft)의 전달 서버를 거친다. 본문이 없으니 내용은 모르지만, 그 기기에 game.byb.kr에서 알림이 언제 왔는지는 안다. 이 사실을 개인정보처리방침에 적는다.

### 3-4. 우주국이 일부러 하지 않는 것

- 같은 주소로 여러 회차를 맡지 않는다(「이번 관측만」. 매 회차 구독을 두면 같은 기기의 여러 회차 접속이 한 줄로 이어진다).
- 구독 요청과 예측서 접수를 같은 요청에 싣지 않는다. 시각으로 이어 볼 여지는 남는다(같은 IP에서 몇 초 차이로 접수와 구독이 오면 운영자가 「이 예측서를 낸 브라우저」를 짐작할 수 있다). 이 짐작은 지금도 IP로 할 수 있는 것과 같은 크기이고, 구독 주소는 회차마다 바뀌고 회차가 끝나면 지워지므로 그 이상 쌓이지 않는다. 그래도 개인정보처리방침에는 숨기지 않고 적는다.
- 통계(umami)에 구독 주소·회차를 보내지 않는다. 셀 것은 3-7의 종류뿐.

### 3-5. 남용 막기와 정상 사용자 비용

| 공격 | 무엇이 생기나 | 막는 것 | 정상 사용자 비용 |
|---|---|---|---|
| 아무 주소나 구독 주소로 보내기(서버를 남의 서버에 요청 보내는 도구로) | 서버가 회차마다 그 주소로 POST를 보낸다(SSRF) | **주소 허용 목록**: `https`이고 호스트가 알려진 전달 서버(`fcm.googleapis.com`, `*.push.apple.com`, `updates.push.services.mozilla.com`, Edge의 WNS)일 때만 받는다. 포트 443만. 목록은 만들 때 각 브라우저로 실제 주소를 찍어 확인 | 없음 |
| 가짜 주소 대량 등록(허용된 호스트에 지어낸 토큰) | 회차마다 보낼 일이 늘어 서버 시간·연결을 쓴다 | 첫 발송에서 404·410이 와 지워지고, 회차가 지나면 어차피 모두 지운다(한 번 등록 = 한 번 요청). 구독 요청에 작업 증명(예측 앞단과 같은 Argon2, 기기에서 1초 안쪽, 미리 뒤에서 푼다)을 붙여 대량 등록에 계산 비용을 물린다 | 단추를 누른 뒤 1초 안쪽(접수증 화면에 있는 동안 미리 풀면 0초) |
| 진짜 브라우저 구독을 자동으로 대량 생성 | 같음, 404가 안 와 끝까지 보낸다 | 작업 증명 + 한 회차 안 전체 구독 수 **안전 퓨즈**(예: 2만. 넘으면 새 구독을 「우주국이 지금은 알림을 더 맡지 못합니다.」로 거절하고 gatus 알림). 사람마다의 상한이 아니라 서버를 지키는 바닥이라, 실제 이용자 수의 몇십 배로 넉넉히 | 공격이 없으면 없음. 공격 중에는 새 구독이 막힐 수 있다(이미 맡긴 알림은 그대로 간다) |
| 남의 구독 지우기 | 그 사람이 알림을 못 받는다 | 지우려면 그 주소를 알아야 하는데 주소는 그 브라우저와 우리 서버만 안다 | 없음 |
| 우리 서버인 척 남의 기기에 알림 보내기 | — | 전달 서버가 우리 VAPID 공개 열쇠로 서명을 확인한다. 비밀 열쇠가 서버 밖으로 나가지 않으면 불가능 | 없음 |

- IP 상한은 1차 수단으로 쓰지 않는다(회사 NAT 뒤 수십 명이 한 IP다. 사용자 전역 원칙, 메모리 「IP 제한 먼저 꺼내지 않기」). 운영에서 IP 앞부분 상한을 꺼 둔 지금 상태(docs/36 11-43)와도 맞는다.
- 「계산은 뒤에서, 사람 수 상한 피함」(메모리 「별 따기 보안 기준」): 작업 증명은 화면이 미리 풀고, 퓨즈는 공격 때만 닿는 높이에 둔다.

### 3-6. 운영 부담(서버 자원)

game.byb.kr의 목적은 「서버 자원 최소, 구성원끼리 신뢰, 안정적 플레이를 실험」(메모리 「game.byb.kr의 목적」)이다.

- 발송 비용: 구독 하나에 회차마다 HTTPS 요청 하나(본문 없음, 응답 작음). 100명이면 100번, 동시 20개씩이면 1초 안팎. 전달 서버 연결은 호스트마다 몇 개를 다시 쓴다(Node 내장 `fetch`). 메모리는 몇 MB 안쪽으로 본다(측정은 만들 때 `bench`로).
- 저장: 줄마다 수백 바이트, 회차가 끝나면 0으로 돌아간다. 백업·복구에서 빼므로 운영 절차(deploy/stardraw/README.md)에 더할 것이 거의 없다.
- 새로 생기는 바깥 의존: 브라우저 회사 전달 서버 넷. 거기가 느리거나 막혀도 별 따기 본 기능(예측·관측·장부)에는 영향이 없게, 발송은 회차 흐름과 따로 돌고 시간 상한(TTL) 안에서 포기한다.
- 지킬 것이 늘어난다: VAPID 열쇠 파일, `push.db`, 주소 허용 목록, 퓨즈 알림. 「이번 관측만」 설계 덕에 셋은 잃어도 되는 것이다.
- 정식 1시간 회차 24번·하루, 시험 20분 회차 72번·하루. 구독은 원하는 사람이 원하는 회차만 맡으므로 회차 수가 곧 발송 수는 아니다.

### 3-7. 사용자 경험

**언제 허락을 묻나**
- **첫 화면에서 바로 묻지 않는다.** 이유 없이 묻는 허락은 거의 거절된다(web.dev 「Permissions best practices」: 데스크톱 허락 요청의 77%가 사용자 의도 신호 없이 뜨고 그중 12%만 허락). 한 번 거절하면 브라우저 설정에서 손으로 풀어야 한다.
- **물을 자리: 예측서를 낸 뒤 접수증 아래.** 이 사람은 방금 이 회차에 예측했고 관측 시각을 기다린다. 접수증 아래에 우주국 문서 결의 한 줄과 단추: 「관측 알림」 칸 — 「n회 관측 1분 전에 이 기기로 알려 드립니다.」 단추 「알림 받기」. 누르면 그때 브라우저 허락 창을 연다(우리 칸이 곧 web.dev가 말하는 미리 묻기다. 따로 확인 창을 한 번 더 두지 않는다, 군더더기 규칙).
- 한 번 허락한 기기는 다음 회차 접수증에서 단추만 누르면 된다(허락 창 없음). 「매번 자동으로」는 두지 않는다(갈림길 N4).
- 관측지 밖에서 회차를 기다리는 사람(예측하지 않고 구경만 하려는 사람)을 위해 홈 회차 카드나 관측 시간표에도 같은 단추를 둘지는 갈림길 N4에 묶는다.
- 거절했거나 이 브라우저가 못 하면 칸을 걷는다(되지 않는 단추를 남기지 않는다).

**아이폰**
- Safari 탭에서는 `PushManager`·`Notification`이 없다. 이때 칸은 「아이폰에서는 홈 화면에 추가한 뒤 알림을 받을 수 있습니다.」와 「추가하는 방법」(공유 단추 → 홈 화면에 추가, 그림 두 장) 하나만. 처음 한 번만 보이고 접을 수 있다.
- 홈 화면 웹 앱으로 열면 지갑이 비어 있을 수 있어(3-1) 신분증 제시부터 해야 한다. 알림만 받는 데는 등록증이 필요 없다(익명 구독)는 점이 도움이 된다: 알림을 눌러 관측지로 가면 언덕 아래에서 숨어서 관측할 수 있다.
- iOS 16.4 아래, 앱 안 브라우저: 칸을 보이지 않는다.

**끄기**
- 「이번 관측만」이라 끄기 단추가 거의 필요 없다. 맡긴 뒤 칸은 「n회 관측 알림을 맡았습니다.」와 「취소」(`unsubscribe` + 서버 지우기).
- 브라우저 알림 허락 자체를 거두는 것은 브라우저 설정이다. 개인정보처리방침에 적는다.

**알림을 누르면**: `/stardraw/now`(지금 회차 화면이 관측 중이면 관측지). 이미 열린 별 따기 창이 있으면 그 창을 앞으로.

**통계(docs/33 11-2에 더할 것)**: `sd-notify` `{kind: "offered"|"granted"|"denied"|"unsupported"|"ios-install"|"cancelled"}`. 회차·주소는 보내지 않는다. 알림이 실제로 닿았는지는 서버 로그 숫자(3-2)로 본다.

### 3-8. 문구(우주국 방송 말투)

docs/41 5절: 우주국 방송은 「~습니다」, 이야기 말만(서버·푸시·구독 같은 기술 말 없이). 알림 창 제목은 기관 이름.

| 자리 | 문구 |
|---|---|
| 알림 제목 | 카노푸스 우주국 |
| 알림 본문(회차를 읽었을 때) | 곧 n회 관측이 시작됩니다. 우주인 여러분은 관측지로 이동해 주시기 바랍니다. |
| 알림 본문(회차를 못 읽었을 때) | 곧 관측이 시작됩니다. 우주인 여러분은 관측지로 이동해 주시기 바랍니다. |
| 접수증 아래 칸 | 관측 알림 · n회 관측 1분 전에 이 기기로 알려 드립니다. [알림 받기] |
| 맡은 뒤 | n회 관측 알림을 맡았습니다. [취소] |
| 아이폰 Safari | 아이폰에서는 홈 화면에 추가한 뒤 알림을 받을 수 있습니다. [추가하는 방법] |
| 퓨즈에 걸렸을 때 | 우주국이 지금은 관측 알림을 더 맡지 못합니다. |
| 허락을 거절했을 때 | (칸을 걷는다. 문구 없음) |

- 알림 본문은 방송 토스트의 「곧」 문구와 같은 말이다. 사람이 알림을 보고 사이트에 오면 같은 방송이 이어진다.
- 낱말: 「알림」은 낱말표에 없는 새 낱말이다. 「관측 알림」을 이야기 쪽 낱말로 쓰고(우주국이 우주인에게 보내는 소식), 「푸시」「구독」은 개인정보처리방침·설명 페이지 기술 쪽에만. 정하면 docs/41 3절에 더한다.

### 3-9. 개인정보처리방침·설명 페이지에 더할 말

`/stardraw/privacy`에 절 하나:

> **관측 알림**
> - 받는 것: 알림을 받겠다고 한 회차 번호와, 브라우저가 알려 주는 알림 전달 주소(Google·Apple·Mozilla·Microsoft의 전달 서버 주소). 우주인 공개 열쇠·등록번호·예측서와는 잇지 않습니다.
> - 쓰는 곳: 그 회차 관측 1분 전에 알림 하나를 보내는 데만 씁니다. 알림에는 내용을 싣지 않고, 기기가 받은 뒤 공개된 회차 정보를 읽어 문구를 채웁니다.
> - 남기는 것: 알림을 보내면 바로 지웁니다. 보내지 못해도 그 회차가 지나면 지웁니다. 백업에 넣지 않습니다.
> - 함께 알게 되는 곳: 알림은 브라우저 회사의 전달 서버를 거칩니다. 그 회사는 이 사이트에서 알림이 왔다는 것과 그 시각을 압니다.
> - 끄기: 맡은 알림은 접수증의 「취소」로, 알림 허락 자체는 브라우저 설정에서 거둡니다.

설명 페이지 「우주국이 보관하는 것」에 한 줄: 「관측 알림을 맡기면 알림 전달 주소를 그 회차 동안만 보관하고, 보낸 뒤 지웁니다.」

적용일 문구(「2026년 10월 31일부터 적용합니다(…를 고침)」)도 함께 고친다.

### ② 꼭 지킬 규칙을 어떻게 보장하나

| 규칙 | 장치 |
|---|---|
| 구독을 우주인과 잇지 않는다 | 구독 API가 열쇠·예측서 id를 받지 않는다(받을 칸이 없다). 서버 시험이 요청 모양을 확인 |
| 회차가 지나면 남지 않는다 | 보낸 뒤 그 회차 줄 지우기 + 시작 때 지난 회차 줄 지우기. 단위 시험(ManualClock으로 회차를 넘김) |
| 백업에 들어가지 않는다 | 장부 DB와 다른 파일. 백업 스크립트가 장부 DB만 고른다는 것을 deploy README에 적고 확인 |
| 남의 서버로 요청을 보내지 않는다 | 주소 허용 목록(호스트·https·443). 단위 시험에 막히는 주소 목록(사설 IP, 다른 포트, 비슷한 호스트 이름) |
| 받은 푸시마다 알림을 띄운다 | 서비스 워커 `push` 처리가 실패해도 기본 문구로 `showNotification`(try/finally). 서비스 워커 단위 시험 |
| 알림이 본 기능을 막지 않는다 | 발송은 회차 흐름과 따로 돌고(봉인·사본 올리기 뒤), 시간 상한 안에서 포기. 전달 서버를 흉내 낸 시험 서버(`stopServer`)로 느린 응답·429·410 |
| 진동은 화면을 보는 사람에게만, 끌 수 있게 | 브라우저 규칙(visible·sticky activation) + `haptics.ts` 한 곳 |
| flaky 시험 금지 | 보내는 시각·TTL은 주입한 시계로, 화면 시험은 조건으로 기다림 |

### ③ 사람과 AI가 데이터를 어떻게 찾아 쓰나

- 사람(운영자): 회차마다 로그 「관측 알림」 줄, `/api/state`의 최근 발송 숫자, gatus 알림(실패율이 높거나 퓨즈에 걸렸을 때). `push.db`를 들여다볼 일은 없게 한다(들여다볼 것도 회차 하나 분량).
- 사람(이용자): 개인정보처리방침의 「관측 알림」 절, 접수증의 맡은 상태.
- AI(세션): 이 문서와 docs/36에 남길 결정 절, 코드 `push.ts`·`sw.js`의 머리 주석. 로그 숫자는 개인 값이 없어 읽어도 된다. 구독 주소는 로그에 찍지 않는다(찍히면 기기 식별자가 로그 보관 기간만큼 남는다).

### ④ 요구가 바뀌면 어디까지 고치나

| 바뀌는 것 | 고칠 곳 |
|---|---|
| 보내는 시각(1분 전 → 5분 전 등) | 서버 상수 하나, 문구의 「1분 전」, 문서 |
| 「매 회차 알림」도 원한다 | 표에 `until_round` 칸 + 화면 선택지 + 개인정보처리방침 보관 기간. 같은 주소가 여러 회차에 남아 3-4의 「이어짐」이 생긴다는 것을 다시 판단해야 한다 |
| 「예측 마감 10분 전」 알림(아직 예측하지 않은 사람용) | 알림 종류 칸 하나(`kind`) + 문구 + 발송 시각. 같은 구조로 된다 |
| 입상 알림 | 서버는 그대로. 서비스 워커가 공개 결과와 기기 안 예측서 목록(IndexedDB 사본)을 견주어 문구를 고른다. 지갑을 IndexedDB에도 쓰는 일이 생긴다 |
| 본문을 실어야 한다(Apple이 본문 없는 푸시를 안 받는 등) | RFC 8291 암호화 구현 + 구독 키(`p256dh`·`auth`) 보관 칸. 보관 기간은 그대로 회차 하나 |
| 우주인과 묶어야 한다 | 데이터 계약이 바뀐다. 「우주국은 우주인이 누구인지 모른다」 문구, 설명 페이지, 개인정보처리방침, 다시 등록의 효과 설명을 모두 다시 써야 한다. 그래서 하지 않는 쪽을 추천 |
| 정식 회차 길이 변경 | 없음(일정표에서 계산) |
| 푸시를 그만둔다 | 구독 API를 410으로, 화면 칸을 걷고, 서비스 워커에서 `push` 처리를 빼기 전 한동안 「아무 일 없음」 대신 기본 알림을 띄운다(남은 구독이 있으면 Safari가 거둬 가게). `push.db`는 지우면 끝 |
| 다른 게임(마이티 방 초대 등)도 알림을 원한다 | 같은 서비스 워커·같은 전달 구조를 쓸 수 있지만 서버가 다르다(게임 센터는 서버 없는 구조). 그때 따로 설계 |

### ⑤ 다른 대안과 고른 근거

| 대안 | 좋은 점 | 아쉬운 점 |
|---|---|---|
| 진동만 | 서버·개인정보 0, 작다 | 화면을 보는 안드로이드 사용자만. 빈 곳을 못 채운다 |
| 진동 + 익명·한 번 쓰는 푸시(추천) | 화면 밖에 있어도 닿는다. 보관이 회차 하나·주소 하나, 백업 불필요, 열쇠를 잃어도 그 회차만 | 아이폰은 홈 화면 추가를 거쳐야 함, 앱 안 브라우저 안 됨, 서버에 새 모듈·바깥 의존(전달 서버) |
| 우주인과 묶은 푸시 | 입상 같은 개인 알림, 여러 기기 | 우주국이 가명↔기기를 알게 되어 핵심 원칙과 부딪친다. 보관 기간이 길어지고 백업·복구 대상이 된다 |
| 매 회차 익명 푸시 | 한 번 허락하면 계속 | 하루 24~72번 알림은 소음이고, 같은 주소가 오래 남아 기기가 이어진다 |
| 달력에 넣기(.ics, 관측 시각 + 1분 전 알람) | 서버 0, 아이폰 Safari에서도 된다(설치 없이) | 달력이 지저분해지고 회차마다 손으로 넣는다. 안드로이드는 파일 받기 → 달력 앱 열기로 번거롭다. 실제 동작은 확인 못 함 |
| Notification Triggers(기기 안에서 정한 시각에 알림) | 서버 없이 정한 시각에 알림 | Chrome 실험이었고 개발이 끝났다(developer.chrome.com 「Notification Triggers」) |
| 화면을 켜 둔 채로 두게(Screen Wake Lock) + 소리 | 서버 0 | 화면을 계속 켜 두라는 요구는 이 문제(화면을 안 볼 때)를 풀지 않는다 |
| 메신저 봇(회사 메신저·카카오톡 채널)으로 회차 공지 | 이미 모두 쓰는 앱이라 설치 없음 | 연락처·메신저 계정을 다뤄야 하고 회사 메신저 정책이 끼어든다. 별 따기 밖 운영 일 |
| 안 함 | 아무 비용 없음 | 사용자 요청을 채우지 못한다. 관측 시간표·홈 카드로 기억에 맡긴다 |

고른 근거: 사용자가 원한 것은 「관측 시작」 한 가지다. 이 한 가지는 사람마다 다른 내용이 아니어서 우주인과 묶을 까닭이 없고, 회차마다 원하는 사람만 맡기면 보관도 회차 하나로 끝난다. 그 범위에서 서버가 새로 지는 짐(열쇠 파일·작은 표·허용 목록)이 가장 작다.

## 6. 추천

1. **진동을 지금 작게 넣는다(2-5).** 방송 토스트가 내려올 때와 관측 카운트다운 시작 때, 「더 보기」의 「진동」 끄기, 흩어진 진동 호출을 `haptics.ts` 하나로. 서버·장부·개인정보는 그대로.
2. **푸시는 클로즈 베타 반응을 본 뒤 정한다.** 지인들이 「관측을 놓쳤다」고 말하는지, 통계의 관측지 입장 수와 예측서 수 차이가 큰지 본다. 하기로 하면 **익명·이번 관측만·본문 없음·관측 1분 전·접수증에서 묻기**로 만든다. Apple 전달 서버가 본문 없는 푸시를 받는지 실기기로 먼저 확인한다.
3. **우주인과 묶은 푸시는 하지 않는다.** 입상 알림이 필요해지면 서비스 워커가 기기 안에서 견주는 길로 한다.
4. 푸시를 만들게 되면 별 따기 전용 매니페스트를 함께 둔다(아이폰 홈 화면 앱이 별 따기로 열리게).

**확인 못 한 것**(만들 때 실기기·문서로 먼저 본다)
- Apple 전달 서버가 본문 없는 푸시로 서비스 워커를 깨우는지.
- 다시 구독하면 전달 서버마다 주소가 바뀌는지.
- 지금 iOS에서 홈 화면 웹 앱과 Safari가 `localStorage`를 나누는지(공식 문서 없음, 2018 버그 보고).
- Edge(WNS) 전달 서버의 정확한 호스트 이름, Chrome 맞춤 탭에서의 푸시.
- 안드로이드 8 이상에서 알림 `vibrate` 옵션이 실제로 쓰이는지(알림 채널이 정한다는 보고만 있음).
- 안드로이드 웹뷰에서 `navigator.vibrate`가 실제로 울리는지(앱 권한).
- 구독 주소가 국내법상 개인정보인지(보수적으로 개인정보로 다룬다).
- `.ics` 파일이 아이폰 Safari·안드로이드 Chrome에서 어떻게 열리는지.
- Playwright에서 CDP `ServiceWorker.deliverPushMessage`로 푸시를 흉내 내 화면 시험을 할 수 있는지.
