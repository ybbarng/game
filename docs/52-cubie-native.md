# 52. Cubie 윈도우판과 플랫폼별 네이티브 앱

> 2026-11-11 사용자: 「큐비 윈도우 버전도 만들 수 있어?」, 「장기적으로는 성능을 고려한 각 플랫폼 네이티브 앱도 고민해 주면 좋겠어. 지금은 용량을 너무 많이 차지하고, 웹에서 오는 성능 하락도 있을 거라고 생각해.」
>
> 이 문서는 HQ 세션의 설계 초안이다. 정할 것은 맨 아래 「정할 것」에 있다.

## 1. 결론부터

- 지금 Cubie의 짐은 디스크가 아니라 **메모리**다. 앱 파일은 4MB인데, 떠 있는 동안 웹 화면 프로세스까지 합쳐 300MB 안팎을 쓴다.
- 장기적으로는 **큐브 계산 코어를 Rust로 한 번 짜고, 큐브 그리기도 Rust(wgpu) 하나로 두고, 플랫폼마다 얇은 네이티브 껍데기**(맥 AppKit, 윈도우 Win32)를 씌우는 구조를 권한다. 예상 메모리는 30~60MB다.
- 바로 갈아타지 않는다. 먼저 맥에서 작은 시제품으로 메모리·CPU가 실제로 줄어드는지 재고, 사이트와 같은 결과를 내는지(섞기·판정·기록) 시험으로 묶은 뒤 옮긴다.
- (2026-11-11 3단계 맥 시제품, 5-2) 네이티브 화면은 가만히·숨김 때 약 40MB(웹 약 170MB), 돌리는 동안 CPU 3~4%(웹 15~18%)였다. 돌리는 순간 메모리는 맥 그래픽 드라이버 몫이 커서 223MB(웹 265~296MB)로 덜 준다. 4단계로 가기를 권한다.
- (2026-11-11 연구, 5-3) 돌리는 동안의 메모리는 맥 드라이버가 GPU로 그리는 프로세스에 붙이는 고정 몫(약 108MB)이라 웹이든 wgpu든 줄지 않는다. 크게 줄이려면 연출을 시스템 합성기에 맡겨야 한다. 지금 웹 앱에서 미니 큐브만 CSS 3D로 그리면 시안 기준 돌리는 동안 265~296MB → 75MB(실제 미니 추정 약 120MB)라 이것을 먼저 권한다. 전환한다면 wgpu 대신 Core Animation 3D(약 25~30MB, 용량 +0.6MB)다.
- (2026-11-11 실험, 5-4) 실제 미니 화면에 CSS 3D 그리기를 실험 주소 `?render=css`로 넣어 쟀다. 돌리는 동안 260MB → 139MB(거울 숨김 261 → 130), 가만히 243 → 98MB, 최고치 합 약 375 → 282MB. GPU 프로세스에 108MB가 붙지 않는다. 대신 돌리는 동안 CPU가 27.6% → 40.1%로 는다(거울 숨김 21.0 → 25.5%).
- (2026-11-12, 5-5) wgpu 대신 Core Animation 3D로 실제 앱 전체(섞기 연출·거울 판·윤곽·2×2~7×7)를 그려 쟀다. 모든 상태 10~17MB(웹 130~300MB), 최고치 17.6MB(웹 약 400MB), 앱 쪽 CPU 돌리는 동안 0.4~0.6%(웹 12~17%, 대신 WindowServer가 약 +10%p), 설치 용량 zip +0.5MB(wgpu는 +3MB). 사용자가 걸린다고 한 설치 용량·최대 메모리가 모두 풀려 **4단계를 이 그리기로 가기를 권한다.** wgpu 경로는 앱에서 뺐다.
- (2026-11-12 4단계, 5-6) 큐브 창을 완전 네이티브로 옮겼다(기본, 되돌림 `CUBIE_WEB=1`은 2026-11-25 지움, 5-20). 기록·힌트(사람 해법 포함)·공식 연습·F1 표·다시 보기·축하·소리·기록 옮기기까지 네이티브이고, 기록 창·티어표·설정만 사이트 창이다(5-8에서 이것도 옮김). 측정 모드 모든 상태 11~32MB(웹 135~291MB), 돌리는 중 CPU 5%(웹 22%, 대부분 소리), 유니버설 zip 2.83MB(0.1.10 1.7MB).
- (2026-11-12, 5-8) 기록 창·티어표·설정 창도 네이티브로 옮겼다(되돌림 `CUBIE_WEB_WINDOWS=1`은 2026-11-25 지움, 5-20). 세 창을 연 동안 353MB(사이트 창) → 39MB, 기록 창 103 → 32MB. 사용자 배치 편집만 사이트 창으로 남겼다.
- 윈도우판은 두 길이 있다. 웹 화면을 그대로 쓰는 Tauri로 빨리 내거나, 위 네이티브 구조를 윈도우부터 쓰는 것이다.

## 2. 지금 얼마나 쓰나(2026-11-11, 이 맥, Cubie 0.1.9가 떠 있을 때)

| 프로세스 | 하는 일 | 메모리(footprint) |
|---|---|---|
| Cubie | 앱 껍데기(창·메뉴·단축키) | 약 65MB(RSS) |
| WebKit.WebContent | 웹 큐브 화면(React·three.js) | 128~145MB, 최고 218MB |
| WebKit.GPU | 웹 화면 그리기 | 35~157MB(움직일 때 늘어남) |
| WebKit.Networking | 웹 화면 받기 | 약 14MB(RSS) |

- 합치면 가만히 있을 때 250MB 안팎, 움직일 때 300MB를 넘는다. 「가만히 CPU 0~1%」는 지금도 맞다.
- 디스크는 4MB라 문제가 아니다.
- 같은 날 다시 보니 이 맥의 WebContent는 둘이었다(140MB + 43MB, `launchctl print pid/<Cubie>`로 둘 다 Cubie 소속). 둘째는 한 번 띄운 단축키 표(F1)가 남긴 것으로 보인다(아래 2-3, 재기에서 단축키 표 하나가 약 34MB).

### 2-1. 재는 방법(5절 1단계 「재기」)

`apps/cubie/scripts/measure-memory.sh`(쓰는 법은 `apps/cubie/DEVELOPMENT.md` 「메모리 재기」).

- 앱을 측정 모드(`CUBIE_MEASURE=1`)로 띄운다. 앱은 앞으로 나올 수 없고(.prohibited), 창은 화면 밖에 투명하게 떠 있으며, 메뉴 막대·전역 단축키·업데이트를 켜지 않고 웹 저장소는 비영속이다. 사용자 화면·포커스·기록을 건드리지 않아, 쓰던 Cubie를 켜 둔 채 잰다. 화면 밖 창도 보이는 창처럼 그리게 WebKit의 가려짐 감지만 끈다.
- 시나리오: 켠 직후 → 가만히 1분 → 포커스·섞기·키로 돌리기(거울 보임) → 거울 숨김 → 포커스 없음 → 숨김 → 단축키 표 불러오기·버리기. 상태마다 Cubie와 그 앱 소속 WebKit 서비스(WebContent·GPU·Networking)의 `phys_footprint`를 1초 간격 세 번 평균한다. 창은 기본 크기 96pt, 화면 배율 2.
- 측정 모드의 Cubie 칸(약 18MB)은 메뉴 막대·Sparkle·말풍선 창이 없어 실제 앱(약 47MB)보다 작다. 웹 쪽 수치는 실제 앱과 같다.
- 흔들림: 같은 빌드도 돌리는 중 WebContent가 93~140MB로 오간다(자바스크립트 쓰레기 치우기 시점). 그래서 견줄 때는 가만히 둔 상태(켠 직후·숨긴 뒤)를 주로 보고, 숨긴 뒤는 전·후 빌드를 같은 시나리오로 이어 잰 값을 쓴다.

### 2-2. 무게가 어디서 오나(재기로 가른 것, 단위 MB)

| 무엇 | WebContent | GPU | 가른 방법 |
|---|---|---|---|

- 기록·다시 보기 자료는 Chrome 힙 기준 1MB 안쪽이라 무게가 아니다.

### 2-4. CPU(2026-11-11, 사이트 `game.byb.kr/cube/mini` 830954872, 측정 모드, 두 번 잼)

같은 스크립트(`measure-memory.sh`)가 상태 구간의 처음과 끝에 프로세스마다 누적 CPU 시간(`ps -o time`)을 읽어, 늘어난 CPU 시간 ÷ 지난 시간으로 평균을 낸다. 100%는 코어 하나를 다 쓴 것이다. 표본을 뽑지 않아 구간 안의 짧은 반짝임도 빠지지 않는다. 합계는 Cubie + 그 앱 소속 WebContent·GPU·Networking.

| 상태(구간 길이) | 합계 | Cubie | WebContent | GPU | Networking |
|---|---|---|---|---|---|
| 가만히(떠 있을 때 연출 포함, 60초) | 1.1% / 1.1% | 0.2 | 0.6 | 0.2 | 0 |
| 섞고 키로 돌리는 중, 거울 보임(초당 약 8수, 20초) | 19.8% / 17.9% | 3.1~3.4 | 10.3~11.3 | 4.4~5.1 | 0.1 |
| 돌리는 중, 거울 숨김(6초) | 17.6% / 13.2% | 2.9~3.6 | 6.8~9.1 | 3.6~4.8 | 0~0.2 |
| 포커스 있고 손을 멈춤(10초) | 1.0% / 1.3% | 0 | 0.7~0.8 | 0.3~0.5 | 0 |
| 포커스 없음(10초) | 1.4% / 1.8% | 0.1 | 0.8~1.1 | 0.5~0.6 | 0 |
| 숨김(숨긴 뒤 30초부터 60초) | 0.0% / 0.0% | 0 | 0 | 0 | 0 |

- 대부분의 시간(가만히·숨김)에는 CPU가 짐이 아니다. 「가만히 CPU 0~1%」는 이번에도 맞았고, 숨기면 0이다.
- 돌리는 동안 코어 하나의 15~20%를 쓰고, 그 절반 남짓이 WebContent(자바스크립트·three.js 장면 갱신), 4분의 1이 GPU 프로세스(화면 합성)다. 측정 모드의 키 입력은 0.12초 간격이라 사람이 빠르게 돌릴 때(초당 5~10수)와 비슷하다.
- Cubie 칸(키 입력을 웹으로 넘기기) 3%는 측정 모드 명령 처리가 섞인 값이라 실제 앱과 조금 다를 수 있다.
- 네이티브 시제품(5절 3단계)과 견줄 기준: 돌리는 동안 15~20%, 가만히 약 1%, 숨김 0%.

### 2-5. 남은 무게와 네이티브 판단 자료

- 가만히 있을 때 남는 약 170MB(측정 모드)는 WebKit 바닥 약 33(WebContent·GPU·Networking), 자바스크립트 코드 약 45, WebGL 약 35, 떠 있을 때 연출·숨긴 뒤 30~40초 사이에 붙는 약 8(원인은 아직 모름, 바꾸기 전에는 18), 그리고 쓰레기 치우기 뒤에도 돌려주지 않은 힙이다.
- 돌리는 동안 붙는 GPU 110~120MB는 WKWebView에서 화면을 갱신하는 한 피할 수 없다. 네이티브 그리기(Metal)라면 이 값이 큐브 장면의 버퍼 몇 MB로 준다. 5절 3단계 맥 시제품은 이 값과 가만히 있을 때 합계를 이 스크립트와 같은 상태로 재어 견준다.

## 3. 웹 화면이 지금 해 주는 것(옮기면 잃거나 다시 만들 것)

- **한 벌 코드**: 큐브 상태·돌리기·섞기·키 배치·힌트(OLL·PLL 알아보기)·티어·다시 보기·공식 연습이 사이트와 같은 TypeScript 코드다. 사이트와 앱의 결과가 어긋날 일이 없다.
- **판 없이 고치기**: 큐브 화면은 사이트에서 불러오므로, 오늘처럼 테두리·키 그림을 고치면 앱 판을 내지 않아도 바로 들어간다.
- **기록 저장**: 기록·다시 보기는 지금 웹 저장소(localStorage)에 있다.

네이티브로 가면 셋 다 대가가 생긴다. 특히 첫째가 중요하다. 사이트 머리글이 「누구든 공정하게」라서, 앱에서 맞춘 기록을 나중에 순위에 올리려면 사이트와 **같은 섞기·같은 판정**을 내야 한다.

## 4. 고른 구조와 대안

### 권하는 구조: Rust 코어 + Rust 그리기 + 얇은 네이티브 껍데기

- **코어(Rust)**: 큐브 상태와 돌리기, 섞기 만들기(같은 씨앗이면 사이트와 같은 섞기), 다 맞췄는지 판정, OLL·PLL 상황 알아보기와 힌트 공식 고르기, 티어 계산, 다시 보기 기록 형식, 키 배치.
- **그리기(Rust, wgpu)**: 맥은 Metal, 윈도우는 Direct3D 12로 그린다. 7×7도 조각이 많지 않아 가볍다. 가만히 있을 때는 그리지 않는다.
- **껍데기(플랫폼마다)**: 맥은 지금 Swift 앱을 그대로 두고 웹 화면 자리에 Rust 그리기 화면을 끼운다(손으로 쓴 C ABI로 연결, UniFFI는 의존을 늘려 쓰지 않는다. 5-2). 윈도우는 Rust로 투명 창, 전역 단축키, 트레이 아이콘, 업데이트를 만든다.
- **어긋남 막기**: 사이트 TypeScript 엔진과 Rust 코어가 같은 결과를 내는지 같은 시험 자료(JSON: 섞기 씨앗 → 섞기, 수 목록 → 상태, 상태 → 힌트·판정)로 양쪽에서 돌린다. CI에서 어긋나면 깨진다.
- **웹에 남기는 것**: 해법 익히기, 대결(같이 하기), 큐브 모양 만들기 같은 큰 화면은 사이트로 연다. 앱은 지금처럼 혼자 하기 전용이다(고정 규칙 5절).

### 대안

| 안 | 장점 | 단점 |
|---|---|---|
| 지금 그대로(맥 WKWebView, 윈도우 Tauri) | 한 벌 코드, 판 없이 고치기 | 메모리 250~300MB가 그대로 |
| 플랫폼마다 따로(맥 Swift+SceneKit, 윈도우 C#+Direct3D) | 플랫폼에 가장 잘 맞음 | 코어를 세 벌(TS·Swift·C#) 짜고 셋을 맞춰야 함 |
| Rust 코어 + 플랫폼별 그리기(맥 SceneKit, 윈도우 Direct3D) | 코어 한 벌 | 그리기를 두 벌 짬 |
| **Rust 코어 + Rust 그리기 + 얇은 껍데기(권함)** | 코어·그리기 한 벌, 가벼움 | Rust·wgpu를 새로 들이고, 큐브 생김새(테두리·거울)를 Rust로 다시 짬 |

### 5-2. 3단계 맥 시제품(2026-11-11)

**결론**: 대부분의 시간(가만히·포커스 없음·숨김)에 메모리가 약 170MB에서 약 40MB로 4분의 1이 되고, 돌리는 동안 CPU가 코어의 15~18%에서 3~4%로 줄었다. 돌리는 동안의 메모리는 덜 준다(웹 265~296MB → 네이티브 약 223MB). 그 몫 대부분은 맥의 그래픽 드라이버가 GPU에 계속 그리기를 보내는 동안 붙이는 메모리라, 웹(WebKit GPU 프로세스)이든 네이티브든 생긴다. 그래서 **4단계(맥 옮기기)로 가기를 권한다.** 다만 돌리는 동안 메모리는 아래 「남은 것」 첫 줄을 먼저 본다.

- 맥의 그래픽 드라이버는 GPU에 계속 그리기를 보내는 동안 프로세스에 약 120MB(`IOAccelerator (graphics)`)를 붙이고, 멈추면 몇 초 안에 거둘 수 있는 메모리로 바꾼다. 2-2절의 「화면을 계속 다시 그리는 동안 GPU +110~120MB」(웹 칸 색만 바꿔도 붙던 것)와 같은 현상이다. 그래서 네이티브로 가도 돌리는 순간의 메모리는 크게 줄지 않는다. 복사 명령이 장마다 끼면 약 80MB가 더 붙어서, 장마다 버퍼를 쓰지 않게 바꿨다.
- 같은 그리기가 창 없는 벤치에서는 146MB, 앱 측정에서는 223MB였다(앱 실행 파일이 새 라이브러리인 것은 확인함). 원인은 아직 모른다(아래 「남은 것」).

### 5-3. 최대 메모리·설치 용량 연구(2026-11-11)

> 사용자(시제품을 써 본 뒤): 「다른 건 좋은데 1. 설치 용량 증가 2. 메모리 최대 사용량은 거의 동일 이 두 점이 조금 걸리네.」, 「큐브 사용성 자체는 거의 동일」, 「메모리를 줄일 방법을 연구해줘. 지금 정도면, 전환하는 비용이 크다고 판단할 수 있을 것 같아.」 그래서 돌리는 동안의 최대 메모리를 먼저, 네이티브 전환 없이 지금 웹 앱에서 되는 길도 같은 무게로 봤다. 설치 용량은 빌드 설정 표만.

**결론**

- 돌리는 동안 붙는 메모리는 **맥 그래픽 드라이버가 「최근 1~3초 안에 GPU 그리기를 보낸 프로세스」에 붙이는 고정 몫 약 108MB**다. 초당 장 수(1장이어도 같다)·그릴 크기(16px~1024px)·MSAA·드로어블 수와 상관이 없다. 그래서 우리 프로세스에서 GPU로 그리는 한(웹 WebGL, wgpu, 맨 Metal 모두) 돌리는 동안 최대 메모리는 크게 줄지 않는다. 프레임·크기를 줄이는 안은 모두 효과가 0~4MB였다.
- 크게 줄이는 길은 하나다. **돌리는 연출을 시스템 합성기(Core Animation, 실제 합성은 WindowServer)에 맡겨, 우리 프로세스가 GPU 그리기를 보내지 않게 한다.** 웹에서는 CSS 3D(`transform-style: preserve-3d`) + Web Animations, 네이티브에서는 `CATransformLayer`다. 둘 다 돌리는 동안 앱 쪽에 드라이버 몫이 붙지 않았다(시안 기준 웹 합계 75MB, 네이티브 약 11MB).
- **지금 웹 앱에서 바로 할 수 있는 것: 미니 화면 큐브를 three.js(WebGL) 대신 CSS 3D로 그리기.** 사이트 배포만으로 앱에 들어간다(앱 새 판 필요 없음). 시안은 돌리는 동안 265~296MB → 75MB였고, 실제 미니의 자바스크립트(React·소리·워커)를 더하면 약 120MB로 본다(추정). 단, 화면에 계속 바뀌는 글자 같은 **다시 그리기가 있으면 웹 GPU 프로세스가 그것을 GPU로 그려 108MB가 다시 붙는다**(0.1초마다 바뀌는 시간 글자로 확인). 지금 미니에는 맞추는 동안 계속 바뀌는 글자가 없다.
- **전환한다면: wgpu 대신 Core Animation 3D + Rust 코어.** 모든 상태 약 25~30MB(추정, 앱 껍데기 포함), 설치 용량은 유니버설 실행 파일 +약 0.6MB(wgpu는 +7MB). 글자를 0.1초마다 바꿔도 드라이버 몫이 붙지 않는다(앱이 CPU로 그린다). 대신 생김새는 면마다 평평한 색이 되고(조명·광택은 흉내), 윈도우판은 그 나라 합성기(DirectComposition)로 따로 그려야 한다.
- wgpu를 유지하면 돌리는 동안 151MB, 켤 때 첫 장 최고 220MB다. Metal을 직접 써도 평소 값은 같고(같은 드라이버 몫), 켤 때 최고만 약 80MB 낮아진다.

#### 생김새와 확인

- CSS 3D·Core Animation 3D 모두 면마다 평평한 색이다. 사이트 장면의 하늘빛·세 방향 빛·광택은 없고, 면 방향마다 정한 밝기나 그라데이션으로 흉내 낸다. 둥근 조각·스티커는 모서리 둥글기로 된다.
- 실루엣 윤곽: 웹은 3D가 아닌 바깥 상자에 사이트와 같은 `drop-shadow` 네 겹 + 그림자를 걸면 된다(3D 층에 걸면 Core Animation이 무시한다는 경고가 난다). 걸어도 돌리는 동안 GPU 프로세스는 18MB 그대로였다(필터를 합성기가 적용). 네이티브는 그림자 하나씩 든 층을 네 겹 감싸 같은 꼴을 만든다.
- 확인 방법의 한계: Playwright WebKit 화면 없는 모드와 `WKWebView.takeSnapshot`은 3D를 납작하게 찍었다(아주 단순한 정육면체도 같음). Chrome에서는 시안이 제대로 그려지고 돌아간다. WKWebView에서는 WebKit이 UI 프로세스에 `CATransformLayer`를 만든 것(단순 정육면체 1개, 시안 약 85개)으로 3D 합성을 확인했고, 실제 앱 창의 모습은 아래 명령으로 사람이 본다.

| 같은 설정, arm64만(참고: 인텔 지원을 끊는 결정은 사용자 몫) | 3.67 | 7.09 | 2.99 |
| opt-level "s", arm64 | 4.41 | 7.84 | 2.98 |
| opt-level "z", arm64 | 4.44 | 7.87 | 2.98 |
| 코어만(wgpu 없음: Metal 직접·Core Animation 길의 Rust 몫), 유니버설 | 약 1.2(칩마다 +0.31 잼) | 약 4.6 | 약 2.0(추정) |

- 크기를 줄이는 빌드 설정은 이미 다 들어 있다. fat LTO·codegen-units 1·panic abort는 Cargo.toml에, 기호 지우기는 `build.sh`의 `strip -rSTx`, `-dead_strip`은 SwiftPM release 링크가 기본으로 건다. opt-level "s"·"z"는 오히려 실행 파일이 0.7MB 커지고 zip은 같았다.
- panic abort는 FFI에 안전하다. C 함수 밖으로 되감기(unwind)가 넘어가지 않고 그 자리에서 끝난다(Rust 1.81부터 `extern "C"` 밖으로 나가는 패닉은 어차피 끝낸다).
- wgpu 기능은 이미 최소다(`metal`·`wgsl`·`std`·`parking_lot`). WGSL 읽기를 빼려면 셰이더를 MSL로 직접 주는 실험 기능(passthrough)이 필요하고 naga의 MSL 출력은 남아 시도하지 않았다.
- 크기 대부분(칩마다 약 3.3MB)은 wgpu·naga다. Metal 직접은 wgpu를 빼므로 코어만 줄에 가깝지만(셰이더 미리 번역 `.metallib`은 이 맥에 Metal Toolchain이 없어 `xcodebuild -downloadComponent MetalToolchain`이 필요하다. 받지 않았다), 메모리는 평소 값이 같아 시제품을 만들지 않았다.
- `swift build`는 정적 라이브러리가 바뀐 것을 몰라 다시 링크하지 않을 수 있다. 크기를 견줄 때는 `.build/<칩>-apple-macosx/release/Cubie`를 지우고 빌드했다.

### 5-4. 실제 미니 화면에서 CSS 3D 그리기 실험(2026-11-11)

> 사용자: 「메모리를 줄일 방법을 연구해줘. 지금 정도면, 전환하는 비용이 크다고 판단할 수 있을 것 같아.」 그래서 5-3의 ①(웹 그대로, 미니 큐브만 CSS 3D)을 실제 미니 코드 위에 실험 주소로 넣고 같은 측정 모드로 쟀다. 기본은 그대로 three.js다.

**결론**

- 돌리는 동안 메모리가 **260MB → 139MB**(거울 숨김 261 → 130), 가만히 **243 → 98MB**로 준다. GPU 프로세스는 돌리는 동안 151 → 22MB로, 5-3의 드라이버 몫 108MB가 붙지 않는다. 5-3의 추정(약 120MB)보다 20MB쯤 높은 것은 앱(UI) 프로세스가 Core Animation 층을 들고 있는 몫(Cubie 칸 17 → 26~27MB)과 WebContent의 조각 상자(DOM)다.
- 대신 **돌리는 동안 CPU가 늘었다**: 27.6% → 40.1%(거울 보임), 21.0% → 25.5%(거울 숨김). 0.12초마다 한 수씩 200수를 두는 측정이라 실제 손보다 빠르다. 가만히·포커스 없음·숨김은 둘 다 0~2%로 같다.
- 맞추는 동안 계속 바뀌는 글자는 미니 화면에 없다. 바뀌는 표시는 아래 목록처럼 한 번씩만 칠한다.
- 기본값으로 바꿀지는 사용자가 실제 앱 창으로 생김새를 본 뒤 정한다(아래 「의견」).

**넣은 것**(`apps/web/src/cube/view/css-cube-view.ts`, 계산 `css-math.ts`, 미니 화면 `MiniCubeApp.tsx`의 `miniRenderCss`)

- `?render=css`일 때만 three.js 대신 CSS 3D 장면(`CssCubeView`)을 만든다. 미니 화면·섞기 연출은 두 장면이 함께 맞춘 꼴 `CubeScene`(`view/types.ts`)만 부른다. 맞춤 판정·키 입력·기록은 그대로다.
- 2×2~7×7, 수 돌리기(그 층 조각을 돌림 상자에 옮겨 `transform`만 Web Animations로, 끝나면 조각 행렬에 굳힌다), 섞기 연출 셋(하나씩 빠르게·짧은 연출 한 바퀴·바로), 실루엣 윤곽(3D가 아닌 바깥 상자에 지금과 같은 흐림 없는 선 + 그림자), 거울 판, 앱에 알리는 누름 자리(`hitRects`).
- 카메라·거울 판 자리는 three.js 장면과 같은 식(세로 시야각 30°, `mirrorPanels`·`mirrorFrame`)이라 같은 창에서 큐브가 같은 크기·자리에 온다.
- **돌리는 동안 다시 칠하지 않는다.** 칸 색은 `setStickers`(섞기·판 바꾸기)에서만 칠한다. 거울 판은 판마다 스티커를 한 벌 더 두고 판 평면으로 눌러(`mirrorFlatten`) 같은 행렬로 함께 돌린다. 수마다 판 칸 색을 바꾸면 그것이 다시 칠하기라 108MB가 다시 붙는다.
- 조각은 겉면만 둔다(3×3 층 54장). 속은 층을 돌리는 동안만 자르는 면에 검은 판 두 장(도는 쪽·나머지 쪽)으로 막는다. 처음에는 조각마다 여섯 면(156장)을 두었는데 CPU가 44.8%였다. 거울 판이 안 보이면 판 쪽 조각은 돌리지 않고 끝난 자리만 쓴다.
- 시험: 단위 `css-math.test.ts`(CSS 좌표 바꾸기, 투영이 카메라와 같은지, 거울상 자리가 `mirrorCells`와 같은지), `css-cube-view.test.ts`(2×2~7×7에서 장면이 계산한 칸이 스티커 계산과 같은지, 상자 수, 누름 자리). 화면 시험 `e2e/cube-mini-css.spec.ts`(연출을 켜고 섞기 → 거울·누름 자리 넷 → 키로 거꾸로 맞춤 → 장면도 맞춘 모양, 기다리기는 모두 조건).

**상태별 견주기**(측정 모드 `measure-memory.sh`, 창 96pt·배율 2, 3×3, 단위 MB. CSS 3D는 `--query render=css`. 같은 날 같은 앱 빌드)

- CSS 3D의 GPU 최고 156MB는 측정 표본(1초 간격)에는 한 번도 잡히지 않은 짧은 순간이다. 5-3 시안도 켤 때 첫 그리기 1~2초에 GPU 128MB가 잠깐 생겼다. 층 내용(스티커 그림)을 처음 칠할 때로 본다(가르지 않았다).
- CPU가 느는 곳은 앱(UI) 프로세스(Cubie 칸 4.9 → 15.2%)다. 수마다 층 묶음을 옮기는 일(돌림 상자로 옮기고 되돌리기, 행렬 쓰기)을 WebKit이 UI 프로세스의 Core Animation에 보내는 몫으로 본다(5-3 시안에서도 9~10%). 남은 줄일 거리: 조각 상자를 옮기지 않고 조각마다 돌림 행렬을 붙이기, 거울 판 세 벌 대신 보이는 면 칸만 두기.

**맞추는 동안 바뀌는 표시**(다시 칠하면 GPU 프로세스가 그려 몇 초 동안 108MB가 붙는다)

- 맞추는 동안 계속 바뀌는 글자·숫자: **없다**. 시간·수는 화면에 내지 않는다(`FocusClock`은 재기만 한다).
- 한 번씩 바뀌는 것: 다 맞춘 순간의 축하(시간 숫자, 약 2.4초 페이드), 힌트 창(앱 말풍선이 없거나 넉넉한 창일 때만 창 안, 힌트를 부를 때마다), 공식 연습 창 안 카드(넉넉한 창이나 옛 앱일 때, 키마다 차례·콤보·공식 칸이 바뀜), 공식 연습 ✓, 섞기·판 바꾸기의 칸 색(`setStickers`). 앱 말풍선으로 가는 힌트·연습 글은 앱이 그린다.
- 장면 안: 수마다 칸 색을 바꾸지 않는다(위 「넣은 것」).

**생김새**

- Chromium(시스템 Chrome, 배율 2, 200×200)으로 바탕 넷(#000·어두운 회색·흰색·사진) × 떠 있음·맞추는 중(거울 보임), 3×3·5×5를 three.js와 나란히 찍었다. 같은 자리·크기, 실루엣 윤곽·거울 판 모두 같게 나온다. 다른 점: 조명·광택이 없어 면마다 평평한 색(스티커에 옅은 비스듬한 빛 띠), 조각 모서리가 덜 둥글다, 검은 바탕에서 조각 사이에 아주 옅은 이음매가 보일 때가 있다. 층을 돌리는 도중(R·M)도 속이 검은 판으로 막혀 보인다.
- **WebKit(Playwright 화면 없는 모드)은 이번에도 3D를 납작하게 찍었다**(앞면 하나만 평면으로, 거울 판도 납작). 5-3과 같은 한계라 앱 창의 실제 모습은 아래 명령으로 사람이 본다.

**못 다룬 것**

- 기록 창의 다시 보기(`?view=records`)는 그대로 three.js다. 장면이 따로 열리는 창이라 이번 측정에 들지 않는다.
- 끌어 둘러보기·밀기·칸 표시는 없다(앱은 마우스 둘러보기를 끄고, 미니 화면은 칸 표시를 쓰지 않는다). 브라우저에서 연 미니 화면도 `?render=css`면 끌어 돌리기가 없다.
- 스티커 없는 모양·가린 색 설정은 받지만 눈으로 견주지 않았다. 4×4 이상은 단위 시험(상태)과 5×5 스크린샷만 봤고, 6×6·7×7 메모리·CPU는 재지 않았다(3×3만).
- 앱 창(WKWebView)의 실제 3D 모습은 사람이 위 명령으로 확인해야 한다.

**의견: 기본값으로 바꿀지**

- 장점: 돌리는 동안 메모리 약 −120MB(260 → 139), 가만히 −145MB, 최고치 합 약 −95MB. 앱 새 판 없이 사이트 배포만으로 들어간다. 네이티브 전환(4단계)보다 비용이 훨씬 작다.
- 단점: 돌리는 동안 CPU +5~13%p(맞추는 동안만, 가만히는 같다), 조명·광택이 없는 평평한 생김새, 기록 창 다시 보기와 두 갈래 그리기 코드를 함께 지켜야 한다. 앱 엔진에서의 생김새를 아직 사람이 보지 않았다.
- 권함: 사용자가 실제 앱 창으로 `?render=css`를 써 보고 생김새·손맛이 괜찮으면 미니 화면 기본을 CSS 3D로 바꾸고(three.js는 둘러보기가 필요한 브라우저 미니에만 남기거나 지움), 그 뒤 CPU 줄이기(조각마다 돌림 행렬)를 한 번 더 해 본다. 생김새가 아쉬우면 지금 그대로 두고 전환 판단은 5-3 ②(Core Animation 3D)로 넘긴다.

### 5-5. Core Animation 3D 네이티브 그리기를 실제 앱 전체로(2026-11-12)

> 사용자(5-4 CSS 3D 실험의 메모리 139MB·CPU 40%를 보고): 「웹사이트를 렌더해서 그렇고, 그래픽을 네이티브로 다 새로 만들면 괜찮지 않을까?」. 앞서 걸린다고 한 것은 「설치 용량 증가」와 「메모리 최대 사용량이 거의 동일」이었다. 그래서 5-2의 wgpu 그리기를 Core Animation 3D(`CATransformLayer` + `CALayer`)로 바꿔, 실제 앱(메뉴·키·섞기 연출·거울 판·윤곽까지)으로 같은 측정을 했다.

**결론**

- **두 걱정이 모두 풀린다.** 메모리 최대치가 웹 약 400MB(프로세스마다 최고치 합) → **17.6MB**, 돌리는 동안 294~300MB → **17MB**, 가만히 261MB → **10.5MB**다. 앱 프로세스는 GPU로 그리기를 보내지 않아 드라이버 몫(108MB, 5-3)이 붙지 않는다. 설치 용량은 wgpu를 빼서 유니버설 실행 파일 7.67MB → **1.67MB**(지금 0.1.9의 0.6MB보다 +1.1MB), zip 4.72MB → **2.18MB**(+0.5MB)다.
- **CPU**: 앱 쪽은 돌리는 동안 **0.4~0.6%**(웹 12~17%, wgpu 2~3%). 대신 실제 합성은 WindowServer가 하므로 그쪽에 몫이 생긴다. 화면에 띄워 같이 재 보니 돌리는 동안 WindowServer가 바탕보다 약 +7~14%p(웹은 +13~20%p) 늘었다. 다른 앱 화면 변화가 섞여 흔들림이 크고(바탕 23~33%) 한 번씩만 쟀다. 합쳐도 웹보다 작다.
- 생김새는 웹 three.js와 같은 자리·크기·윤곽·거울 판으로 나온다. 조명·광택은 스티커에 미리 그린 옅은 빛 띠로 흉내 낸다(5-4 CSS 3D와 같은 수준).
- **4단계(맥 옮기기)를 이 그리기로 가기를 권한다.** wgpu 경로는 앱에서 뺐다(아래 「wgpu 경로」).

**의견: 4단계를 이 그리기로**

- 장점: 모든 상태 10~17MB(웹 130~300MB, wgpu 34~151MB, CSS 3D 98~139MB), 최고치 17.6MB, 앱 쪽 CPU 1% 안, 설치 용량 +0.5MB(zip). 그리기 코드가 Swift 수백 줄이라 4단계 옮기기(말풍선·메뉴·키 그림)가 같은 AppKit 안에서 이어진다.
- 단점: 조명·광택은 흉내(웹 CSS 3D와 같은 수준), 윈도우판은 그리기를 따로 만들어야 한다(DirectComposition 같은 그 나라 합성기, 코어 한 판 C ABI는 같이 씀). 돌리는 동안 WindowServer 몫(약 +10%p)은 남는다.
- 다음 일: 사용자가 실제 창으로 생김새·손맛을 보고 괜찮으면 4단계(기록 옮기기·힌트·공식 연습·단축키 표·사용자 배치)를 이 그리기 위에서 시작한다. 그 전에 윤곽 그림자 겹을 줄였을 때 WindowServer CPU가 얼마나 주는지 한 번 재 본다.

### 5-6. 4단계 완전 네이티브로 옮기기(2026-11-12)

> 사용자: 「완전 네이티브로 만들어서 메모리 사용량 측정 필요」, F2L 전 힌트는 「사람 해법 계산도 Rust로 옮기기」. 그리기는 5-5의 Core Animation 3D, 계산은 Rust 코어(사이트와 공통 시험 자료로 어긋남 0)가 맡는다. 앱은 간단한 혼자 하기 전용이라(고정 규칙 5절) 큰 화면(기록 창·티어표·설정·배우기)은 사이트 창으로 남겨도 된다.

#### 짜임

- **스위치**: 기본이 네이티브 화면이다. 되돌림 스위치 `CUBIE_WEB=1`(예전 웹 큐브 창)은 2026-11-25 지웠다(5-20, 마지막 판은 git 태그 `cubie-web-fallback-last`). 앱 저장소를 읽지 않아 켜면 옛 WebKit 기록이 보이고 맞춘 판이 네이티브 기록에 들어가지 않아 되돌림 구실을 못 했다.
- **앱 껍데기**: `AppDelegate`(메뉴·단축키·말풍선·단축키 표·업데이트·사이트 창)는 `CubeSurface` 약속만 본다. 창 다루기(자리 기억·끌기·핀치·빈 곳 넘기기)는 두 화면이 `FloatingWindow`를 함께 쓴다.
- **네이티브 화면**(`NativeCubeWindow`): 포커스 시계·기록 책·힌트 제한·떠 있을 때 움직임·축하·소리·프로필. 계산은 모두 코어 C ABI(`native/cubie-native/src/ffi_game.rs`·`ffi_records.rs`, 머리 파일 `cubie_native.h`).
- **코어 이식**(`native/cube-core`, 브랜치 `cubie-core-human`을 합침): 한 판 세션 `session.rs`(이정표 `progress.rs`, 흐름 콤보 `combo.rs`), 사람 해법 `human.rs`(`solve_cfop`·`solve_advanced2`), 힌트 고르기 `hint.rs`, 키캡 `keys/route.rs`, 공식 연습 진행기 `practice.rs`. 공통 시험 자료 `fixtures/session.json`(13판·467차례), `hint.json`(124), `keycaps.json`(2,019수), `practice.json`(1,329) 모두 어긋남 0. CI `rust` 작업의 조건에 새 기준 파일(`packages/cube-ai/`, `solve-session.ts`, `flow/combo.ts`, `practice/`, `keys/move-keys·reach.ts`, `mini/practice.ts`, `algs/store.ts`)을 더했다.
- **저장**: UserDefaults `store.<키>`에 사이트 localStorage와 같은 키·같은 JSON 글. 앱이 여는 사이트 창(지금은 설정 창의 「모든 설정…」 하나)에는 문서 시작 때 그 글을 넣고(`WebStoreSync`), 그 창을 닫으면 사이트에서 바뀐 `cube.*` 키(앱이 쓰는 `cube.mini.*` 빼고)만 읽어 온다(5-19).
- **기록 옮기기**: 처음 띄울 때 `~/Library/WebKit/kr.byb.cubie/WebsiteData/Default/<출처>/<출처>/LocalStorage/localstorage.sqlite3`를 읽기 전용으로 열어(출처 파일에 사이트 호스트가 든 폴더만) `cube.`로 시작하는 키를 같은 글 그대로 옮긴다. 웹 저장소는 지우지 않고, 표시 `cubie.migrated.v1`(옮긴 때·키)을 남겨 다시 하지 않는다. 네이티브에 이미 있는 키는 덮지 않는다. 이 맥의 웹 저장소에는 `cube.mini.v1`(40KB)·`cube.mini.profile.v1`·`cube.mini.practice.v1`이 있었다(키 이름과 길이만 봄).

#### 웹과 다르게 한 것(일부러)

- 힌트·공식 연습은 창 크기와 상관없이 늘 큐브 옆 말풍선이다(웹은 짧은 변 240px 이상이면 창 안 카드). 앱 창 안에 글을 그리면 큐브와 겹치고, 말풍선이 이미 있다.
- 다시 볼 판이 없을 때 홈 시연은 사이트 첫 화면 해법 표 전부(2×2 둘, 3×3 넷, 4×4~7×7 축소법 둘)를 사이트와 같은 수로 한다(5-10). 섞기는 바로 보이고 풀이는 그동안 화면 스레드 밖에서 만든다(사이트도 섞는 동안 워커가 푼다). 사이트에 있는 「워커가 늦으면 화면 스레드에서 풀기」·「풀이를 기다리는 상한」은 두지 않았다: 가장 오래 걸리는 7×7도 약 0.6초라 섞기와 섞은 뒤 멈춤(약 6.5초) 안에 끝나고, 혹시 늦으면 풀이가 올 때까지 멈춰 있는다.
- 단축키 표의 칸 글은 코어 `keys::table`이 사이트 `KeyboardMap` 「모두」와 같게 만든다(3×3 「두 손」 X·. = M′, 큰 큐브에서 못 쓰는 M′·M은 흐리게, Alt 줄, ↑ 처음 각도). 같은지는 공통 자료 `fixtures/keytable.json`(두 손·표기·사용자 × 2~7)으로 본다(2026-11-12). 줄이 넷인 칸(Alt와 Alt+Shift가 다 있는 사용자 배치)은 글꼴을 줄여 칸 안에 넣는다(웹은 넘치면 잘린다).
- 소리는 사이트와 같은 모양을 처음 쓸 때 PCM으로 만들어 두고 `NSSound`로 낸다(돌리기는 여섯 벌을 돌려 씀, 울림 없음). 웹은 수마다 새로 합성했다.
- 3D로 돌린 층(조각 겉면 몸통·스티커·거울 판과 유리·돌리는 동안 자르는 면 판)은 곧은 가장자리 다듬기(`allowsEdgeAntialiasing`, 네 변)를 켠다(`CACubeView.smoothEdges`). Core Animation은 기본으로 둥근 모서리만 다듬고 곧은 변은 다듬지 않아, 사용자가 「대각선 안티알리어싱이 애매하고 조금 계단처럼 보인다」고 했다(2026-11-12. 웹과 나란히 띄워 보면 차이는 크지 않다고 했고, 메모리·성능 부하가 크면 되돌리기로 함). 잰 값(`measure-memory.sh --native`, 96pt): 메모리는 상태마다 −1.1~+0.8MB(가장 늘어난 공식 연습 중 29.9 → 30.7MB), 돌리는 중 CPU는 거울 보임 3.1 → 3.6%, 거울 숨김 3.5 → 3.2%, 공식 연습 2.0 → 2.6%, 가만히·숨김은 그대로 0%. 되돌릴 기준(어느 상태든 5MB 넘게, 돌리는 중 2%p 넘게)보다 작아 그대로 둔다. 화면 밖 스크린샷(`CARenderer`)은 설정 전에도 대각선을 다듬어 그려 전후가 거의 같다(192×192 중 5픽셀 다름, `docs/cubie-native/compare-edges.webp`). 실제 창(WindowServer 합성)에서 나아졌는지는 사용자가 본다.

### 5-7. 사이트 미니 화면과 네이티브가 어긋나지 않게(2026-11-12)

> 사용자: 「네이티브가 기존과 모든 기능이 같은가, 앞으로 불일치를 해결할 방법은?」. 0.2.0부터 큐브 창 고침은 Cubie 새 판으로만 나가므로(5-6 「판을 내기 전에」 8), 사이트 미니 화면만 고치면 앱과 조용히 달라진다. 장치는 셋이다.

1. **값은 공통 시험 자료로 견준다.** 판 규칙·섞기·힌트·공식 연습·키캡·F1 표 글자·한 판 기록·티어, 그리고 화면 상태(공식 연습 가리기·F1 표 칸 색)는 코어가 만든 값과 사이트가 만든 값을 같은 자료(`native/cube-core/fixtures/*.json` ↔ `apps/web/src/cube/native/core-fixtures*.ts`)로 본다. 사이트 결과가 바뀌면 사이트 쪽 자료 시험이 먼저 깨지고, 자료를 다시 쓰면 `native/`가 바뀌어 CI `rust` 작업이 돈다. 화면 상태 자료는 `mask.json`(가리기 이름 × 크기, 공식 연습 단계마다 시작 모양에서 칠할 값)·`keypaint.json`(F1 표 칸마다 칠하기, 배색마다 칸 바탕·선·사선 색), 홈 시연은 `hero.json`이다(2026-11-12). ### 5-8. 기록 창·티어표·설정 창도 네이티브로(2026-11-12)

> 사용자: 「나중에는 기록 창도 네이티브로 바꾸면 좋겠네」(지도 남은 일 ⑤). 근거는 5-6 측정에서 기록 창을 열면 Cubie 37MB + 사이트 창 68MB = 105MB였던 것.

**결론**

- 메뉴 「기록 보기」·「티어표」·「키 배치·색…」이 앱이 직접 그린 창(AppKit)을 연다. WebKit 프로세스가 뜨지 않는다. 사이트 화면과 같은 글·같은 차례·같은 동작이고, 계산은 코어 C ABI다(요약 평균은 새로 `summary.rs`, 사이트와 공통 시험 자료 어긋남 0).
- 메모리(측정 모드, 같은 앱 빌드): 기록 창을 연 동안 102.6MB(사이트 창) → **32.0MB**, 세 창을 함께 연 동안 353.0 → **39.2MB**(다시 보기 중 353.8 → 39.9), 세 창을 닫은 뒤 60.8(GPU 프로세스 24MB가 남음) → **34.8MB**. 앱이 끌 때까지 쓰는 최고치는 Cubie 40.3MB 하나다(사이트 창이면 Cubie 37.4 + WebKit GPU 최고 233.3 + WebContent 셋). 큐브 창만 쓰는 상태(11~30MB)는 그대로다.
- 되돌림: 처음에는 `CUBIE_WEB_WINDOWS=1`이면 세 창만 예전 사이트 창이었다. 「모든 설정…」 말고 쓰는 곳이 없어 2026-11-25 지웠다(5-20, git 태그 `cubie-web-fallback-last`).
- 설정 창의 사용자 배치 편집(키 지정·겹친 키 묻기·내보내기·가져오기)은 이때 옮기지 않았다가 2026-11-16 옮겼다(5-9). 이제 「모든 설정…」만 사이트 창을 연다.

| 해법 | 한 판 계산 |

- 처음 옮긴 그대로는 7×7이 한 판 약 12초였다. 가운데 단계에서 공식마다 준비 수 목록을 잠금·해시표로 다시 찾고 준비 수 색 배열을 해시표에 두던 것을, 공식을 만들 때 준비 수를 함께 묶고 색 배열은 번호로 바로 찾게 바꿔 약 0.6초가 됐다(수는 그대로, 자료 어긋남 0).
- 그래도 화면 스레드에서 0.6초면 큐브가 멈춰 보인다. 그래서 앱은 섞기만 먼저 코어에서 받아(`cubie_hero_scramble`, 바로 끝남) 곧바로 보이고, 같은 씨앗의 한 판(`cubie_hero_steps`)은 화면 스레드 밖에서 만든다(`NativeCubeWindow.startHero`·`HeroRun`). 섞기와 섞은 뒤 멈춤은 7×7 약 6.5초(44수 × 80ms + 3초)라 풀이가 먼저 와 있고, 섞은 뒤 멈춤이 끝나면 그 판의 나머지 걸음을 잇는다. 늦으면 풀이가 올 때까지 멈춰 있는다. 섞기가 다르면(못 풀어 다른 섞기로 다시 짠 판, 생기지 않는다) 잇지 않고 끝낸다. 사용자가 느끼는 지연은 없다(사이트는 같은 일을 워커로 한다).
- `cubie_hero_steps`는 마지막 한 판을 기억해 두어, Swift 감싸개가 길이를 묻고 다시 부를 때 두 번 풀지 않는다.

### 5-11. 티어표 진열과 메뉴 프로필 칸 흔들기(2026-11-16)

> 사용자: 「티어표 열면 옛날 모습만 나오고 엠블럼은 잘 안 보이는데?」. 사이트 티어 화면에 진열(PR #279, docs/47 14-7 「진열」)을 넣을 때 「진열은 사이트에만」으로 넘겨, 그 전 사이트 화면을 옮긴 네이티브 티어표 창(5-8)이 옛 모습으로 남았다. 실수로 보고 고정 규칙 5절·지적 기록에 적었다.

**결론**

- 앱 티어표 창이 사이트 티어 화면과 같은 차례로 그린다: 크기 단추 → 위쪽 큰 칸(엠블럼 280pt를 9초에 한 번 좌우로 천천히 흔들기, 구간 표시 마름모, 이름·내 최고 Ao5, 다음 티어까지 줄일 시간) → 열 티어 사다리(위 줄 보석·아래 줄 금속 계단, 칸마다 그 티어에 드는 시간) → 티어 매기는 법 → 크기별 기준표 → WCA 출처. 사다리 칸을 누르면(Space·Return도) 큰 칸이 그 티어로(이름·기준 시간·구간 넷, 아래에 내 기록과 위 티어면 줄일 시간), 같은 칸·내 칸을 누르면 내 티어로. 모든 칸 중간 밝기, 보고 있는 칸만 제 밝기와 티어 색 3pt 테두리·빛, 내 티어 칸은 기준표의 내 줄과 같은 밝은 배경 판, 기록이 없으면 어두운 아이언이 큰 칸에 뜨고 아이언이 보고 있는 칸.
- **3D를 띄우지 않는다.** 앱이 GPU로 그리면 드라이버가 약 108MB를 붙인다(5-3). 사이트 큰 칸 3D가 그리는 장을 ±0.5 라디안(약 29°) 안 21각으로 미리 찍은 그림을 넘기고, 이웃한 두 장을 위 층 투명도로 겹쳐 사이 각을 메운다. 앱은 초당 20번 각을 셈해 층 그림·투명도만 바꾸고, 그 사이 투명도는 합성기가 시계 한 칸(50ms) 동안 고르게 잇는다(처음 판은 초당 30번이라 CPU가 더 들었다). 지금 보이는 장만 풀어 둔다(최근 네 장, 560px 한 장 1.2MB).
- 끌면 그림이 덮는 폭 안에서 따라 돌고, 놓고 1.6초 뒤 그 각에서 다시 흔든다(사이트와 같은 셈 `TierShowcase.Sway`). 사이트처럼 한 바퀴를 넘겨 돌리지는 못한다(그림이 ±0.5 라디안까지).
- 사다리 칸은 사이트 진열 칸 그림(17각 띠, `public/cube/tiers/emblem3d/sprite/`)을 그대로 묶는다(`build.sh`가 복사). 쉬는 칸은 정면 한 장만 두고, 아래 티어부터 한 칸씩 3초 동안 띠를 풀어 `contentsRect`를 넘긴다(사이트 `cube-ladder-sweep`과 같은 60걸음). 앱은 3초에 한 번 칸을 바꾸기만 한다.
- 창이 보이지 않으면(가려짐·내림·닫힘) 큰 칸과 사다리 모두 멈추고, 동작 줄이기 설정이면 흔들지 않는다(끈 각에 남고 「처음 각도로」 단추). 확인용 `CUBIE_REDUCE_MOTION=1`.
- 메뉴 막대 메뉴의 프로필 칸 엠블럼(32pt)도 메뉴가 열린 동안 같은 9초 왕복으로 흔든다(13각 띠, 정지 그림 작은 단계와 같은 맞춤·티어 색). 메뉴가 닫히면 멈추고, 동작 줄이기면 정면 그림. 사이트 창으로 그린 화면(`CUBIE_WEB=1`)은 예전처럼 멈춘 그림이다.

**GPU 비동기 그리기를 피한 것**: 처음 만든 판은 창을 열거나 사다리 칸을 누를 때 측정 모드 최고치가 열에 예닐곱 번 160~190MB로 뛰었다(그 뒤 약 60MB로 내려옴). `footprint`로 보니 `IOAccelerator (graphics)` 89MB(되찾을 수 있는 몫), `sample`로 보니 Core Animation의 `CA::CG::AccelRenderer`가 앱 안에 Metal 문맥을 만들고 있었다. 원인은 둘: ① 넓은 칸을 `draw`로 그리면(큰 칸 테두리 상자 736×312pt, 사다리 뒤 테두리·빛) AppKit이 그 칸을 GPU 비동기 그리기로 돌린다(그 층의 `drawsAsynchronously`가 켜져 있었다) ② `CATransition`(밝기 바꿈·티어 바꿈의 겹쳐 사라지기)은 바꾸기 전 모습을 앱 안에서 찍는다. 그래서 넓은 상자는 층 속성(바탕·모서리·테두리, `FlippedView.layerDrawn`)으로, 사다리 뒤 표시는 칸마다 층 셋(배경 판·떠오르기 그림자·테두리와 빛, 칸 안쪽은 가리개)으로, 겹쳐 바꾸기는 `contents` 애니메이션으로 바꿨다. 고친 뒤 새로 켠 앱에서 티어표 열기·칸 누르기를 여섯 번 되풀이해 최고 49~65MB(뛰는 일 없음). 원래 티어표(5-8)는 넓은 칸을 그리지 않아 이 일이 없었다(같은 방법으로 여섯 번 최고 20~22MB). 다시 생기지 않게: 넓은 상자는 `layerDrawn`으로 두고, `CATransition`을 쓰지 않는다.

- ~~「이 크기는 아직 Ao5가 없습니다.」 문장은 두 줄로 나눠 둔다~~(2026-11-18 5-14: 「이 크기는 아직 5판 평균이 없어요.」 한 문단, 사이트 `?records=cubie`와 같은 글. 2026-11-20 뒤 문장은 지움).
- 휴대폰 너비 꼴(사다리 60px)은 없다(창 너비 760pt 고정 꼴).

**판을 내기 전에 사용자가 볼 것**

1. 메뉴 「티어표」: 큰 칸 엠블럼이 천천히 좌우로 흔들리는지(끊겨 보이거나 두 장이 겹쳐 흐려 보이지 않는지), 사다리 칸이 아래 티어부터 한 칸씩 흔들리는지, 다른 창으로 덮거나 창을 내리면 멈추는지(활성 상태 보기에서 Cubie CPU).
2. 사다리 칸 누르기: 큰 칸이 그 티어로 200ms 겹쳐 바뀌는지, 이름·기준 시간·구간 넷과 내 기록 칸, 같은 칸·내 칸을 다시 누르면 내 티어로, 보고 있는 칸 테두리·빛과 내 칸 배경 판, 마우스를 올리면 살짝 떠오르는지, Tab으로 칸을 옮기고 Space로 누르기.
3. 큰 칸을 좌우로 끌면 따라 돌고 놓은 뒤 잠시 있다 다시 흔드는지.
4. 시스템 설정 「손쉬운 사용 → 디스플레이 → 동작 줄이기」를 켜면 큰 칸·사다리·메뉴 칸이 멈추는지, 큰 칸을 끈 뒤 「처음 각도로」 단추.
5. 메뉴 막대 메뉴를 열면 프로필 칸 엠블럼이 천천히 흔들리고 닫으면 멈추는지(밝은·어두운 메뉴).
6. 크기를 바꾸거나 기록이 없는 크기(어두운 아이언과 문장).

### 5-12. 홈 시연 4×4 야우(2026-11-17)

> 지도 남은 일: 「야우 첫 화면 연출(야우 단계 함수를 Cubie 코어로 옮겨야 함)」. 작업 트리 브랜치, 커밋만.

사이트 첫 화면 해법 표에 「야우」(`4-yau`, docs/47 0절 「4×4 야우」)를 더하면서 앱 홈 시연도 같은 수로 돌게 했다. 해법 표 전부는 이제 2×2 둘·3×3 넷·4×4~7×7 축소법 둘·4×4 야우다.

| 해법(id) | 사이트 원본 | 코어 | 첫 면 색 |
|---|---|---|---|
| 4×4 야우(`4-yau`) | `learn/yau-hero.ts` `solveYauHuman`, `learn/yau-solve.ts` `solveYau`와 단원 길(`beginner-path.ts`·`big-path.ts`·`big-solve.ts`·`yau-path.ts`) | `yau.rs` `solve_yau_human` | 십자 셋이 가장 싼 색(고른 색을 흰색으로 읽게 스티커 색을 바꿔 흰색 차례로) |

- 야우는 탐색하지 않고 단원의 경우별 정해진 길만 따라, 옮긴 코드도 경우 고르기와 수 잇기뿐이다. 축소법(`reduction.rs`)·3×3 사람 해법(`taught.rs`)과는 다른 길이라 3×3 처음 맞추기의 다음 한 걸음(흰 십자 ~ 코너 방향)도 `beginner-path.ts`에서 따로 옮겼다.

**비교 그림** `docs/cubie-native/compare-hero-yau.webp`: 4×4 야우 씨앗 5, 멈춤 자리마다 웹(이 브랜치로 빌드한 사이트 미니, WebKit)과 네이티브(화면 밖 스크린샷)를 나란히, 어두운 회색·#000 바탕. 다시 만들기는 5-10과 같고 해법만 `CUBIE_NATIVE_N=4 CUBIE_NATIVE_SHOT_HERO=4-yau:5`, 배포 전에는 사이트 주소에 로컬 서버를 준다.

**옆 센터 쥐기 고침(2026-11-17, docs/47 16-22)**: 흰-주황 엣지 블럭이 우연히 제자리라 흰 십자 넷이 다 있는 판에서 `side_hold`가 넣어 둔 흰 십자 엣지를 오른쪽에 두어 R이 빼냈다. 사이트와 함께 흰-주황 자리를 오른쪽에 둔 쥐기만 고르게 고쳤고, `hero-show-yau.json`에 그런 판(씨앗 1029, 첫 면 노랑)을 더했다. 첫 화면 연출 씨앗 1~2000 가운데 셋(1029·1302·1942)의 수가 바뀐다. **Cubie 새 판이 필요하다**: 홈 시연 4×4 야우는 앱 코어가 계산하므로 새 판을 내야 사용자 앱에서 바뀐다(판 내기는 하지 않음, 지도 next-cube). 이 작업 트리에서는 `cargo test`가 rustc를 찾지 못해 돌지 않았다.

### 5-13. 표기 오류 글 말투(2026-11-17)

사이트의 다른 게임 화면 글을 해요체 + 마침표로 맞추면서(docs/standing-rules.md 3절) 큐브 표기 오류 글 넷도 바꿨다. 코어 `notation.rs`가 사이트 `cube-engine/src/notation.ts`와 같은 글을 내야 해서 함께 고쳤다.

| 전 | 후 |
|---|---|
| 큐브 돌리기에는 층 번호·w를 붙이지 않는다 | 큐브 돌리기에는 층 번호·w를 붙이지 않아요. |
| 가운데 층에는 층 번호·w를 붙이지 않는다 | 가운데 층에는 층 번호·w를 붙이지 않아요. |
| n×n에는 정가운데 층이 없다 | n×n에는 정가운데 층이 없어요. |
| 소문자 면에는 w를 붙이지 않는다 | 소문자 면에는 w를 붙이지 않아요. |

- 공통 자료 `moves.json`을 다시 썼고 어긋남 0(`cargo test` `moves_and_states_match_site`).
- **Cubie 새 판이 필요하다.** 코어가 앱 실행 파일에 들어가므로 바뀐 글은 다음 판부터 앱에 실린다. 다만 지금 앱은 표기 오류 글을 화면에 보이지 않는다(`cubie-native`·Swift 어디에서도 `NotationError::message`를 쓰지 않음). 그래서 이 고침만으로 판을 서둘러 낼 까닭은 없고, 다음 판에 함께 넣으면 된다.

### 5-14. 앱의 티어는 모두 Cubie 기록으로(2026-11-18)

사용자 「내 기록에 맞게 티어가 보이지 않는 것 같은데 점검해줘」(스크린샷: 기록 창은 「Cubie 기록 기준 · 최고 Ao5」 3×3 브론즈 II, 티어표 창 3×3은 「이 크기는 아직 Ao5가 없습니다」).

- **원인**: 앱 안의 티어 표시 셋 가운데 기록 창(`NativeRecordsWindow`)과 메뉴 프로필 칸(`NativeCubeWindow` `book.tier`)은 Cubie 기록(`cube.mini.v1`)으로 셌지만, 티어표 창(`NativeTiersWindow`)만 사이트 티어 화면을 옮길 때 그 화면의 `useMyTier`(사이트 혼자 맞추기 기록 `cube.records.v1`·`cube.best5.v1`)를 그대로 옮겼다. 앱에서 맞춘 판은 혼자 맞추기 기록에 쌓이지 않으니 늘 「아직 없음」이었다. 0.2.0~0.6.0 모두 같다. 사이트 창으로 여는 길(`CUBIE_WEB_WINDOWS=1`, 기록 창 사이트 화면의 「티어표」 링크)도 같은 원인이었다.

### 5-16. 엠블럼 HDR(2026-11-19, 메뉴 엠블럼 미리보기는 2026-11-20 없앰)

> 사이트 티어 화면은 HDR 맥에서 보석 티어 반짝임이 흰색보다 밝게 빛난다(docs/47 14-7 「HDR 길」). 사용자가 앱 메뉴 프로필 칸 엠블럼도 빛나는지 보고 싶어 했는데, 앱은 미리 찍은 SDR 각도 그림만 넘겨(5-11 「반짝임은 그림에 찍힌 대로다(HDR 길 없음)」) 빛나지 않았고, 사용자 티어가 브론즈라 보석 티어를 메뉴에서 볼 길도 없었다.

**결론**

- **사이트와 같은 규칙**: 보석 다섯 티어만, 화면이 흰색보다 밝게 낼 수 있을 때(`NSScreen.maximumPotentialExtendedDynamicRangeColorComponentValue > 1`, 창·메뉴가 뜬 화면) HDR로 그린다. 생김새는 SDR 그림 그대로이고 반짝임만 흰색의 최대 3배(`HDR_HEADROOM`)까지 밝다. 금속 티어·SDR 화면·잠긴(어둡게 한) 큰 칸은 지금 그대로다. 티어표 창 위쪽 큰 칸과 메뉴 프로필 칸 둘 다(사다리 칸은 사이트도 SDR 그림이라 그대로).
- **방법(배율 지도)**: 사이트 HDR 길은 화소마다 「SDR 화면 값 × 키우기 배율(1~3)」이다. 그래서 흔들기 그림(SDR 색)은 그대로 두고, 같은 각마다 배율만 담은 회색 그림을 묶는다. 앱은 HDR 화면에서만 색 그림을 선형으로 펴 배율을 곱하고(`CubieCore/EmblemHdr.swift`), 반 정밀도 확장 선형 sRGB `CGImage`에 「흰색의 3배까지」 표시(`CGImageCreateWithContentHeadroom`)를 붙여 층에 건다. 층은 macOS 26부터 `preferredDynamicRange = .high`(사이트 `dynamic-range-limit: no-limit`와 같은 뜻), macOS 15~25는 `wantsExtendedDynamicRangeContent`. 다른 화면으로 옮기거나 화면 설정이 바뀌면(`didChangeScreen`·`didChangeScreenParameters`) 다시 정한다.
- **고르지 않은 것**: HDR 그림을 통째로(PQ AVIF) 묶으면 큰 칸 105장이 약 2.4MB라 1MB 상한을 넘는다. 배율 지도는 거의 검정이라 작다. 3D(Metal) 그리기는 5-11처럼 드라이버 메모리가 붙어 쓰지 않는다. 색 그림에 더하기 섞기 층을 얹는 방법은 합성기가 흰색 위를 자를 수 있어 그림을 미리 합친다.
- **배율 지도 찍기**: `apps/web/scripts/render-emblem-posters.mjs` `ONLY=cubie-hdr` → `apps/cubie/Resources/Emblems/hdr/<보석 티어>/00~20.webp`(560px, 큰 칸 흔들기 그림과 같은 각)·`<보석 티어>-menu.webp`(64px × 13각 띠). 큰 칸은 사이트 HDR 길 장을 SDR 화면 값으로 한 번, 1/3로 줄여 한 번 찍은 비에서, 메뉴 칸은 정지 그림 작은 단계와 같은 맞춤에서 HDR 길과 같은 규칙(톤 매핑 전 밝기 1.5~8 사이를 smoothstep으로 1~3배, `ShotJob.boost`)으로 잰다. 흔들기 그림(`ONLY=cubie-sway`)을 다시 찍으면 함께 찍는다.
- **크기**: 배율 지도 합계 641KB(큰 칸 105장 624KB, 메뉴 띠 다섯 17KB), 이 맥 칩용 앱 zip 약 +632KB(9.2MB). 메모리는 HDR일 때 큰 칸 한 장이 1.2MB → 2.5MB(최근 네 장)라 티어표를 연 동안 약 +5MB.
- **숨은 설정**: 강제로 끄기·켜기 `defaults write kr.byb.cubie emblemHdr off|on`(지우기 `defaults delete kr.byb.cubie emblemHdr`, 환경 변수 `CUBIE_EMBLEM_HDR=0|1`이 먼저). 같은 HDR 화면에서 둘을 견줄 때 쓴다.
- **메뉴 엠블럼 미리보기는 2026-11-20 사용자 결정으로 없앴다**: 누구나 켤 수 있는 숨은 설정이라, 지금은 제 화면만 바뀌어도 나중에 랭킹·프로필 공유가 붙으면 남의 눈에 다른 티어로 보일 길이 된다. 앱은 그 설정을 더 읽지 않고, 이미 적어 둔 사용자 설정값을 지우지도 않는다.
- 시험 `EmblemHdrTests`(언제 HDR인지, 화소 셈, 묶은 다이아몬드 그림으로 만든 HDR 그림이 흰색보다 밝은 화소 0.1~5%이고 바탕은 SDR 그대로, 배율 지도 장 수·크기). 배율 셈을 일부러 1배로 두면 실패하는 것을 확인했다.
- **사람이 HDR 맥에서 볼 것**: 헤드리스·스크린샷은 흰색 위 밝기를 담지 못한다. ① 내 티어가 보석 티어일 때 메뉴를 열어 엠블럼 반짝 점이 메뉴 글자(흰색)보다 밝은지 ② 티어표 창 사다리에서 보석 칸을 눌러 큰 칸 반짝임이 흰 글자보다 밝은지 ③ `emblemHdr off`로 견주어 생김새는 같고 반짝임만 다른지 ④ 큰 칸이 흔들릴 때 반짝임이 깜빡이거나 화면 밝기가 출렁이지 않는지.
- **Cubie 새 판이 필요하다**(티어표 창·메뉴는 앱이 그린다).
- **흔들기 끊김(0.11.0 뒤 고침)**: 「HDR은 되는데 움직임이 좀 끊긴다」. 원인은 큰 칸이 각이 바뀔 때마다 주 스레드에서 그림을 풀고 HDR로 만든 것(이 맥 릴리스 빌드 한 장 가운데 8.6ms·최대 15.6ms, SDR은 풀기만 2.7ms)과, 사다리 칸이 3초마다 주 스레드에서 띠를 풀고 어둡게 칠한 것(5~22ms)이다. 재기 모드에서 흔드는 동안 한 장 갱신은 HDR 켜기 평균 1.4~2.4ms·최대 11~17.7ms, 3초 60번 가운데 7~15번이 120Hz 예산 7.1ms를 넘었다. 고친 것: 각도 그림 창고 `CubieCore/SwayFrames.swift`(보이는 두 장과 앞뒤 두 장씩, 많아야 여섯 장)가 원하는 장만 백그라운드 줄(`EmblemArt.work`)에서 만들고, 흔드는 길은 만든 그림만 꺼낸다. 티어를 고르면 정면 SDR 한 장을 바로 보이고 HDR 그림이 오는 대로 같은 자리에 바꿔 낀다. 사다리 칸은 다음 칸 띠를 미리 만든다. 고친 뒤 HDR 켜기·끄기 모두 평균 0.1~0.2ms·최대 1ms 안쪽, 예산 넘김 0번. 메모리는 재기 모드 footprint가 고치기 전과 같은 약 52MB(큰 칸 그림은 최근 네 장에서 많아야 여섯 장으로, HDR이면 10MB → 15MB까지, 사다리 띠 한 장 3.4MB를 미리 둔다). 메뉴 칸은 13장을 메뉴를 열 때 한 번 만들고 흔드는 동안은 꺼내기만 해서 같은 원인이 아니었다(HDR 최대 1.3ms). 함께 고친 것: 창이 놓인 화면을 모를 때 `NSScreen.main`으로 넘겨짚지 않고 SDR로 두며, 창이 화면에 나오거나 메뉴 창이 다른 화면에 놓이면 다시 정한다. 화면 감시는 창의 화면이나 그 화면의 밝기 한도가 바뀔 때만 다시 정한다(화면 설정 알림은 이 맥 내장 화면에서 초당 약 12번 온다). 재기: `CUBIE_DEBUG=1`이나 재기 모드에서 `[cubie] sway hero|menu hdr=… avg=… max=… over7.1=…`(3초마다)·`[cubie] emblem hdr=… screen=…`·`[cubie] ladder sweep … ms=…`, 재기 명령 `place tiers <화면 번호|off>`로 창을 그 화면에 거의 투명하게 둔다(LG에 두면 `hdr=0`, 내장 화면이면 `hdr=1`을 확인했다). 시험 `SwayFramesTests`(흔들기 18초를 흉내 내 50ms에 한 장만 만들어도 빈 장이 없는지, 여섯 장 상한, 흔드는 길·사다리 차례 바꾸기의 소스에 그림 풀기·HDR 셈이 없는지). 미리 두기를 0장으로 하거나 예전 코드면 실패한다.

### 5-17. 스크롤 막대가 내용 폭을 차지할 때(2026-11-20)

- 사용자 지적 「다시보기 버튼이 가리는 것 같아」: 판이 16개인 기록 창에서 줄 끝 「다시 보기」가 「다시 보」까지만 보이고 세로 스크롤 막대에 가렸다. macOS 「스크롤 막대 보기: 항상」이나 마우스를 이은 맥에서는 막대가 겹치지 않고 내용 폭을 15pt 차지하는데(AppKit `.legacy`), 기록 창은 줄 폭을 스크롤 보기 바깥 폭으로 잡았다. 같은 원인으로 티어표·설정 창은 막대가 생겨 문서 보기 폭이 줄어도 다시 배치되지 않아(막대가 문서 보기 자신의 `layout()` 안에서 생겨 다시 배치 표시가 지워졌다) 오른쪽 여백이 거의 없고 사다리 고른 칸 테두리가 막대에 닿았다.
- 고친 것: 공통 `ContentScrollView`(`NativeUI.swift`)가 `tile()` 뒤에 문서 보기를 내용 폭(`contentView` 폭)에 맞추고 폭이 바뀌면 다음 차례에 다시 배치한다(막대가 생기거나 사라짐·막대 설정이 바뀜·창 크기). 기록 창은 줄 폭을 `CubieCore/ScrollContent.swift` `width`로 셈하고(막대가 자리를 차지하고 판이 넘칠 때만 막대 몫을 뺀다), 줄 칸 자리는 `RecordsSheet.rowColumns`가 정한다. 시간 뒤 칸(칩·수·「다시 보기」)은 줄지 않고, 모자라면 때 칸이 줄어든다(320 창에서도 「다시 보기」가 다 들어간다). 사이트 기록 목록은 막대 몫을 뺀 폭 안에 이미 한 줄로 들어가 고칠 것이 없었다.
- 시험 `RecordsSheetTests`(내용 폭 셈, 380·320 창, 때 칸 줄기. 막대 몫을 빼지 않게 하면 실패 확인), 화면 `cube-mini-scrollbar.spec.ts`(헤드리스 Chrome의 `--hide-scrollbars`를 빼고 막대를 보이게 해 380·320에서 단추가 막대 앞 한 줄인지, 줄 폭을 막대만큼 넓히면 실패 확인). 비교판 `docs/cubie-native/compare-windows-records-scroll.webp`(`window-compare.mjs` 장면 `records-scroll`, 판 20개, 네이티브는 `.legacy`, 사이트 WebKit은 자리를 차지하는 막대 꾸밈), 네이티브만 `native-tiers-scroll`·`native-settings-scroll`·`native-settings-custom-scroll`.
- **Cubie 새 판이 필요하다**(세 창은 앱이 그린다).

### 5-18. 보통 창이 열린 동안 Dock·⌘Tab에 나오기, ⌘W로 닫기(2026-11-23)

- 사용자 보고: 기록·티어표·설정 창이 다른 앱 창 뒤로 가면 ⌘Tab으로 고를 수 없어 찾지 못하고 남아 있었다. 앱이 늘 `.accessory`(Info.plist `LSUIElement`)라 Dock·⌘Tab에 안 나왔고, 메인 메뉴가 없어 ⌘W로도 닫히지 않았다.
- 정한 것: 보통 창(네이티브 세 창 `sheets`와 사이트 창 `webWindows`, 최소화한 창 포함)이 하나라도 열린 동안만 `.regular`로 Dock·⌘Tab에 나오고, 모두 닫으면 `.accessory`로 돌아간다. 떠 있는 큐브 창·단축키 표·말풍선은 세지 않는다. 재기 모드(`.prohibited`)는 바꾸지 않는다. 판단은 `CubieCore/AppPresence.swift`(시험 `AppPresenceTests`, 일부러 틀리게 하면 실패 확인), 바꾸기는 `AppDelegate.updatePresence`(두 창 목록이 바뀔 때마다. `.accessory`로는 창 닫기가 끝난 다음 차례에).
- `.regular`인 동안만 앱 메뉴를 건다: 「Cubie」(Cubie 끝내기 ⌘Q), 「창」(닫기 ⌘W·최소화 ⌘M, 키를 받는 보통 창에만, 큐브 창이면 아무것도 안 함). `.accessory`로 돌아갈 때 메뉴를 떼어 큐브 창의 ⌘Q는 예전처럼 앱을 끄지 않는다. 큐브 코어는 ⌘ 조합을 ⌘Z 말고 모두 무시해(`keymap.rs` `resolve_action`) 큐브 키와 부딪치지 않는다. 키 배치 편집기의 키 지정은 지역 감시가 메뉴보다 먼저 받는다. 비활성 메뉴 항목도 단축키를 먹으므로(AppKit, 따로 확인) 「꺼 두기」 대신 메뉴를 떼는 쪽을 골랐다.
- 마지막 보통 창을 닫으면 `.accessory`로 바뀌며 앞 앱(창을 열기 전 쓰던 앱)이 다시 앞으로 온다. 큐브 창에 키가 남지 않는다.
- 확인(번들 id만 바꾼 ad-hoc 사본, `CUBIE_DEBUG=1`의 `[cubie] presence regular|accessory`, `lsappinfo` 앱 종류): 기록 창을 열면 `Foreground`·Dock에 앱 아이콘, 「창 → 닫기」로 닫으면 `UIElement`로 돌아가고 큐브 창은 남음, 최소화한 동안은 `Foreground`, 다시 열면 펼쳐짐. ⌘W 키 자체는 키 입력을 앞 앱에 보내는 도구가 다른 앱에 닿을 수 있어 사람이 본다.
- **Cubie 새 판이 필요하다**.

### 5-19. 읽기 전용 검토가 찾은 것 고치기(2026-11-24)

- **「모든 설정…」 사이트 창을 닫을 때**: 연 때 넣은 앱 저장소 글과 닫을 때 읽은 localStorage를 견주어 사이트에서 바뀐(더해진·지워진) `cube.*` 키만 옮긴다(`CubieCore/WebStoreMerge.swift`, 시험 `WebStoreMergeTests`). 예전에는 통째로 덮어써 창이 열린 동안 네이티브 설정 창에서 바꾼 값이 되돌아갔다. 저장소에 `remove`를 더했다. 사이트 창 제목은 네이티브 설정 창(「Cubie 키 배치·색」)과 Dock·⌘Tab에서 갈리게 「Cubie 모든 설정」.
- **앱 메뉴에 「편집」**(보통 창이 열린 동안만 거는 메뉴, 5-18): 잘라내기 ⌘X·복사 ⌘C·붙여넣기 ⌘V·전체 선택 ⌘A, 표준 동작을 응답 사슬로(target nil). 되돌리기 ⌘Z는 큐브 되돌리기라 두지 않는다. 키 배치 가져오기 글 칸에 붙여넣기가 된다. 보통 창 Esc 닫기는 글 칸에 쓰는 중이면 닫지 않는다(`CubieCore/EscClose.swift`, 시험 `EscCloseTests`). 큐브 창이 키를 받는 동안 ⌘C 등은 메뉴가 먹지만 큐브 코어는 ⌘Z 말고 ⌘ 조합을 쓰지 않아 상관없다.
- **한 판 맞추면 열린 티어표 창도** 지금 보는 크기로 다시 그린다(기록 창만 다시 읽었다).
- **공식 연습 중 「다시 불러오기」**(`NativeCubeWindow.reload`)가 `onReady`로 말풍선을 숨긴 뒤 줄이 그대로라 다시 그리지 않던 것: reload 끝에 연습 말풍선을 다시 그린다.
- **세 창의 칩(`Chip`)과 기록 창 티어 칸(`TierCell`)**: 손쉬운 사용 단추(이름은 제목, 누르기 동작은 칩 동작. 동작 없는 배지는 글), Tab으로 오고 Space·Return·숫자판 Enter로 누르기, 포커스 테두리. 티어 사다리 칸과 같은 방식이고 사다리 칸에도 손쉬운 사용 누르기를 더했다. 보통 창은 Tab 차례를 저절로 다시 셈한다(`autorecalculatesKeyViewLoop`). 남은 것: 키 배치 편집기는 바뀔 때마다 칩을 새로 만들어, 키보드로 누르면 포커스가 창으로 돌아간다.
- **보통 창이 크기·자리를 기억한다**(UserDefaults `CubieWindowFrame.<이름>`, 네이티브 `CubieWindow.<창>`·사이트 `CubieSite.<창>`, `FrameMemory`). 옮기거나 크기를 바꾸거나 닫을 때 저장한다. 처음 열거나 기억한 자리가 화면 밖이면 큐브 창이 있는 화면 가운데(`WindowPlacement.normalWindowFrame`, 시험 넷). AppKit `setFrameAutosaveName`·`setFrameUsingName`은 쓰지 않는다: 화면이 둘인 이 맥에서 내장 화면 (300, 219)에 두고 닫은 창이 다시 열 때 주 화면(LG) (-2002, 109)로 되살아났다. 재기 모드는 화면 밖에 두므로 기억하지 않는다.
- **키 지정 중 설정 창을 닫으면** 편집기의 지역 키 감시를 뗀다(창 닫힘 알림·보기가 창에서 빠질 때).
- **안 보일 때 도는 것 멈추기**: 공식 연습 0.1초 시계는 연습 중이고 포커스가 있을 때만(`PracticeTick`), 기록 창 다시 보기는 창이 가려지거나 최소화되면 멈췄다가 다시 보이면 이어 간다(`AutoPause`, 사람이 멈춘 것은 그대로, `MotionWatch`), 떠 있는 창의 전역 마우스 감시는 큐브를 숨기면 떼고 다시 나오면 건다. 시험 `AutoPauseTests`.
- **설정 슬라이더·색 칸을 끄는 동안**: 바뀔 때마다 큐브 창 전체 다시 읽기(프로필·말풍선 포함)와 키 배치 편집기 다시 만들기가 돌았다. 이제 설정 칸만 다시 보이고, 큐브 창(설정·키 배치만)과 단축키 표는 한 차례에 한 번 다시 읽는다(`CubieCore/Coalescer.swift`, 시험 `CoalescerTests`). 끄는 동안에도 바로 반영된다.
- `ProfileMenuView`는 `@MainActor`로 두고 `MainActor.assumeIsolated`를 걷었다(타이머 안은 그대로).
- 확인용 디버그 명령(`CUBIE_DEBUG=1`, 알림 `kr.byb.cubie.debug`)에 `tiers`·`settings`·`site-settings`·`visible`·`reload`·`practice:<단계 id>`를 더했고 `dump`가 말풍선이 떠 있는지도 찍는다. 시험 앱 확인은 번들 id와 **프로세스 이름까지 바꾼** 사본으로 한다: System Events는 `whose unix id is …`로 고른 프로세스도 이름으로 되짚어, 이름이 같은 「Cubie」면 설치된 앱을 누른다(2026-11-24 이 확인 중 설치된 앱의 「키 배치·색…」이 한 번 눌렸다).
- 실제 앱(시험 사본)에서 확인한 것: 「편집」 메뉴가 「Cubie」와 「창」 사이에 있음, 설정·기록·티어표 창이 큐브 창 화면(내장) 가운데에 처음 뜸, 옮기고 닫았다 다시 열면 그 자리, 사이트 창 제목 「Cubie 모든 설정」과 그 창이 열린 동안 네이티브에서 「색약 친화」로 바꾸고 사이트 창을 닫아도 남음(옮긴 키 0개), 칩·티어 칸이 손쉬운 사용 단추로 읽히고 누르기(AXPress)로 색 묶음·크기가 바뀜, 공식 연습 중 다시 불러와도 말풍선이 떠 있음, 숨기기·보이기에 전역 마우스 감시가 떼어지고 걸림. 확인 못 한 것: Esc·Tab·Space 같은 키 입력(앞 앱에 키를 보내지 않는다), 글 칸 붙여넣기, 한 판 맞춘 뒤 티어표 다시 그리기(맞추려면 키 입력), 다시 보기 저절로 멈춤(시험 기록 없음), 키 지정 중 닫기, 슬라이더 끄는 동안의 다시 읽기 횟수.
- **Cubie 새 판이 필요하다**.

### 5-20. 웹 되돌림 스위치 지우기와 앱 코드 정리(2026-11-25)

사용자에게 보이는 동작은 바꾸지 않는 정리다.

- **웹 되돌림 스위치 둘을 지웠다**: `CUBIE_WEB=1`(웹 큐브 창 `CubeWindow`·다리 `Bridge`·웹 재기 `Measure`)은 앱 저장소를 읽지 않아 켜면 옛 WebKit 기록이 보이고 맞춘 판이 네이티브 기록에 들어가지 않아 되돌림 구실을 못 했다. `CUBIE_WEB_WINDOWS=1`(기록·티어표·설정 사이트 창)은 「모든 설정…」 사이트 창 말고 쓰는 곳이 없었다. 지우기 전 마지막 커밋에 로컬 git 태그 `cubie-web-fallback-last`를 두었다(옛 앱으로 견줄 때 그 태그를 빌드한다). 단축키 표는 늘 앱이 그리고(`KeysPanel`의 웹 갈래 지움), 앱이 여는 사이트 창은 「모든 설정…」 하나다(Esc는 그 창에서 웹 화면 몫, `EscClose.siteSettings`). `PageFreshness`는 사이트 창의 캐시 정책(`load`)만 남겼다(실패 때 저장본·빌드 커밋 비교는 웹 큐브 창만 썼다). `measure-memory.sh`는 네이티브가 기본이고 `--url`·`--web`·`--query`·`--inject`·`--web-windows`를 지웠다(`--native`는 받아만 둔다).

## 6. 윈도우판을 언제 어떻게 낼지

- **Tauri로 먼저**: 몇 주 안에 낼 수 있고 지금 웹 화면을 그대로 쓴다. 메모리는 Edge 웹 화면이라 맥과 비슷하게 무겁다. 네이티브로 옮길 때 껍데기는 Rust라 일부(창·단축키·트레이)를 다시 쓸 수 있다.
- **네이티브로 바로**: 5절 2·3단계를 먼저 해야 해서 늦다. 대신 버리는 코드가 없다.

## 7. 정할 것

- 윈도우판: Tauri로 먼저 낼지, 네이티브 구조가 준비될 때까지 기다릴지.
- 윈도우판을 시험할 PC(사용자 본인이나 동료).
- 윈도우 서명: 처음엔 없이 낼지(SmartScreen 경고), Azure Trusted Signing(월 10달러 안팎)을 붙일지.
- 네이티브 단계를 지금 시작할지(2단계 코어부터), 앱 사용자가 늘면 시작할지.
