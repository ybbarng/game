# 52. Cubie 윈도우판과 플랫폼별 네이티브 앱

> 2026-11-11 사용자: 「큐비 윈도우 버전도 만들 수 있어?」, 「장기적으로는 성능을 고려한 각 플랫폼 네이티브 앱도 고민해 주면 좋겠어. 지금은 용량을 너무 많이 차지하고, 웹에서 오는 성능 하락도 있을 거라고 생각해.」
>
> 이 문서는 HQ 세션의 설계 초안이다. 정할 것은 맨 아래 「정할 것」에 있다.

## 1. 결론부터

- 지금 Cubie의 짐은 디스크가 아니라 **메모리**다. 앱 파일은 4MB인데, 떠 있는 동안 웹 화면 프로세스까지 합쳐 300MB 안팎을 쓴다.
- 장기적으로는 **큐브 계산 코어를 Rust로 한 번 짜고, 큐브 그리기도 Rust(wgpu) 하나로 두고, 플랫폼마다 얇은 네이티브 껍데기**(맥 AppKit, 윈도우 Win32)를 씌우는 구조를 권한다. 예상 메모리는 30~60MB다.
- 바로 갈아타지 않는다. 먼저 맥에서 작은 시제품으로 메모리·CPU가 실제로 줄어드는지 재고, 사이트와 같은 결과를 내는지(섞기·판정·기록) 시험으로 묶은 뒤 옮긴다.
- (2026-11-11 3단계 맥 시제품, 5-2) 네이티브 화면은 가만히·숨김 때 약 40MB(웹 약 170MB), 돌리는 동안 CPU 3~4%(웹 15~18%)였다. 돌리는 순간 메모리는 맥 그래픽 드라이버 몫이 커서 223MB(웹 265~296MB)로 덜 준다. 4단계로 가기를 권한다.
- (2026-11-11 연구, 5-3) 돌리는 동안의 메모리는 맥 드라이버가 GPU로 그리는 프로세스에 붙이는 고정 몫(약 108MB)이라 웹이든 wgpu든 줄지 않는다. 크게 줄이려면 연출을 시스템 합성기에 맡겨야 한다. 지금 웹 앱에서 미니 큐브만 CSS 3D로 그리면 시안 기준 돌리는 동안 265~296MB → 75MB(실제 미니 추정 약 120MB)라 이것을 먼저 권한다. 전환한다면 wgpu 대신 Core Animation 3D(약 25~30MB, 용량 +0.6MB)다.
- (2026-11-11 실험, 5-4) 실제 미니 화면에 CSS 3D 그리기를 실험 주소 `?render=css`로 넣어 쟀다. 돌리는 동안 260MB → 139MB(거울 숨김 261 → 130), 가만히 243 → 98MB, 최고치 합 약 375 → 282MB. GPU 프로세스에 108MB가 붙지 않는다. 대신 돌리는 동안 CPU가 27.6% → 40.1%로 는다(거울 숨김 21.0 → 25.5%).
- (2026-11-12, 5-5) wgpu 대신 Core Animation 3D로 실제 앱 전체(섞기 연출·거울 판·윤곽·2×2~7×7)를 그려 쟀다. 모든 상태 10~17MB(웹 130~300MB), 최고치 17.6MB(웹 약 400MB), 앱 쪽 CPU 돌리는 동안 0.4~0.6%(웹 12~17%, 대신 WindowServer가 약 +10%p), 설치 용량 zip +0.5MB(wgpu는 +3MB). 사용자가 걸린다고 한 설치 용량·최대 메모리가 모두 풀려 **4단계를 이 그리기로 가기를 권한다.** wgpu 경로는 앱에서 뺐다.
- (2026-11-12 4단계, 5-6) 큐브 창을 완전 네이티브로 옮겼다(기본, 되돌림 `CUBIE_WEB=1`). 기록·힌트(사람 해법 포함)·공식 연습·F1 표·다시 보기·축하·소리·기록 옮기기까지 네이티브이고, 기록 창·티어표·설정만 사이트 창이다. 측정 모드 모든 상태 11~32MB(웹 135~291MB), 돌리는 중 CPU 5%(웹 22%, 대부분 소리), 유니버설 zip 2.83MB(0.1.10 1.7MB).
- 윈도우판은 두 길이 있다. 웹 화면을 그대로 쓰는 Tauri로 빨리 내거나, 위 네이티브 구조를 윈도우부터 쓰는 것이다.

## 2. 지금 얼마나 쓰나(2026-11-11, 이 맥, Cubie 0.1.9가 떠 있을 때)

| 프로세스 | 하는 일 | 메모리(footprint) |
|---|---|---|
| Cubie | 앱 껍데기(창·메뉴·단축키) | 약 65MB(RSS) |
| WebKit.WebContent | 웹 큐브 화면(React·three.js) | 128~145MB, 최고 218MB |
| WebKit.GPU | 웹 화면 그리기 | 35~157MB(움직일 때 늘어남) |
| WebKit.Networking | 웹 화면 받기 | 약 14MB(RSS) |

- 합치면 가만히 있을 때 250MB 안팎, 움직일 때 300MB를 넘는다. 「가만히 CPU 0~1%」는 지금도 맞다.
- 디스크는 4MB라 문제가 아니다.
- 같은 날 다시 보니 이 맥의 WebContent는 둘이었다(140MB + 43MB, `launchctl print pid/<Cubie>`로 둘 다 Cubie 소속). 둘째는 한 번 띄운 단축키 표(F1)가 남긴 것으로 보인다(아래 2-3, 재기에서 단축키 표 하나가 약 34MB).

### 2-1. 재는 방법(5절 1단계 「재기」)

`apps/cubie/scripts/measure-memory.sh`(쓰는 법은 `apps/cubie/DEVELOPMENT.md` 「메모리 재기」).

- 앱을 측정 모드(`CUBIE_MEASURE=1`)로 띄운다. 앱은 앞으로 나올 수 없고(.prohibited), 창은 화면 밖에 투명하게 떠 있으며, 메뉴 막대·전역 단축키·업데이트를 켜지 않고 웹 저장소는 비영속이다. 사용자 화면·포커스·기록을 건드리지 않아, 쓰던 Cubie를 켜 둔 채 잰다. 화면 밖 창도 보이는 창처럼 그리게 WebKit의 가려짐 감지만 끈다.
- 시나리오: 켠 직후 → 가만히 1분 → 포커스·섞기·키로 돌리기(거울 보임) → 거울 숨김 → 포커스 없음 → 숨김 → 단축키 표 불러오기·버리기. 상태마다 Cubie와 그 앱 소속 WebKit 서비스(WebContent·GPU·Networking)의 `phys_footprint`를 1초 간격 세 번 평균한다. 창은 기본 크기 96pt, 화면 배율 2.
- 측정 모드의 Cubie 칸(약 18MB)은 메뉴 막대·Sparkle·말풍선 창이 없어 실제 앱(약 47MB)보다 작다. 웹 쪽 수치는 실제 앱과 같다.
- 흔들림: 같은 빌드도 돌리는 중 WebContent가 93~140MB로 오간다(자바스크립트 쓰레기 치우기 시점). 그래서 견줄 때는 가만히 둔 상태(켠 직후·숨긴 뒤)를 주로 보고, 숨긴 뒤는 전·후 빌드를 같은 시나리오로 이어 잰 값을 쓴다.

### 2-2. 무게가 어디서 오나(재기로 가른 것, 단위 MB)

| 무엇 | WebContent | GPU | 가른 방법 |
|---|---|---|---|
| 빈 페이지(WebKit 바닥) | 10 | 17 | 빈 HTML을 같은 방식으로 띄움(Networking 5.6) |
| 사이트 CSS | +2.5 | 0 | CSS만 불러온 페이지 |
| 자바스크립트(React·큐브 화면 코드·three.js) | 약 +45 | 0 | WebGL을 막은 미니(58)에서 CSS 페이지를 뺌. 같은 코드가 Chrome 힙에서는 10.7MB라, 대부분 JSC가 코드(바이트코드·JIT·원본)를 들고 있는 값이다 |
| WebGL 문맥과 3D 장면 | 약 +20 | 약 +15 | WebGL을 막은 미니와 견줌 |
| 소리 엔진(AudioContext, 잔향·잡음 버퍼) | +13~16 | 0 | 첫 키에서 열려 앱을 끌 때까지 남았다. 소리를 막고 견줌 |
| 큐브 워커(섞기 줄·연출 줄) | +5~15 | 0 | 워커를 막고 견줌 |
| 단축키 표(F1)를 한 번 띄운 뒤 | +34(WebContent 하나 더) | +1 | 한 번 띄우면 앱을 끌 때까지 남았다(Networking +2.5) |
| **화면을 계속 다시 그리는 동안** | 0 | **+110~120** | 빈 페이지에서 20px 칸 색만 매 프레임 바꿔도 17 → 126. 큐브 돌리기·떠 있을 때 연출 동안 붙었다가 멈추면 1초 안에 풀린다 |

- 돌리는 동안의 GPU 무게는 창 크기·화면 배율(1로 낮춰도)·안티에일리어싱·테두리 필터·초당 그리기 횟수(30fps로 묶어도)와 상관이 없었다. WKWebView가 화면을 갱신할 때 붙는 엔진 비용이라 웹 코드로는 줄일 수 없다.
- 기록·다시 보기 자료는 Chrome 힙 기준 1MB 안쪽이라 무게가 아니다.

### 2-4. CPU(2026-11-11, 사이트 `game.byb.kr/cube/mini` 830954872, 측정 모드, 두 번 잼)

같은 스크립트(`measure-memory.sh`)가 상태 구간의 처음과 끝에 프로세스마다 누적 CPU 시간(`ps -o time`)을 읽어, 늘어난 CPU 시간 ÷ 지난 시간으로 평균을 낸다. 100%는 코어 하나를 다 쓴 것이다. 표본을 뽑지 않아 구간 안의 짧은 반짝임도 빠지지 않는다. 합계는 Cubie + 그 앱 소속 WebContent·GPU·Networking.

| 상태(구간 길이) | 합계 | Cubie | WebContent | GPU | Networking |
|---|---|---|---|---|---|
| 가만히(떠 있을 때 연출 포함, 60초) | 1.1% / 1.1% | 0.2 | 0.6 | 0.2 | 0 |
| 섞고 키로 돌리는 중, 거울 보임(초당 약 8수, 20초) | 19.8% / 17.9% | 3.1~3.4 | 10.3~11.3 | 4.4~5.1 | 0.1 |
| 돌리는 중, 거울 숨김(6초) | 17.6% / 13.2% | 2.9~3.6 | 6.8~9.1 | 3.6~4.8 | 0~0.2 |
| 포커스 있고 손을 멈춤(10초) | 1.0% / 1.3% | 0 | 0.7~0.8 | 0.3~0.5 | 0 |
| 포커스 없음(10초) | 1.4% / 1.8% | 0.1 | 0.8~1.1 | 0.5~0.6 | 0 |
| 숨김(숨긴 뒤 30초부터 60초) | 0.0% / 0.0% | 0 | 0 | 0 | 0 |

- 대부분의 시간(가만히·숨김)에는 CPU가 짐이 아니다. 「가만히 CPU 0~1%」는 이번에도 맞았고, 숨기면 0이다.
- 돌리는 동안 코어 하나의 15~20%를 쓰고, 그 절반 남짓이 WebContent(자바스크립트·three.js 장면 갱신), 4분의 1이 GPU 프로세스(화면 합성)다. 측정 모드의 키 입력은 0.12초 간격이라 사람이 빠르게 돌릴 때(초당 5~10수)와 비슷하다.
- Cubie 칸(키 입력을 웹으로 넘기기) 3%는 측정 모드 명령 처리가 섞인 값이라 실제 앱과 조금 다를 수 있다.
- 네이티브 시제품(5절 3단계)과 견줄 기준: 돌리는 동안 15~20%, 가만히 약 1%, 숨김 0%.

### 2-5. 남은 무게와 네이티브 판단 자료

- 가만히 있을 때 남는 약 170MB(측정 모드)는 WebKit 바닥 약 33(WebContent·GPU·Networking), 자바스크립트 코드 약 45, WebGL 약 35, 떠 있을 때 연출·숨긴 뒤 30~40초 사이에 붙는 약 8(원인은 아직 모름, 바꾸기 전에는 18), 그리고 쓰레기 치우기 뒤에도 돌려주지 않은 힙이다.
- 돌리는 동안 붙는 GPU 110~120MB는 WKWebView에서 화면을 갱신하는 한 피할 수 없다. 네이티브 그리기(Metal)라면 이 값이 큐브 장면의 버퍼 몇 MB로 준다. 5절 3단계 맥 시제품은 이 값과 가만히 있을 때 합계를 이 스크립트와 같은 상태로 재어 견준다.

## 3. 웹 화면이 지금 해 주는 것(옮기면 잃거나 다시 만들 것)

- **한 벌 코드**: 큐브 상태·돌리기·섞기·키 배치·힌트(OLL·PLL 알아보기)·티어·다시 보기·공식 연습이 사이트와 같은 TypeScript 코드다. 사이트와 앱의 결과가 어긋날 일이 없다.
- **판 없이 고치기**: 큐브 화면은 사이트에서 불러오므로, 오늘처럼 테두리·키 그림을 고치면 앱 판을 내지 않아도 바로 들어간다.
- **기록 저장**: 기록·다시 보기는 지금 웹 저장소(localStorage)에 있다.

네이티브로 가면 셋 다 대가가 생긴다. 특히 첫째가 중요하다. 사이트 머리글이 「누구든 공정하게」라서, 앱에서 맞춘 기록을 나중에 순위에 올리려면 사이트와 **같은 섞기·같은 판정**을 내야 한다.

## 4. 고른 구조와 대안

### 권하는 구조: Rust 코어 + Rust 그리기 + 얇은 네이티브 껍데기

- **코어(Rust)**: 큐브 상태와 돌리기, 섞기 만들기(같은 씨앗이면 사이트와 같은 섞기), 다 맞췄는지 판정, OLL·PLL 상황 알아보기와 힌트 공식 고르기, 티어 계산, 다시 보기 기록 형식, 키 배치.
- **그리기(Rust, wgpu)**: 맥은 Metal, 윈도우는 Direct3D 12로 그린다. 7×7도 조각이 많지 않아 가볍다. 가만히 있을 때는 그리지 않는다.
- **껍데기(플랫폼마다)**: 맥은 지금 Swift 앱을 그대로 두고 웹 화면 자리에 Rust 그리기 화면을 끼운다(손으로 쓴 C ABI로 연결, UniFFI는 의존을 늘려 쓰지 않는다. 5-2). 윈도우는 Rust로 투명 창, 전역 단축키, 트레이 아이콘, 업데이트를 만든다.
- **어긋남 막기**: 사이트 TypeScript 엔진과 Rust 코어가 같은 결과를 내는지 같은 시험 자료(JSON: 섞기 씨앗 → 섞기, 수 목록 → 상태, 상태 → 힌트·판정)로 양쪽에서 돌린다. CI에서 어긋나면 깨진다.
- **웹에 남기는 것**: 해법 익히기, 대결(같이 하기), 큐브 모양 만들기 같은 큰 화면은 사이트로 연다. 앱은 지금처럼 혼자 하기 전용이다(고정 규칙 5절).

| 안 | 장점 | 단점 |
|---|---|---|
| 지금 그대로(맥 WKWebView, 윈도우 Tauri) | 한 벌 코드, 판 없이 고치기 | 메모리 250~300MB가 그대로 |

### 5-2. 3단계 맥 시제품(2026-11-11)

**결론**: 대부분의 시간(가만히·포커스 없음·숨김)에 메모리가 약 170MB에서 약 40MB로 4분의 1이 되고, 돌리는 동안 CPU가 코어의 15~18%에서 3~4%로 줄었다. 돌리는 동안의 메모리는 덜 준다(웹 265~296MB → 네이티브 약 223MB). 그 몫 대부분은 맥의 그래픽 드라이버가 GPU에 계속 그리기를 보내는 동안 붙이는 메모리라, 웹(WebKit GPU 프로세스)이든 네이티브든 생긴다. 그래서 **4단계(맥 옮기기)로 가기를 권한다.** 다만 돌리는 동안 메모리는 아래 「남은 것」 첫 줄을 먼저 본다.

- 같은 그리기가 창 없는 벤치에서는 146MB, 앱 측정에서는 223MB였다(앱 실행 파일이 새 라이브러리인 것은 확인함). 원인은 아직 모른다(아래 「남은 것」).

### 5-3. 최대 메모리·설치 용량 연구(2026-11-11)

> 사용자(시제품을 써 본 뒤): 「다른 건 좋은데 1. 설치 용량 증가 2. 메모리 최대 사용량은 거의 동일 이 두 점이 조금 걸리네.」, 「큐브 사용성 자체는 거의 동일」, 「메모리를 줄일 방법을 연구해줘. 지금 정도면, 전환하는 비용이 크다고 판단할 수 있을 것 같아.」 그래서 돌리는 동안의 최대 메모리를 먼저, 네이티브 전환 없이 지금 웹 앱에서 되는 길도 같은 무게로 봤다. 설치 용량은 빌드 설정 표만.

**결론**

- 돌리는 동안 붙는 메모리는 **맥 그래픽 드라이버가 「최근 1~3초 안에 GPU 그리기를 보낸 프로세스」에 붙이는 고정 몫 약 108MB**다. 초당 장 수(1장이어도 같다)·그릴 크기(16px~1024px)·MSAA·드로어블 수와 상관이 없다. 그래서 우리 프로세스에서 GPU로 그리는 한(웹 WebGL, wgpu, 맨 Metal 모두) 돌리는 동안 최대 메모리는 크게 줄지 않는다. 프레임·크기를 줄이는 안은 모두 효과가 0~4MB였다.
- 크게 줄이는 길은 하나다. **돌리는 연출을 시스템 합성기(Core Animation, 실제 합성은 WindowServer)에 맡겨, 우리 프로세스가 GPU 그리기를 보내지 않게 한다.** 웹에서는 CSS 3D(`transform-style: preserve-3d`) + Web Animations, 네이티브에서는 `CATransformLayer`다. 둘 다 돌리는 동안 앱 쪽에 드라이버 몫이 붙지 않았다(시안 기준 웹 합계 75MB, 네이티브 약 11MB).
- **지금 웹 앱에서 바로 할 수 있는 것: 미니 화면 큐브를 three.js(WebGL) 대신 CSS 3D로 그리기.** 사이트 배포만으로 앱에 들어간다(앱 새 판 필요 없음). 시안은 돌리는 동안 265~296MB → 75MB였고, 실제 미니의 자바스크립트(React·소리·워커)를 더하면 약 120MB로 본다(추정). 단, 화면에 계속 바뀌는 글자 같은 **다시 그리기가 있으면 웹 GPU 프로세스가 그것을 GPU로 그려 108MB가 다시 붙는다**(0.1초마다 바뀌는 시간 글자로 확인). 지금 미니에는 맞추는 동안 계속 바뀌는 글자가 없다.
- **전환한다면: wgpu 대신 Core Animation 3D + Rust 코어.** 모든 상태 약 25~30MB(추정, 앱 껍데기 포함), 설치 용량은 유니버설 실행 파일 +약 0.6MB(wgpu는 +7MB). 글자를 0.1초마다 바꿔도 드라이버 몫이 붙지 않는다(앱이 CPU로 그린다). 대신 생김새는 면마다 평평한 색이 되고(조명·광택은 흉내), 윈도우판은 그 나라 합성기(DirectComposition)로 따로 그려야 한다.
- wgpu를 유지하면 돌리는 동안 151MB, 켤 때 첫 장 최고 220MB다. Metal을 직접 써도 평소 값은 같고(같은 드라이버 몫), 켤 때 최고만 약 80MB 낮아진다.

#### 생김새와 확인

- CSS 3D·Core Animation 3D 모두 면마다 평평한 색이다. 사이트 장면의 하늘빛·세 방향 빛·광택은 없고, 면 방향마다 정한 밝기나 그라데이션으로 흉내 낸다. 둥근 조각·스티커는 모서리 둥글기로 된다.
- 실루엣 윤곽: 웹은 3D가 아닌 바깥 상자에 사이트와 같은 `drop-shadow` 네 겹 + 그림자를 걸면 된다(3D 층에 걸면 Core Animation이 무시한다는 경고가 난다). 걸어도 돌리는 동안 GPU 프로세스는 18MB 그대로였다(필터를 합성기가 적용). 네이티브는 그림자 하나씩 든 층을 네 겹 감싸 같은 꼴을 만든다.
- 확인 방법의 한계: Playwright WebKit 화면 없는 모드와 `WKWebView.takeSnapshot`은 3D를 납작하게 찍었다(아주 단순한 정육면체도 같음). Chrome에서는 시안이 제대로 그려지고 돌아간다. WKWebView에서는 WebKit이 UI 프로세스에 `CATransformLayer`를 만든 것(단순 정육면체 1개, 시안 약 85개)으로 3D 합성을 확인했고, 실제 앱 창의 모습은 아래 명령으로 사람이 본다.

| 코어만(wgpu 없음: Metal 직접·Core Animation 길의 Rust 몫), 유니버설 | 약 1.2(칩마다 +0.31 잼) | 약 4.6 | 약 2.0(추정) |

- 크기를 줄이는 빌드 설정은 이미 다 들어 있다. fat LTO·codegen-units 1·panic abort는 Cargo.toml에, 기호 지우기는 `build.sh`의 `strip -rSTx`, `-dead_strip`은 SwiftPM release 링크가 기본으로 건다. opt-level "s"·"z"는 오히려 실행 파일이 0.7MB 커지고 zip은 같았다.
- panic abort는 FFI에 안전하다. C 함수 밖으로 되감기(unwind)가 넘어가지 않고 그 자리에서 끝난다(Rust 1.81부터 `extern "C"` 밖으로 나가는 패닉은 어차피 끝낸다).
- wgpu 기능은 이미 최소다(`metal`·`wgsl`·`std`·`parking_lot`). WGSL 읽기를 빼려면 셰이더를 MSL로 직접 주는 실험 기능(passthrough)이 필요하고 naga의 MSL 출력은 남아 시도하지 않았다.
- 크기 대부분(칩마다 약 3.3MB)은 wgpu·naga다. Metal 직접은 wgpu를 빼므로 코어만 줄에 가깝지만(셰이더 미리 번역 `.metallib`은 이 맥에 Metal Toolchain이 없어 `xcodebuild -downloadComponent MetalToolchain`이 필요하다. 받지 않았다), 메모리는 평소 값이 같아 시제품을 만들지 않았다.
- `swift build`는 정적 라이브러리가 바뀐 것을 몰라 다시 링크하지 않을 수 있다. 크기를 견줄 때는 `.build/<칩>-apple-macosx/release/Cubie`를 지우고 빌드했다.

### 5-4. 실제 미니 화면에서 CSS 3D 그리기 실험(2026-11-11)

> 사용자: 「메모리를 줄일 방법을 연구해줘. 지금 정도면, 전환하는 비용이 크다고 판단할 수 있을 것 같아.」 그래서 5-3의 ①(웹 그대로, 미니 큐브만 CSS 3D)을 실제 미니 코드 위에 실험 주소로 넣고 같은 측정 모드로 쟀다. 기본은 그대로 three.js다.

**결론**

- 돌리는 동안 메모리가 **260MB → 139MB**(거울 숨김 261 → 130), 가만히 **243 → 98MB**로 준다. GPU 프로세스는 돌리는 동안 151 → 22MB로, 5-3의 드라이버 몫 108MB가 붙지 않는다. 5-3의 추정(약 120MB)보다 20MB쯤 높은 것은 앱(UI) 프로세스가 Core Animation 층을 들고 있는 몫(Cubie 칸 17 → 26~27MB)과 WebContent의 조각 상자(DOM)다.
- 대신 **돌리는 동안 CPU가 늘었다**: 27.6% → 40.1%(거울 보임), 21.0% → 25.5%(거울 숨김). 0.12초마다 한 수씩 200수를 두는 측정이라 실제 손보다 빠르다. 가만히·포커스 없음·숨김은 둘 다 0~2%로 같다.
- 맞추는 동안 계속 바뀌는 글자는 미니 화면에 없다. 바뀌는 표시는 아래 목록처럼 한 번씩만 칠한다.
- 기본값으로 바꿀지는 사용자가 실제 앱 창으로 생김새를 본 뒤 정한다(아래 「의견」).

**넣은 것**(`apps/web/src/cube/view/css-cube-view.ts`, 계산 `css-math.ts`, 미니 화면 `MiniCubeApp.tsx`의 `miniRenderCss`)

- `?render=css`일 때만 three.js 대신 CSS 3D 장면(`CssCubeView`)을 만든다. 미니 화면·섞기 연출은 두 장면이 함께 맞춘 꼴 `CubeScene`(`view/types.ts`)만 부른다. 맞춤 판정·키 입력·기록은 그대로다.
- 2×2~7×7, 수 돌리기(그 층 조각을 돌림 상자에 옮겨 `transform`만 Web Animations로, 끝나면 조각 행렬에 굳힌다), 섞기 연출 셋(하나씩 빠르게·짧은 연출 한 바퀴·바로), 실루엣 윤곽(3D가 아닌 바깥 상자에 지금과 같은 흐림 없는 선 + 그림자), 거울 판, 앱에 알리는 누름 자리(`hitRects`).
- 카메라·거울 판 자리는 three.js 장면과 같은 식(세로 시야각 30°, `mirrorPanels`·`mirrorFrame`)이라 같은 창에서 큐브가 같은 크기·자리에 온다.
- **돌리는 동안 다시 칠하지 않는다.** 칸 색은 `setStickers`(섞기·판 바꾸기)에서만 칠한다. 거울 판은 판마다 스티커를 한 벌 더 두고 판 평면으로 눌러(`mirrorFlatten`) 같은 행렬로 함께 돌린다. 수마다 판 칸 색을 바꾸면 그것이 다시 칠하기라 108MB가 다시 붙는다.
- 조각은 겉면만 둔다(3×3 층 54장). 속은 층을 돌리는 동안만 자르는 면에 검은 판 두 장(도는 쪽·나머지 쪽)으로 막는다. 처음에는 조각마다 여섯 면(156장)을 두었는데 CPU가 44.8%였다. 거울 판이 안 보이면 판 쪽 조각은 돌리지 않고 끝난 자리만 쓴다.
- 시험: 단위 `css-math.test.ts`(CSS 좌표 바꾸기, 투영이 카메라와 같은지, 거울상 자리가 `mirrorCells`와 같은지), `css-cube-view.test.ts`(2×2~7×7에서 장면이 계산한 칸이 스티커 계산과 같은지, 상자 수, 누름 자리). 화면 시험 `e2e/cube-mini-css.spec.ts`(연출을 켜고 섞기 → 거울·누름 자리 넷 → 키로 거꾸로 맞춤 → 장면도 맞춘 모양, 기다리기는 모두 조건).

**상태별 견주기**(측정 모드 `measure-memory.sh`, 창 96pt·배율 2, 3×3, 단위 MB. CSS 3D는 `--query render=css`. 같은 날 같은 앱 빌드)

- CSS 3D의 GPU 최고 156MB는 측정 표본(1초 간격)에는 한 번도 잡히지 않은 짧은 순간이다. 5-3 시안도 켤 때 첫 그리기 1~2초에 GPU 128MB가 잠깐 생겼다. 층 내용(스티커 그림)을 처음 칠할 때로 본다(가르지 않았다).
- CPU가 느는 곳은 앱(UI) 프로세스(Cubie 칸 4.9 → 15.2%)다. 수마다 층 묶음을 옮기는 일(돌림 상자로 옮기고 되돌리기, 행렬 쓰기)을 WebKit이 UI 프로세스의 Core Animation에 보내는 몫으로 본다(5-3 시안에서도 9~10%). 남은 줄일 거리: 조각 상자를 옮기지 않고 조각마다 돌림 행렬을 붙이기, 거울 판 세 벌 대신 보이는 면 칸만 두기.

**맞추는 동안 바뀌는 표시**(다시 칠하면 GPU 프로세스가 그려 몇 초 동안 108MB가 붙는다)

- 맞추는 동안 계속 바뀌는 글자·숫자: **없다**. 시간·수는 화면에 내지 않는다(`FocusClock`은 재기만 한다).
- 한 번씩 바뀌는 것: 다 맞춘 순간의 축하(시간 숫자, 약 2.4초 페이드), 힌트 창(앱 말풍선이 없거나 넉넉한 창일 때만 창 안, 힌트를 부를 때마다), 공식 연습 창 안 카드(넉넉한 창이나 옛 앱일 때, 키마다 차례·콤보·공식 칸이 바뀜), 공식 연습 ✓, 섞기·판 바꾸기의 칸 색(`setStickers`). 앱 말풍선으로 가는 힌트·연습 글은 앱이 그린다.
- 장면 안: 수마다 칸 색을 바꾸지 않는다(위 「넣은 것」).

**생김새**

- Chromium(시스템 Chrome, 배율 2, 200×200)으로 바탕 넷(#000·어두운 회색·흰색·사진) × 떠 있음·맞추는 중(거울 보임), 3×3·5×5를 three.js와 나란히 찍었다. 같은 자리·크기, 실루엣 윤곽·거울 판 모두 같게 나온다. 다른 점: 조명·광택이 없어 면마다 평평한 색(스티커에 옅은 비스듬한 빛 띠), 조각 모서리가 덜 둥글다, 검은 바탕에서 조각 사이에 아주 옅은 이음매가 보일 때가 있다. 층을 돌리는 도중(R·M)도 속이 검은 판으로 막혀 보인다.
- **WebKit(Playwright 화면 없는 모드)은 이번에도 3D를 납작하게 찍었다**(앞면 하나만 평면으로, 거울 판도 납작). 5-3과 같은 한계라 앱 창의 실제 모습은 아래 명령으로 사람이 본다.

**못 다룬 것**

- 기록 창의 다시 보기(`?view=records`)는 그대로 three.js다. 장면이 따로 열리는 창이라 이번 측정에 들지 않는다.
- 끌어 둘러보기·밀기·칸 표시는 없다(앱은 마우스 둘러보기를 끄고, 미니 화면은 칸 표시를 쓰지 않는다). 브라우저에서 연 미니 화면도 `?render=css`면 끌어 돌리기가 없다.
- 스티커 없는 모양·가린 색 설정은 받지만 눈으로 견주지 않았다. 4×4 이상은 단위 시험(상태)과 5×5 스크린샷만 봤고, 6×6·7×7 메모리·CPU는 재지 않았다(3×3만).
- 앱 창(WKWebView)의 실제 3D 모습은 사람이 위 명령으로 확인해야 한다.

**의견: 기본값으로 바꿀지**

- 장점: 돌리는 동안 메모리 약 −120MB(260 → 139), 가만히 −145MB, 최고치 합 약 −95MB. 앱 새 판 없이 사이트 배포만으로 들어간다. 네이티브 전환(4단계)보다 비용이 훨씬 작다.
- 단점: 돌리는 동안 CPU +5~13%p(맞추는 동안만, 가만히는 같다), 조명·광택이 없는 평평한 생김새, 기록 창 다시 보기와 두 갈래 그리기 코드를 함께 지켜야 한다. 앱 엔진에서의 생김새를 아직 사람이 보지 않았다.
- 권함: 사용자가 실제 앱 창으로 `?render=css`를 써 보고 생김새·손맛이 괜찮으면 미니 화면 기본을 CSS 3D로 바꾸고(three.js는 둘러보기가 필요한 브라우저 미니에만 남기거나 지움), 그 뒤 CPU 줄이기(조각마다 돌림 행렬)를 한 번 더 해 본다. 생김새가 아쉬우면 지금 그대로 두고 전환 판단은 5-3 ②(Core Animation 3D)로 넘긴다.

### 5-5. Core Animation 3D 네이티브 그리기를 실제 앱 전체로(2026-11-12)

> 사용자(5-4 CSS 3D 실험의 메모리 139MB·CPU 40%를 보고): 「웹사이트를 렌더해서 그렇고, 그래픽을 네이티브로 다 새로 만들면 괜찮지 않을까?」. 앞서 걸린다고 한 것은 「설치 용량 증가」와 「메모리 최대 사용량이 거의 동일」이었다. 그래서 5-2의 wgpu 그리기를 Core Animation 3D(`CATransformLayer` + `CALayer`)로 바꿔, 실제 앱(메뉴·키·섞기 연출·거울 판·윤곽까지)으로 같은 측정을 했다.

**결론**

- **두 걱정이 모두 풀린다.** 메모리 최대치가 웹 약 400MB(프로세스마다 최고치 합) → **17.6MB**, 돌리는 동안 294~300MB → **17MB**, 가만히 261MB → **10.5MB**다. 앱 프로세스는 GPU로 그리기를 보내지 않아 드라이버 몫(108MB, 5-3)이 붙지 않는다. 설치 용량은 wgpu를 빼서 유니버설 실행 파일 7.67MB → **1.67MB**(지금 0.1.9의 0.6MB보다 +1.1MB), zip 4.72MB → **2.18MB**(+0.5MB)다.
- **CPU**: 앱 쪽은 돌리는 동안 **0.4~0.6%**(웹 12~17%, wgpu 2~3%). 대신 실제 합성은 WindowServer가 하므로 그쪽에 몫이 생긴다. 화면에 띄워 같이 재 보니 돌리는 동안 WindowServer가 바탕보다 약 +7~14%p(웹은 +13~20%p) 늘었다. 다른 앱 화면 변화가 섞여 흔들림이 크고(바탕 23~33%) 한 번씩만 쟀다. 합쳐도 웹보다 작다.
- 생김새는 웹 three.js와 같은 자리·크기·윤곽·거울 판으로 나온다. 조명·광택은 스티커에 미리 그린 옅은 빛 띠로 흉내 낸다(5-4 CSS 3D와 같은 수준).
- **4단계(맥 옮기기)를 이 그리기로 가기를 권한다.** wgpu 경로는 앱에서 뺐다(아래 「wgpu 경로」).

**의견: 4단계를 이 그리기로**

- 장점: 모든 상태 10~17MB(웹 130~300MB, wgpu 34~151MB, CSS 3D 98~139MB), 최고치 17.6MB, 앱 쪽 CPU 1% 안, 설치 용량 +0.5MB(zip). 그리기 코드가 Swift 수백 줄이라 4단계 옮기기(말풍선·메뉴·키 그림)가 같은 AppKit 안에서 이어진다.
- 단점: 조명·광택은 흉내(웹 CSS 3D와 같은 수준), 윈도우판은 그리기를 따로 만들어야 한다(DirectComposition 같은 그 나라 합성기, 코어 한 판 C ABI는 같이 씀). 돌리는 동안 WindowServer 몫(약 +10%p)은 남는다.
- 다음 일: 사용자가 실제 창으로 생김새·손맛을 보고 괜찮으면 4단계(기록 옮기기·힌트·공식 연습·단축키 표·사용자 배치)를 이 그리기 위에서 시작한다. 그 전에 윤곽 그림자 겹을 줄였을 때 WindowServer CPU가 얼마나 주는지 한 번 재 본다.

### 5-6. 4단계 완전 네이티브로 옮기기(2026-11-12)

> 사용자: 「완전 네이티브로 만들어서 메모리 사용량 측정 필요」, F2L 전 힌트는 「사람 해법 계산도 Rust로 옮기기」. 그리기는 5-5의 Core Animation 3D, 계산은 Rust 코어(사이트와 공통 시험 자료로 어긋남 0)가 맡는다. 앱은 간단한 혼자 하기 전용이라(고정 규칙 5절) 큰 화면(기록 창·티어표·설정·배우기)은 사이트 창으로 남겨도 된다.

#### 짜임

- **스위치**: 기본이 네이티브 화면이다. 되돌림은 `CUBIE_WEB=1`(예전 웹 큐브 창 그대로, 사이트 판 비교·연결 없음 화면까지). 예전 확인용 `CUBIE_NATIVE=1`은 이제 기본과 같다.
- **앱 껍데기**: `AppDelegate`(메뉴·단축키·말풍선·단축키 표·업데이트·사이트 창)는 `CubeSurface` 약속만 본다. 창 다루기(자리 기억·끌기·핀치·빈 곳 넘기기)는 두 화면이 `FloatingWindow`를 함께 쓴다.
- **네이티브 화면**(`NativeCubeWindow`): 포커스 시계·기록 책·힌트 제한·떠 있을 때 움직임·축하·소리·프로필. 계산은 모두 코어 C ABI(`native/cubie-native/src/ffi_game.rs`·`ffi_records.rs`, 머리 파일 `cubie_native.h`).
- **코어 이식**(`native/cube-core`, 브랜치 `cubie-core-human`을 합침): 한 판 세션 `session.rs`(이정표 `progress.rs`, 흐름 콤보 `combo.rs`), 사람 해법 `human.rs`(`solve_cfop`·`solve_advanced2`), 힌트 고르기 `hint.rs`, 키캡 `keys/route.rs`, 공식 연습 진행기 `practice.rs`. 공통 시험 자료 `fixtures/session.json`(13판·467차례), `hint.json`(124), `keycaps.json`(2,019수), `practice.json`(1,329) 모두 어긋남 0. CI `rust` 작업의 조건에 새 기준 파일(`packages/cube-ai/`, `solve-session.ts`, `flow/combo.ts`, `practice/`, `keys/move-keys·reach.ts`, `mini/practice.ts`, `algs/store.ts`)을 더했다.
- **저장**: UserDefaults `store.<키>`에 사이트 localStorage와 같은 키·같은 JSON 글. 기록 창·티어표·설정·(`CUBIE_WEB=1`의) 단축키 표 같은 사이트 창에는 문서 시작 때 그 글을 넣고(`AppDelegate.storeScript`), 설정 창을 닫으면 그 창의 `cube.*` 글(앱이 쓰는 `cube.mini.*` 빼고)을 읽어 온다. 기록을 남기면 열린 기록 창·티어표에도 넣는다.
- **기록 옮기기**: 처음 띄울 때 `~/Library/WebKit/kr.byb.cubie/WebsiteData/Default/<출처>/<출처>/LocalStorage/localstorage.sqlite3`를 읽기 전용으로 열어(출처 파일에 사이트 호스트가 든 폴더만) `cube.`로 시작하는 키를 같은 글 그대로 옮긴다. 웹 저장소는 지우지 않고, 표시 `cubie.migrated.v1`(옮긴 때·키)을 남겨 다시 하지 않는다. 네이티브에 이미 있는 키는 덮지 않는다. 이 맥의 웹 저장소에는 `cube.mini.v1`(40KB)·`cube.mini.profile.v1`·`cube.mini.practice.v1`이 있었다(키 이름과 길이만 봄).

#### 웹과 다르게 한 것(일부러)

- 힌트·공식 연습은 창 크기와 상관없이 늘 큐브 옆 말풍선이다(웹은 짧은 변 240px 이상이면 창 안 카드). 앱 창 안에 글을 그리면 큐브와 겹치고, 말풍선이 이미 있다.
- 다시 볼 판이 없을 때 홈 시연(사람 해법 풀이) 대신 조금 섞었다 되돌린다. 사이트도 시연이 없는 크기에서는 이 길로 간다.
- 단축키 표의 칸은 면 색을 테두리로만 보인다(웹은 칸 바탕을 옅게 칠한다). 가운데 층·큐브 돌리기(M′·x 등)는 테두리 색이 없다(웹은 빌린 면 색 띠). 칸 글은 코어 `keys::table`이 사이트 `KeyboardMap` 「모두」와 같게 만든다(3×3 「두 손」 X·. = M′, 큰 큐브에서 못 쓰는 M′·M은 흐리게, Alt 줄, ↑ 처음 각도). 같은지는 공통 자료 `fixtures/keytable.json`(두 손·표기·사용자 × 2~7)으로 본다(2026-11-12). 줄이 넷인 칸(Alt와 Alt+Shift가 다 있는 사용자 배치)은 글꼴을 줄여 칸 안에 넣는다(웹은 넘치면 잘린다).
- 소리는 사이트와 같은 모양을 처음 쓸 때 PCM으로 만들어 두고 `NSSound`로 낸다(돌리기는 여섯 벌을 돌려 씀, 울림 없음). 웹은 수마다 새로 합성했다.
- 3D로 돌린 층(조각 겉면 몸통·스티커·거울 판과 유리·돌리는 동안 자르는 면 판)은 곧은 가장자리 다듬기(`allowsEdgeAntialiasing`, 네 변)를 켠다(`CACubeView.smoothEdges`). Core Animation은 기본으로 둥근 모서리만 다듬고 곧은 변은 다듬지 않아, 사용자가 「대각선 안티알리어싱이 애매하고 조금 계단처럼 보인다」고 했다(2026-11-12. 웹과 나란히 띄워 보면 차이는 크지 않다고 했고, 메모리·성능 부하가 크면 되돌리기로 함). 잰 값(`measure-memory.sh --native`, 96pt): 메모리는 상태마다 −1.1~+0.8MB(가장 늘어난 공식 연습 중 29.9 → 30.7MB), 돌리는 중 CPU는 거울 보임 3.1 → 3.6%, 거울 숨김 3.5 → 3.2%, 공식 연습 2.0 → 2.6%, 가만히·숨김은 그대로 0%. 되돌릴 기준(어느 상태든 5MB 넘게, 돌리는 중 2%p 넘게)보다 작아 그대로 둔다. 화면 밖 스크린샷(`CARenderer`)은 설정 전에도 대각선을 다듬어 그려 전후가 거의 같다(192×192 중 5픽셀 다름, `docs/cubie-native/compare-edges.webp`). 실제 창(WindowServer 합성)에서 나아졌는지는 사용자가 본다.

| 최고(프로세스마다 최고치 합) | 약 423(Cubie 20.6·WebContent 139.2·GPU 249.4·Net 13.7) | Cubie 37.6(기록 창을 연 동안 GPU 135.1 따로) | | |

- 대부분의 시간(가만히·포커스 없음·숨김)에 웹 172~263MB → 네이티브 11~25MB, 돌리는 중 289~291 → 24~25MB다. 큐브 창만 쓰는 동안은 WebKit 프로세스가 하나도 뜨지 않는다.
- 네이티브가 켠 직후 10.9MB에서 섞고 돌린 뒤 23~25MB로 느는 것은 코어 표(3×3 2단계 섞기 표, 사람 해법 거리 표는 힌트를 볼 때)와 소리(CoreAudio, 아래)다. 공식 연습을 열면 연습 자료로 약 +3MB. 앱을 끌 때까지 30MB 안쪽에 머문다.
- 기록 창·티어표·설정은 사이트 창이라 여는 동안 WebKit(WebContent 약 40·GPU 약 20·Networking 약 8MB)이 붙는다. 창을 닫으면 WebContent·Networking은 곧 끝나고, GPU 프로세스는 잠시 남았다가 끝난다.
- CPU(앱 프로세스 기준, WindowServer 합성은 빼고): 돌리는 동안 22% → 5.3%. 5-5의 0.4%보다 늘었는데, 돌리는 동안 앱을 표본으로 떠 보니(`sample`) 시간이 거의 소리 스레드(`AQConverterThread`·CoreAudio IO)에 있었다. 0.12초마다 한 수씩 200수 동안 돌리기 소리를 내는 시나리오라 실제 손보다 잦다. 큐브 계산·층 옮기기는 표본에 거의 나오지 않는다. 설정에서 소리를 끄면 이 몫이 없어진다(재지 않음).

#### 앱 크기(유니버설, `build.sh --universal`, 기호 지운 뒤)

| 판 | 실행 파일 | 앱(`du`) | zip(`ditto`) |
|---|---|---|---|
| 0.1.9·0.1.10(웹 화면) | 0.6 | 4.0 | 1.7 |
| 5-5 Core Animation 시제품(코어 한 판) | 1.67 | 5.10 | 2.18 |
| **완전 네이티브(이번)** | **2.92** | **6.45** | **2.83** |

- 5-5보다 실행 파일이 1.25MB 큰 것은 이번에 옮긴 코어(사람 해법·공식 연습 자료·세션·키캡)와 앱 쪽(기록·말풍선·단축키 표·소리)이다. 티어 엠블럼 PNG 열 장이 96KB다.

#### 생김새

- `docs/cubie-native/compare-full.webp`: 바탕 넷(#000·어두운 회색·흰색·사진) × 웹(WebKit, 배율 2) 떠 있을 때·섞인 큐브·맞추는 중(거울)과 네이티브 맞춘 큐브·섞인 큐브·맞추는 중(거울)·돌리는 중·돌리는 중 거울도 따라 돎·다 맞춘 축하(빛 고리와 금색 시간). 윤곽·거울 판 자리는 5-5와 같고, 돌리는 동안 거울 판의 그 층도 같이 돈다.
- `docs/cubie-native/compare-panels.webp`: 네이티브 힌트 말풍선(3×3 섞기, 사람 해법의 십자 단계와 키캡 줄)·공식 연습 말풍선(십자 1/10, 지금 칠 수 밑줄)과 웹 README 공식 연습 그림, 그리고 F1 단축키 표 3×3(J 누름 빛남)·7×7을 네이티브와 웹(사이트 `?view=keys&panel=1`, WebKit 560×300)으로 한 줄에 나란히. 단축키 표는 같은 글·같은 배치, 칸 색 칠하는 방식만 다르다(위 「웹과 다르게 한 것」).
- 다시 만들기: `CUBIE_NATIVE_SHOT=<폴더> apps/cubie/Cubie.app/Contents/MacOS/Cubie` 뒤 `node apps/cubie/scripts/native-compare.mjs <폴더>`. 큐브는 `CARenderer`(Metal 텍스처), 말풍선·단축키 표는 층과 보기 그리기로 PNG를 뜬다. 창을 띄우지 않는다.

#### 판을 내기 전에 사용자가 볼 것

1. 처음 띄운 뒤 메뉴 「기록 보기」에 0.1.10에서 쌓은 기록·티어가 그대로 있는지, 메뉴 맨 위 프로필 이름이 같은지(같은 `cube.mini.profile.v1`을 옮긴다).
2. ⌃⌥⌘C → 키로 돌리기·Enter 섞기·⌫ 되돌리기·←↓ 살짝 보기, Esc로 이전 앱, 다 맞췄을 때 축하·소리·기록 창에 한 줄.
3. `\` 힌트: 3×3 섞은 직후(십자)·F2L 중간·마지막 층에서 말풍선과 키캡 줄, 20초·3번 제한.
4. 메뉴 「공식 연습 ▸」: 단계 하나를 따라 치기·보고 치기(`\`로 펼치기)로 한 판, 판 끝 결과에서 Enter 한 판 더, Esc로 맞추던 판으로.
5. F1 단축키 표: 키를 치면 칸이 빛나는지, 크기를 바꾸면 표도 바뀌는지.
6. 키 배치·색 설정 창에서 배치나 색을 바꾸고 닫으면 큐브에 바로 들어가는지.
7. 끌어 옮기기·핀치·창 크기 메뉴·모니터 떼기, 떠 있을 때(포커스를 잃고 1분 뒤) 내 판 다시 보기와 조금 섞기.
8. 판에 넣을지: 기본이 네이티브라 판을 내면 모든 사용자의 큐브 창이 바뀐다. 웹 쪽 고침이 앱에 바로 들어가던 길(15-26)은 큐브 창에서는 없어지고, 앞으로 큐브 창을 고치면 앱 판을 내야 한다(기록 창·티어표·설정은 지금처럼 사이트 배포로 바뀐다). **2026-11-12 사용자 결정: 받아들인다**(「앞으로 큐브 창 고침도 Cubie 새 판으로만 내기」 응). 0.2.0부터 네이티브로 낸다.

### 5-7. 사이트 미니 화면과 네이티브가 어긋나지 않게(2026-11-12)

> 사용자: 「네이티브가 기존과 모든 기능이 같은가, 앞으로 불일치를 해결할 방법은?」. 0.2.0부터 큐브 창 고침은 Cubie 새 판으로만 나가므로(5-6 「판을 내기 전에」 8), 사이트 미니 화면만 고치면 앱과 조용히 달라진다. 장치는 셋이다.

1. **값은 공통 시험 자료로 견준다.** 판 규칙·섞기·힌트·공식 연습·키캡·F1 표 글자·한 판 기록·티어, 그리고 화면 상태(공식 연습 가리기·F1 표 칸 색)는 코어가 만든 값과 사이트가 만든 값을 같은 자료(`native/cube-core/fixtures/*.json` ↔ `apps/web/src/cube/native/core-fixtures*.ts`)로 본다. 사이트 결과가 바뀌면 사이트 쪽 자료 시험이 먼저 깨지고, 자료를 다시 쓰면 `native/`가 바뀌어 CI `rust` 작업이 돈다.
2. **PR 검사 `native-parity`**(`scripts/native-parity.mjs`, 시험 `native-parity.test.mjs`, CI 작업 `native-parity`를 `ci-ok`가 기다림): PR에서 큐브 창 동작에 닿는 사이트 코드가 바뀌었는데 `apps/cubie/`·`native/` 아래가 하나도 안 바뀌면 실패한다. 네이티브와 상관없는 고침이면 PR 본문에 `네이티브 해당 없음: <이유>` 줄을 적으면 통과한다(목록 표시 `-`나 굵게 `**`가 붙어도 된다, 이유가 비면 안 된다). 본문을 고친 뒤 작업을 다시 돌리면 스크립트가 GitHub API로 지금 본문을 읽는다. 단위 시험 파일만 바뀐 것은 보지 않는다.
   - 검사 대상(스크립트의 `WATCHED`, 사이트 `apps/web/src/` 아래): `cube/mini/`·`app/cube/mini/`(미니 화면), `cube/view/`(그리기·거울 판·카메라), `cube/input/`(키 해석·배치), `cube/keys/` 가운데 `two-hand`·`layout`·`move-keys`·`reach`·`hand-layers`·`key-colors`, `cube/components/KeyboardMap.tsx`(F1 표), `cube/settings.ts`, `cube/scramble-show.ts`, `cube/solve-session.ts`, `cube/flow/combo.ts`, `cube/hero/`(홈 시연·첫 면 색), `cube/practice/`(대결 `versus*` 빼고), `cube/learn/judge.ts`(가리기)·`alg-sets.ts`, `cube/algs/spot.ts`·`store.ts`, `cube/game-sounds.ts`, `game/sound.ts`, `cube/replay-player.ts`, `cube/records.ts`, `cube/tiers/rank.ts`, `cube/native/`(공통 자료의 사이트 쪽).
   - 넣지 않은 것: 기록 창·티어표·설정 창(앱이 사이트 창으로 열어 사이트 배포로 바뀐다), 수 계산 패키지 `packages/cube-*`(CI `rust` 작업과 공통 자료가 값으로 본다). 목록의 파일·폴더를 옮기거나 지우면 시험이 깨지니 목록도 함께 고친다.
3. **큐브 창 생김새를 바꾼 PR에는 웹·네이티브 비교 그림을 붙인다.** 값 자료로 못 잡는 그리기·연출은 사람이 본다. 네이티브는 화면 밖 스크린샷 모드(창을 띄우지 않음), 웹은 앱과 같은 엔진 WebKit으로 찍는다.

```sh
apps/cubie/build.sh                                         # 이 폴더 안에 Cubie.app(설치하지 않음)
CUBIE_NATIVE_SHOT=<폴더> apps/cubie/Cubie.app/Contents/MacOS/Cubie        # 화면 밖 스크린샷(창·포커스 없음)
node apps/cubie/scripts/native-compare.mjs <폴더> [사이트 주소] # 바탕 넷 × 웹(WebKit)·네이티브 → <폴더>/compare.png, 말풍선·F1 표 → compare-panels.png
# 거울 판 전후(고치기 전 폴더·고친 뒤 폴더를 따로 찍은 뒤)
node apps/cubie/scripts/mirror-compare.mjs shoot <폴더> <사이트 주소> 160
CUBIE_NATIVE_SHOT=<폴더> CUBIE_NATIVE_SHOT_SIDE=160 apps/cubie/Cubie.app/Contents/MacOS/Cubie
node apps/cubie/scripts/mirror-compare.mjs sheet <결과.png> <전 폴더> <후 폴더> 160
```

- 사이트 주소는 기본이 `https://game.byb.kr`(배포된 판)이다. 고친 웹을 찍으려면 로컬 서버(`pnpm dev`, 또는 빌드한 `out/`를 띄운 주소)를 준다. 고친 화면에 맞는 그림을 `docs/cubie-native/`에 webp로 남기고 PR 본문에 붙인다.

## 6. 윈도우판을 언제 어떻게 낼지

- **Tauri로 먼저**: 몇 주 안에 낼 수 있고 지금 웹 화면을 그대로 쓴다. 메모리는 Edge 웹 화면이라 맥과 비슷하게 무겁다. 네이티브로 옮길 때 껍데기는 Rust라 일부(창·단축키·트레이)를 다시 쓸 수 있다.
- **네이티브로 바로**: 5절 2·3단계를 먼저 해야 해서 늦다. 대신 버리는 코드가 없다.

## 7. 정할 것

- 윈도우판: Tauri로 먼저 낼지, 네이티브 구조가 준비될 때까지 기다릴지.
- 윈도우판을 시험할 PC(사용자 본인이나 동료).
- 윈도우 서명: 처음엔 없이 낼지(SmartScreen 경고), Azure Trusted Signing(월 10달러 안팎)을 붙일지.
- 네이티브 단계를 지금 시작할지(2단계 코어부터), 앱 사용자가 늘면 시작할지.
